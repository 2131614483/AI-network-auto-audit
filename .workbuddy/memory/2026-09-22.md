### 真实差距（三条，均有实测数据）
1. **图谱基本是空的 —— 缺「插件目录 → 图谱」建图流水线**（最根本）
   - 实测：`capability` 节点 **3 个**（`capability:audit.ledger.validate` / `audit.finding.draft` / `quant.research-note.draft`）、

     **没有任何代码从插件目录自动建图**。
2. **只支持单跳展开**：`expand_to_capabilities` 断言 `expand_hops in (0, 1)`；且桥的目标被限定 `ts.level='L2'`。
   「多级展开」需要 L3 域 → L2 族/阶段 → L2 能力 → 端口契约 的逐级下钻，
   而**「族/阶段」这一层在图谱里根本不存在**（`pack.json` 里有 s1–s8 定义，但没建成图节点）。
3. **`similarity()` 排序用不上 GIN trgm 索引 —— 10 万级会退化成全表扫描**
   - `match_nodes` 是 `ORDER BY GREATEST(similarity(label,%s), alias子查询)`。
     GIN trgm 索引只服务 `%` / `LIKE` 操作符，**对 `similarity()` 排序不生效** → N 行逐行算相似度。
   - 修法两条：`SET pg_trgm.similarity_threshold` + `%` 粗筛（走索引）再精排；或直接用项目已配好的 **pgvector**
     （`EMBEDDING_DIMENSION=1024`）做 ANN 召回。

## 踩到的 4 个坑（都在实现中修掉，务必记住）
1. **`execute_values(..., fetch=True)` 的 `RETURNING` 顺序不可靠**。我原本用 `INSERT ... RETURNING canonical_key, id` 然后按位置 zip 成 `id_by_key`，结果**整张图的边都接到了错误的节点上**（节点自报 `properties.family=s4`，入边 source 却是 `s5`）。**修法：插入后单独 `SELECT` 回查映射**（`_node_ids`）。**不要依赖 RETURNING 顺序。**
2. **`audit_app` 没有 DELETE 权限**（项目原则：历史不可硬删）。所以重跑要"收敛"只能靠 **`valid_to` 软失效**（`UPDATE ... SET valid_to = now()`），所有读者都过滤 `valid_to IS NULL`。
3. **`contains` 与 `depends_on` 的同步语义必须分开**。第一版对两者都做"软失效不在推导集合里的边"，把 **0048 迁移人工建立**的语义边 `ledger.validate → finding.draft` 一起清掉了（它不在 `contract_edges` 里，因为它是治理声明而非端口兼容）→ planner 无法再展开。**修法：`contains` 由索引器独占可 reconcile；`depends_on` 必须 `retire_stale=False`（只增不删）。**
4. **node `label` 只填空、不覆盖**。第一版 `DO UPDATE SET label = EXCLUDED.label` 把 0048 人工写的中文名「总账质量校验」覆盖成插件的 `spec.name`「审计总账质量校验」，导致 `match_nodes` 的 `match_kind` 从 `direct` 退化为 `alias`，5 个 M10 测试失败。**修法：`label = COALESCE(NULLIF(graph.nodes.label, ''), EXCLUDED.label)`**；插件名仍记录在 `properties.name`。

# S2 召回可扩展性（同日完成）—— 结论反直觉，务必按实测走

## 目标
让 `CapabilityGraphAdapter.match_nodes` 在 10 万节点的图谱上仍然可负担。最初假设：
「`similarity()` 排序走不了 GIN，改用 `%` 操作符 + 阈值粗筛」。

## 实测推翻了那个假设（这是本次最重要的收获）
1. **`%` 方案在本项目的角色下不可用**。`%`（GIN trgm）语义与 `similarity >= x` 精确等价、
   索引也早已建好（0048），但**计划器需要选择性估计才肯选它**；而 `graph.nodes` 受 RLS 保护，
   以 `audit_app`（非 superuser）执行时估计**塌成表行数的 1 %**（50 000 节点：真实 7 行，
   估 1–509 行）→ **计划器放弃索引、改全表扫描**。
   - 定位过程：`SET ROLE audit_app` 在 superuser 会话里可复现 → 与角色有关；
     `GRANT SELECT ON pg_statistic TO audit_app` **无效**（排除权限假设）；
     `VACUUM` 前后都是 seq scan（VACUUM 只影响 GIN pending list，是另一个不相干的坑）。
   - **所以「改成 `%`」这条路不用再试**。

2. **正解是 GiST + KNN**：`ORDER BY label <-> q LIMIT k` 按距离有序扫索引、到 k 即停，
   **不需要任何选择性估计**，因此在 RLS 下照样走索引。
   - 迁移 `0067_graph_knn_gist_indexes` 新增两个 GiST trgm 索引（**GIN 保留**，
     M10 契约测试断言其存在）。
   - 实测（50 000 节点，`audit_app` + RLS）：oracle 全扫 **238–269ms → 6.0–6.6ms（约 40x）**，
     结果与 oracle **逐条一致**。

3. **两个陷阱**（都写进了 docstring，避免后人重踩）：
   - **有界 KNN 会失效**：`WHERE label <-> q <= 0.95 ORDER BY label <-> q` 语义上**精确等价**
     于 `similarity >= 0.05`（实测 5/5 查询零差异），但计划器又因有了可估的过滤条件而
     放弃 GiST 改全表扫描。**必须用无界 `ORDER BY <-> LIMIT k`，再在外层复核阈值**。
   - **候选来源必须两支**：label 与 alias 各走一次 KNN。只剪 label 会**静默丢掉全部别名匹配**
     （真实语料里恰好没有"仅别名命中"的节点，所以测试里**自建了探针**来覆盖）。

4. **正确性论证**：`k >= max_matches` 即可 —— 节点若在 label 维度前 k 之外，就有 k 个节点
   label 分更高、`GREATEST` 必然压制它；alias 维度同理。故 `GREATEST(label,alias)` 的 top-N
   必落在两分支并集里。实现取 `max(max_matches*4, 64)`，**4 倍余量是为了并列（tie）**。

## 交付物
- `packages/graph/graph_planning.py`：`_CANDIDATE_SQL`（KNN 两段式）+ `_candidate_budget`；
  **删除了 `_bind_similarity_threshold`** —— KNN 不依赖 `pg_trgm.similarity_threshold` GUC，
  那个「默认 0.3 vs 需要 0.05，没设对就静默漏召回」的陷阱随之消失。
- `migrations/versions/0067_graph_knn_gist_indexes.py`（主库与测试库都已 upgrade 到 0067）。
- `tests/integration/test_plugin_graph_recall.py`：27 个契约测试，**保留优化前的实现当 oracle**
  逐条对比；另含候选预算不变式、0.05–0.3 低相似度带不被丢弃、别名探针（自建数据 + 用后软删）。

## 验证
- 相关测试合集 **516 passed / 3 skipped**；`ruff check .` 全绿；`mypy packages` 130 文件 0 问题。
- `match_nodes` 端到端在 5 万节点、真实角色下从 250ms 降到 63ms。

## 顺带发现（未修，但值得单独排期）
**本机 PG 连接开销 ~55ms**：`psycopg2.connect` 稳定耗时 54.6–56.8ms，
`localhost` / `127.0.0.1` / kwarg 三种写法一样（**不是 IPv6 回退**，疑似 scram PBKDF2）。
于是 `match_nodes` 的 63ms 里 **~55ms 是连接开销，召回 SQL 本身只 7.5ms**。
项目里多处「每次调用新建连接」（`CapabilityGraphAdapter.match_nodes`、`GraphService.upsert_node`）。
**修法是连接池**，属架构级改动、影响面广，本次未动。

# S4 召回目录合流（同日完成）—— 10 万级真正会崩的那一环

## 要解决的问题
S1/S2/S3 让图谱"知道插件、能多级展开、召回够快"，但 AI 规划端点仍在用**全量目录**：
audit 域 107 插件 / 161 端口 → 提示词 **82 063 字符**。10 万插件时不可行。

## 实测收益
| | catalog | 契约 | 提示词字符 |
|---|---|---|---|
| 全量（改动前） | 108 | 166 | **82 063** |
| 「对底稿做三级复核后加密归档」 | 5 | 13 | **6 941**（11.8x） |
| 「识别高风险领域并抽取凭证」 | 6 | 13 | 7 581（10.8x） |
| 「总账质量校验并出具量化研究结论」 | 4 | 12 | 6 279（13.1x） |
| 召回为空的意图 | 108 | 166 | 回退全量 ✓ |

## 设计要点（都写进了 docstring）
1. **catalog 与 contracts 必须从同一次筛选派生**。提示词由 contracts 生成，而 `validate_draft`
   要求模型逐字段复制 catalog 里每个端口的契约 —— 若两个筛选各写各的，就会出现"目录里有端口、
   契约里没有"，模型看不到却被要求复制 → **必然 `contract_mismatch`**。这是 S4 最容易犯的错。
2. **召回为空 → 回退全量**（不是"给模型空目录"）。空目录只能规划失败；回退保证不退化。
   空召回是可识别的返回值（`recalled == ()`），不是静默行为。
3. **legacy 那一半永不裁剪**。CW5 demo 链与所有 TEMPLATES 依赖它，且它的端口只以 legacy 名存在
   （`ledger`/`candidates`）。**实测主库 legacy 只有 2 条**（`audit.ledger.validate`、
   `quant.experiment.evaluate`）—— 因为 `capability_catalog_from_db` 只收
   `capability_contract.capability` **非空**的蓝图，而 S1 注册的 100 个插件蓝图没有这个键，
   所以它们不进 legacy 目录（能力由 domain 目录提供）。职责因此很干净。
4. **图谱不可达时降级为全量**（捕获 `psycopg2.Error`）：召回是**优化**，不是前置条件。

## ⚠️ S4 暴露的下一个真问题：长意图的召回偏窄（实测，未修）

**现象**：真实用户的 goal 是自然语言长句（「对底稿做三级复核后加密归档」，13 字），
而图谱标签是短词组（「底稿三级复核」，6 字）。召回只返回 **2 条**能力、最高分仅 **0.105**。

**根因**：pg_trgm 的 `similarity(a,b) = 2|a∩b| / (|a|+|b|)` —— **分母含查询长度**，所以
查询串越长、与短标签的相似度就越低。中文又是字节级 trigram，稀释更明显。
这不是 bug，是 trigram 相似度的固有性质；但 `_MIN_SIMILARITY = 0.05` 这个阈值当年是
按短查询串校准的，长意图下只剩"勉强够用"，召回面自然窄。

**实测 `word_similarity` 明显更好**（取目标串中与查询最匹配的连续片段，不惩罚查询长度）：

| 长意图 | `similarity` top1 | `word_similarity` top1 |
|---|---|---|
| 对底稿做三级复核后加密归档 | 底稿三级复核 0.105 | 底稿三级复核 **0.286** |
| 识别高风险领域并抽取凭证 | 高风险领域定位 0.167 | 高风险领域定位 **0.375** |
| 请帮我对总账做质量校验 | 数据质量校验 0.188 | 数据质量校验 **0.429** |

top-1 命中一致，但信噪比明显改善（2.7–2.3x）。

**为什么没顺手改**：改用 `word_similarity` 是**评分语义的破坏性变更** ——
① 阈值要重新校准（`word_similarity >= 0.30` 在当前数据上命中 0 个，得降到 ~0.2）；
② M10/S3 的既有断言写死了具体分数（如「证据与底稿」→族 **0.556**），全部要适配；
③ 需另行验证 `<->>`（word distance）的 GiST KNN 是否同样走索引。属于独立一轮的改动。

**可作为过渡旋钮**：`recall_planning_directory(max_matches=16)` 已是 `match_nodes` 上限，
展开预算受 `_EXPANSION_CAP=8` 限制（硬编码）—— 若要放宽召回面，这是可动的参数。

# 实际启动 Electron 看画面（同日完成）—— 抓到一个我自己引入的破坏性回归

## 环境障碍：两个 WorkBuddy 注入项
1. **`ELECTRON_RUN_AS_NODE=1`**（还有 `NODE_OPTIONS=--require=...node-language-shim.cjs`）→ Electron 被当纯 Node 跑，
   报 `Cannot read properties of undefined (reading 'handle')`（`electron.ipcMain` 为 undefined）。
   **解法**：`env -u ELECTRON_RUN_AS_NODE -u NODE_OPTIONS npm --prefix desktop run dev`。
2. **`HTTP_PROXY=http://127.0.0.1:13556`** → `curl http://127.0.0.1:8010/...` 一律返回 **502**（代理无法连本地服务），
   会让人误判"API 不健康"。**解法**：用 Python 直连并先 `os.environ.pop` 掉 proxy 变量。

## 截图链路（用于"看画面"）
