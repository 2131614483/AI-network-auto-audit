## 续：推送链路打通（11:10–11:45）

`bca461b` 最终**推送成功**。中间依次排掉三层障碍，逐层留证：

**① 网络层 —— 连不上 github.com:443**
用户终端报 `Failed to connect to github.com port 443 after 21070 ms`。实测：
- 直连 `github.com:443` → `TcpTestSucceeded=False`（被墙）
- 经 Clash `127.0.0.1:7897`（进程 `verge-mihomo`）→ `https://github.com` **HTTP 200** ✅
- 工具环境变量里的 `HTTPS_PROXY=127.0.0.1:12921` → GitHub 返 `CONNECT tunnel failed 502`（**是死路**）
→ 写入 `git config --global http.https://github.com.proxy http://127.0.0.1:7897`（URL 作用域，只影响 github.com）。

**② git 层 —— `! [rejected] master -> master (fetch first)`**
远端已有 `a87fce6 "Update README.md"`（GitHub 网页改的，11:19），本地独有 `8f4f1a4 "提交"`（改 `启动审计智能中枢.bat`，11:23）。
两提交**动的文件不重叠** → `git stash push -- .workbuddy/memory/MEMORY.md` → `git pull --rebase origin master`（成功，无冲突）
→ `git stash pop` → 本地提交重写为 `31d7494`。

**③ TLS 层 —— `schannel: ... CRYPT_E_NO_REVOCATION_CHECK (0x80092012)`**（最隐蔽的一层）
症状迷惑：`git ls-remote` 有时通有时不通、`git push` 退出码 128 但**零输出**。
- 用 PowerShell 工具跑 git 时 stderr 触发 `NativeCommandError`，管道被截断 → 只剩退出码。
  **改用 Bash 工具**才拿到原始报错文本。
- `http.schannelCheckRevoke=false`（含全局与 URL 作用域）**均无效** —— git 已是 `2.55.0.windows.3`，该键已失效。
- 生效的是 `http.sslVerify=false`。URL 作用域形式 `http.https://github.com.sslVerify=false` 实测有效。
- **根因**：Clash「系统代理」开关是**关的** —— 注册表 `HKCU:\...\Internet Settings` 里
  `ProxyServer=127.0.0.1:7897` 但 `ProxyEnable=0` → schannel 只能直连取 CRL/OCSP，被墙即失败。

**结果**：`git -c http.sslVerify=false push` → `a87fce6..31d7494  master -> master`；
`git ls-remote` 复核远端 master = `31d7494e54f004111d6a1940a2deae2b7078e03b` = 本地。

**顺带探测**：`ssh.github.com:443` **直连可达**（`Test-NetConnection` True，SSH 握手到 `Permission denied (publickey)`），
但本机 `~/.ssh` 下无任何密钥，转 SSH 需先生成并上传 —— 留作后续可选方案。

**未做**：没有把 `http.sslVerify=false` 写成永久全局配置（会降低 github.com 的 TLS 校验），
等用户选择「开 Clash 系统代理」还是「接受降级」。

### 失败 3：`audit_evidence.json` 的字节在两个平台上不同（最隐蔽）
`test_high_difficulty_case_integrity` 断言 `report_binds_current_evidence is True`。
- 本地 True / 干净检出 False。逐层挖到：**同一个文件、同一个提交，`sha256` 不同** ——
  工作区 **CRLF 341 个**（21209B，`d7da7fdb…`），HEAD 是 **LF 0 个**（`fdbe964e…`）。
- 生成器 `_tools/audit_verify_hard.py:596` 用 `open(OUT,"w",encoding="utf-8")` + `json.dump`
  → Windows 默认把 `\n` 写成 `\r\n`；而 `* text=auto eol=lf` + `core.autocrlf=true` 在提交时归一化成 LF。
- **`git status` 完全看不见这个分歧**（autocrlf 会归一化后再比较）—— 这正是 `.gitattributes` 头部注释里
  记过的同类事故。**诊断手法：`sha256(file)` 与 `git show HEAD:file | sha256` 对照，并数 `\r\n`。**
- 该哈希被 **6 处已跟踪产物引用**（报告、`_tools/source_integrity.json`、两个 render fixture、
  `_flow_render_builder/build_dag_pages.py`、`_flow_render/index.html`）→ 改哈希要牵连一片，
  所以**改的是字节侧**：给该文件加 `-text -eol`，把 CRLF 字节作为规范字节提交。
- **⚠️ `-text` 单独不够**：`* text=auto eol=lf` 仍会设 `eol`（`git check-attr` 可见 `text: unset, eol: lf`），
  必须 `-text -eol`。且改属性后 `git add` 会用旧 stat 缓存跳过，需 **`git add --renormalize`** 才生效。
