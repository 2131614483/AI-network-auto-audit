## 二·A 时间成本复盘：R4（高难度）为什么明显更耗时

### A-1 可验证的时间线（按文件时间戳与会话节点）

| 时间 | 事件 | 产物 |
| --- | --- | --- |
| 21:24–21:36 | 高难度案例造数脚本链 | coa.py（13.6KB）→ case_design.py（41KB）→ selfcheck.py（10KB）→ gen_hard_data.py（103.8KB）→ make_docs.py（15.6KB） |
| 22:09 | 对 51 个资料文件做结构探查 | probe_schema.py（856B），产出数据字典 |
| 22:09–22:34 | **审计取证核心阶段：audit_verify_hard.py 连续多轮迭代** | 37,880 字节，v3 定型 |
| 22:34 | 取证结果落盘 | audit_evidence.json（21.2KB：24 findings + 5 noises） |
| 22:34 后 | 引用证据撰写报告 | 审计报告(实验组_高难度).md（361 行） |

对比 R2（20:32 数据验证 → 21:03 报告扩展，3 个会话内完成）与 R3（21:51 读要求/资产 → 22:00 全流程一次跑通 42/42，单会话完成）：**R4 从造数完成（21:36）到取证定型（22:34）就花了近 1 小时，且取证后还有报告写作——总耗时为前三份的 2–3 倍。**

### A-2 原因分析（按贡献度排序）

1. **能力重心发生质变（主因）**：R3 的 42 项漏洞以确定性规则为主（T1/T2 占多数），detect_issues.py 可以直接枚举规则；R4 的 24 项中 **T3–T5 占 16 项（67%）**，没有现成规则可抄——每项都要"设计取证方案 → 探查数据结构 → 编写重算逻辑 → 验证命中参考值"走完一整轮。这是 5+ 轮脚本迭代的根源。
2. **取证脚本边界约束更强**：R4 要求探测器只读原始 CSV/MD、不引用生成器内存变量、独立重算（如折旧逐卡重算、账龄回原始日期），正向逻辑（算出应有值）比反向逻辑（查已算好的值）工作量成倍增加。
3. **噪音排除比检出更贵**：检出只要"有一个信号命中"；排除要"证明该信号为什么合规"（披露完整性 + 政策合规性双重确认），每项噪音的证据链长度与漏洞相当。
4. **隐藏手法升级导致双线排查**：R4 的错报用对冲（H03）、合并抵消（H04/H22）、趋势信号（H05/H08）、文字线索（H09/H10）、单位陷阱（H11）五种形态藏身。每次"未命中参考值"，必须先判断是**脚本逻辑错**还是**数据口径错**，两条线都要排查才能改一处代码——调试本身变成审计判断。
5. **脚本工程化程度不足（非审计专业的开销）**：本次报错有一半以上是 SyntaxError / Decimal 序列化 / JSON 键类型等纯工程问题，与审计专业无关，却占用了大量调试时间（见 §二·B）。
6. **会话上下文丢失的恢复成本**：R4 任务跨会话进行，期间一次上下文丢失需要依据摘要重建取证进度，恢复本身消耗了时间。

## 二·B 报错明细与解决完善方案（R4 实证清单）

### B-1 语法与运行时错误（按出现顺序）

| # | 报错 / 现象 | 位置 | 根因 | 修复方式 |
| --- | --- | --- | --- | --- |
| E1 | `SyntaxError: f-string: unmatched '['` | H21 客户集中度 | f-string 内再嵌带引号的 f-string，引号解析混乱 | 改为先构造元组列表再格式化：`[(r['排名'], r['客户名称'], r['占营业收入比例']) for r in top5]` |
| E2 | `decimal.InvalidOperation: ConversionSyntax` | H04 个税归属 | 从字符串里拆分金额，遇到非数字文本 | 不再解析字符串，改用字典直接匹配计提主体与缴纳主体 |
| E3 | `ValueError: invalid literal for int() with base 10: ''` | H05 季度统计 | 个别行季度字段为空，int() 收到空串 | 空季度归入默认键 `"?"`，保证 sorted 稳定 |
| E4 | `SyntaxError: invalid character '，' (U+FF0C)` | H19 未决诉讼 | 代码里混入中文逗号 | 中文逗号改英文逗号，同步调整 f-string 引号嵌套 |
| E5 | `TypeError: keys must be str, int, float, bool or None, not tuple` | H11 消费税 | JSON 序列化时用了 `(主体, 产品)` 元组键 | 键改字符串 `f"{会计主体}|{产品}"` |
| E6 | `TypeError: Object of type Decimal is not JSON serializable` | H11 及全量落盘 | 证据值含 Decimal | 金额统一转 str / int 后再序列化 |

**共同点**：E1–E6 全是"防不胜防的工程细节"，单次修复 1–2 分钟，但每次都要重跑全量脚本（30+ 秒级），累计吃掉大量轮次。

### B-2 取证逻辑未命中（比报错更贵的部分）

| # | 现象（预期 vs 实测） | 根因 | 修复方式 |
| --- | --- | --- | --- |
| L1 | H01 暂估差额未命中 6,800,000 | 按日期匹配发票，而非按发票号关联入库单 | 改按发票号逐笔匹配；差额 = 发票汇总 − 入库汇总 |
| L2 | H02 账龄重算不显示 4,500,000 | 未识别"被压入 1 年以内的 1–2 年金额"（某某商贸 18,000,000） | 明确识别压档行：按原始赊销日期重算分档，落到 1–2 年档 |
| L3 | H03 折旧净差不对 | 转固月数/已达应计上限的处理规则不符 | 逐卡重算"应计折旧总额上限"，超提 6,032,500 与少提 6,483,750 分开列示 |
| L4 | H05 少转成本不是 38,000,000 | 把非批发成本混入；售后回购合同（XS-2025-011）与春酿跨期行未排除 | 新增 `cost_w_by_q` 仅归集黔岭销售 S1 主体 6401 借方；排除回购/跨期；按 Q2/Q3 正常率 38.44% 倒推应结转 |

| L6 | H13 租赁现值偏差 | PVIFA 提前量化导致精度漂移 | 先算未量化 `(1-1.05^-5)/0.05`，再四舍五入 4 位（4.3295），现值 = 9,000,000 × 4.3295 = 38,965,500 |
| L7 | H14/H16/H21 边界不对 | 费用跨期归集范围、盘亏净值（原值−累计折旧）、客户集中度口径 | 按单据日期过滤 ≥2026；净值 = 原值 34,000,000 − 折旧 11,166,666.67；Top5 客户占比独立重算 |

### B-3 解决与完善方案（针对 A-2 与 B-1/B-2 逐条落实）

| 方案 | 解决的痛点 | 具体做法 |
| --- | --- | --- |
| **S1 取证原语工程化** | B-1 全部（语法/序列化反复） | 把 Decimal 工具函数、安全金额提取、账龄重算、逐卡折旧、跨表比差、JSON safe_dump（Decimal→str）固化为公共工具库；**禁止嵌套 f-string、金额一律走工具函数**写成强制约定 |
| **S2 数据字典先行** | A-2#4、L5（单位陷阱） | probe 探查后先产出数据字典（字段/单位/主键/样例），单位校准（万瓶↔瓶）在字典层一次完成并写入报告 §2，程序不再各自猜口径 |
| **S3 三段式验收** | A-2#2、B-2 返工 | 脚本完成后按"① 语法+序列化冒烟 → ② 24 项命中 → ③ 5 项噪音排除"三段验收，任一段失败不回退重写，而是定点修复后全量重跑一次 |
| **S4 双线排查协议** | A-2#4 | 未命中参考值时不急动代码：先打印中间变量（应结转、实际结转、差额）判断是"逻辑错还是口径错"，**一次只改一处**，改完跑全量 |
| **S5 常量治理** | 第五章#1（照着答案调参风险） | 造数脚本"设计参考值"与探测器"行业常识常量"彻底分离；报告中对设计与实测差异显式说明（如 H11 设计 2,900,000，实测 2,900,000+ 略高） |
| **S6 证据快照绑定** | 第五章#3 | 报告头部记录所用 audit_evidence.json 的 SHA-256；取证脚本、证据 JSON、报告三者同步版本号，防"证据改了报告没同步" |
| **S7 上下文韧性** | A-2#6 | 长流程开工前先固化"任务需求.md"（预期清单摘要 + 数据字典 + 报告骨架 + 已完成进度），即使上下文丢失也能据此重建，不重复踩坑 |

**效果预估**：S1–S4 直接消除 R4 中约 60% 的返工轮次（报错与未命中都变成一次性通过）；S5–S7 消除"隐性返工"（调参争议、版本漂移、恢复成本）。若 R4 重做，预计取证轮次可从 5+ 降到 2 轮以内。

## 三、遇到的困难与解决方式（方法论层）

| 困难 | 表现形式 | 解决方式 | 沉淀规则 |
| --- | --- | --- | --- |
| 伪造的安心感 | 汇总数完全平（账龄合计=总账），"没问题" | 放弃汇总数，用原始赊销日期逐笔重算账龄 | 不信任汇总数，回原始单据重算 |
| 对冲型错误 | 超提 6,032,500 与少提 6,483,750 互抵，净差 451,250 低于重要性 | 逐张卡片独立重算并检查应计折旧上限 | 逐条重算而非核对合计数 |
| 合并抹平真相 | 跨主体归属错位在合并层消失 | 分主体取申报表与账面对 | "分主体比对"应是默认程序 |
| 藏在趋势里 | 单月无异常，Q4 毛利率跳升 6.8pp | 分季度毛利率趋势线 + 白酒行业常识 | 主动做分析性程序，不只查点 |
| 该有的表没有 | 资料包缺"存货跌价测试表" | 周转天数 210→340 反推减值迹象，独立测算可变现净值 | 由缺失证据反推 + 比率分析 |
| 一行字的线索 | 售后回购/代理协议只写进合同台账关键条款 | 逐份通读合同条款，判断控制权转移/主要责任人 | 研读文本线索 + 实质重于形式 |
| 语义陷阱 | "万瓶"实为"瓶"；"按预算成本结转"实为少转成本 | 用交叉证据定价（售价 500 元/瓶）校准单位口径 | 单位/口径必须独立校准，不信表头 |
| 噪音伪装 | N01 关联交易等外观与漏洞一致 | 披露完整性 + 政策合规性双重确认后排除 | 排除必须给出"为什么合规"的证据 |

## 六、经验教训沉淀（可直接复用的清单）

- **数据即证据**：每个数字来自机器实测，禁止凭声明值/记忆写报告。
- **可复算**：任何关键 KPI 都能被脚本逐行重算；报告发布前重跑一次取证脚本。
- **可追溯**：发现必须锚定"文件 + 行/值/单据编号"；编号（F/P/E）全文一致。
- **造假是系统性行为**：错报常以"对冲、合并抵消、藏在趋势、该有的表没有、一行字线索"五类形态隐身——对应五类反制程序。
- **诚实优先**：未验证项进边界声明，绝不提前写"已验证"。
- **先要表再写程序**：组网成败首先在数据域完备性（对照组 F7 教训）。
- **只读血缘**：程序只读原始 CSV/MD，不引用生成器内存变量；无随机、无网络、无 LLM。
- **工程细节是隐性杀手**：语法/序列化/类型类报错有通用解法（禁止嵌套 f-string、金额走 Decimal 工具、JSON safe_dump），应固化为工具库与强制约定，而不是每次现场修——R4 一半以上的调试轮次来自这类非专业问题。
- **耗时与难度不是线性关系**：漏洞从"规则可检"转向"职业判断"时，取证工程量至少翻倍；排错还应遵守"一次只改一处、先判逻辑错还是口径错"。
- **详细度不是"章节齐"，是"逐项可查"**：§7/§8/§9 的达标线是"每个插件独立小节、每条边逐条列全、每个源 ≥2 行原始行"，而不是"有这几个章节标题"。骨架越顺，越要防"填标题不填内容"（§七·B）。
- **文件手术：清理与写入必须分开**（S8）：`rm -f` 与拼接写在同一条命令 → 工具重试会造成"第一次已成功、重试报 FileNotFoundError"的**假失败**。清理单独执行、先备份、拼接脚本带幂等断言。
- **标准要对着标杆校验**（S10）：写"详细度标准"后必须拿标杆报告逐条回验；两者冲突时先判断谁才是正确形态，再改错的那一方——否则会写出一条连标杆自己都不满足的规则。

## 七、插件级稳健性优化方案（把一次性经验固化为插件能力）

> 前一版的 S1–S7 是"过程与工具约定"，靠写脚本的人自觉执行；本节把同一条教训**升级为插件契约内建能力**——由协议化的插件提供固有能力，框架层面天然兼容 R4 暴露的六类脆弱点，不再依赖每次"小心翼翼写脚本"。
> 定位声明：本节为**设计提案**，落地验证仅使用独立测试数据库的合成数据，不触碰真实基础设施与生产数据（符合 AGENTS.md 阶段边界）。

### 7.1 总体架构：证据锻造套件（evidence-forge，4 插件接入既有 L0–L5）

| --- | --- | --- | --- |
| **P-E0 evidence-dictionary** 数据字典 | `audit.network.evidence-dictionary` | L5 单位陷阱、B-2 口径错位、A-2#4 一半的排错 | 探查后强制产出字段级字典（字段/单位/主键/样例）；单位校准规则表（"万瓶↔瓶"、千分位、含税价）在字典层一次完成，程序只读字典、禁止各自猜口径 |

### 7.3 契约与治理对齐（沿用项目既有规范）

- **三件套**：每个插件产出 `plugin.manifest.json` + `plugin.protocol.json` + `plugin.runtime-binding.json`（模板对齐 `plugins/builtin/audit_network_skill_output` 现状）。
- **只读边界**：`side_effects: read_only`、`permissions.data_write: []`、`network: none`、`secrets: []`——与 AGENTS.md"插件只读、无网络"硬约束一致。
- **治理**：`policy.gateway_required / approval_required / evidence_required: true`、`observability.trace_required: true`；每次执行带租户、trace_id 与幂等键。
- **幂等**：P-E1/P-E2 幂等键 = 输入工件 SHA-256 + 程序/原语清单哈希 + 插件版本；同输入重跑产出同哈希证据，天然防重复导入与版本漂移。
- **生命周期**：协议层 `lifecycle: contract_only`；若建蓝图则 `planned`，不携带 runtime/entrypoint 字段（memory 既有教训）。
- **契约先行**：每个插件先写 `tests/contract/` 契约测试 + `tests/unit/` 回归测试，再实现 runtime.py（符合 AGENTS.md"先更新契约和测试，再实现服务逻辑"）。

### B-5 本轮新增的三个坑（已并入 §二·B 的 S 清单）

| # | 坑 | 根因 | 规则 |
| --- | --- | --- | --- |
| S8 | **`rm -f` 与"拼接"写在同一命令 → 假失败** | 工具对失败的命令会重试：第一次拼接**已成功**，紧随的 `rm -f` 删掉了草稿；重试时草稿已不在 → `FileNotFoundError`。**看起来失败，其实文件早已改好**。一度误判"内容丢失"并重写一遍 | ① 清理命令**永远单独执行**；② 大段文本手术**先备份**（本次留 `.data/backup/`）；③ 拼接脚本加**幂等断言**（锚点缺失即退出、不写），否则重跑会把已改好的文件改坏 |
| S9 | **中文路径 + heredoc 的编码风险** | 含中文路径的脚本走 shell heredoc 曾在拼接处失败 | 草稿与拼接脚本落 **ASCII 路径**（`.data/draft/`），中文路径写在 UTF-8 源文件里而**不写在命令行**上 |
| S10 | **标准 vs 实现的双向校验缺位** | v1.1 的 §7 条目照"理想形态"写，没对着标杆报告核 | 写详细度标准后，**必须拿标杆报告逐条回验**；标准与标杆冲突时，先判断谁才是正确形态，再改错的那一方 |

### B-6 验收方式（不靠"看起来够长"）

- **规模**：逐份统计行数 / 字节 / §7·§8·§9 各自行数 / 占比（脚本量测，非目测）。
- **逐源**：§9 按围栏内行数逐源统计，报出"数据行 <2 的源"与"说明行 <4 的源"清单。
- **编号**：高难度按 P1–P28 + PN1–PN5 逐个 grep 是否都有独立小节；扫"节选 /（缩略）/ E1–E18"等陈旧写法残留。
- **结构**：代码围栏配对、表格行数、拼接接缝上下文。
- **一致性**：三份报告同一数据源的取值对齐（本轮据此把基础版 §9 S10 的补助到账日期由 08-20 更正为源文件的 **12-20**）。

## 八、一句话总结

> R2 教会我"报告骨架"，R3 教会我"程序即证据"，R4 教会我"判断要证据、排除也要证据"，还教会我"工程细节欠账会在最难的一份上集中偿还"——R4 的耗时与报错不是白费的：5+ 轮迭代把每一条坑都变成了工具约定与排查协议（S1–S7），下次再遇同一难度，取证轮次可以压缩到 2 轮以内。四份文档的问题没有一次是重复的，每一次报错都对应一条可沉淀的规则，这正是这套方法能持续自愈的原因。
>
> **补一句（交付后追加）**：这四份报告随后又经历了一轮"详细度补齐"（§七·B），说明"骨架复用"本身是双刃剑——它让交付变快，也让"只填标题不填内容"变得难以察觉。真正的门禁不该是"章节齐不齐"，而是"每个数字能否回溯源文件、每个插件是否有独立小节、每个源是否有 ≥2 行原始行"。另有一条自纠值得记住：**写标准时要对着标杆报告校验，而不是对着理想形态**——v1.1 里那条不实的 §7 要求，正是照理想形态写出来的。
