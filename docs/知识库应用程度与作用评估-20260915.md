# 知识库在本项目中的应用程度与作用评估

- **评估日期**：2026-09-15
- **评估对象**：`audit_network` 仓库中的「知识库」子系统（知识域）
- **评估方式**：全量只读 —— 代码可达性 grep、数据库直查（`local-dev` 租户）、真实调用检索服务、迁移与文档交叉核对
- **一句话结论**：知识库是一个**已建成、已通电、可运行**的一等子系统（2,846 行代码 / 16 张表 / 39 个端点 / 桌面一级导航），但它**在"审计组网"这条主线上只承担了一个窄角色**——知识图谱作为组网规划的语义索引；而它更显眼的"文档知识库 / RAG"能力，因语料是测试残留、向量索引近乎空白、且未接入 AI 起草链路，**当前实际处于"可演示、未生产"的状态**。
- **本次改动声明**：仅新增本文件，未修改仓库中任何其他文件

## 一、结论速览

| 问题 | 结论 |
| --- | --- |

## 二、界定：本项目里的「知识库」指什么

先澄清一处**同名不同物**，否则后续所有数字都会被误读：

| 名称 | 实体 | 位置 | 性质 |
| --- | --- | --- | --- |
| **知识库**（本报告对象） | 文档摄入 → 分块 → 向量/全文检索 + 知识图谱治理 | `packages/knowledge/`、`semantic.*`、`knowledge.*` | 一等子系统，桌面有独立页面 |
| **知识星云** | **插件拓扑**的可视化（插件=节点、接口=子节点） | `desktop/src/public/knowledge-nebula.html`、`ai_planner/nebula_graph.py` | 纯前端投影，与文档语料无关 |

两者共用 `knowledge` 前缀，容易被当成同一个东西。本报告只评前者（下文简称"知识库"），必要时才提及知识星云。

知识库由**两个 schema 分工**：

```
semantic.*    语义层：documents / chunks / chunk_embeddings（pgvector）
               └ 存"内容"，是检索的对象
knowledge.*   治理层：ingest_* / releases / change_sets / conflict_* /
                     arbitration_decisions / validation_runs / recycle_bin /
                     rich_media_jobs / upload_idempotency
               └ 存"这批内容怎么进来的、谁批的、发过没有"，是审计轨迹
```

## 四、应用程度：四层判定

判定口径：**建成 ≠ 通电 ≠ 有数据 ≠ 真在用**。逐层给结论。

| 层 | 判定 | 依据 |
| --- | --- | --- |
| ① 已建成 | **✅ 完整** | 2,846 行、16 表、39 端点、6 阶段方案、22 测试文件 |
| ② 已通电 | **✅ 高** | API + 桌面页 + Worker + Policy 四层全接；降级路径有实现 |
| ③ 有真实数据 | **❌ 否** | 语料为测试残留（见 §5.3），无业务知识 |
| ④ 真在被用 | **⚠️ 部分** | **图驱动规划在用**（16 次意图）；**文档 RAG 未被任何业务流调用** |

### 4.1 「④ 真在被用」的精确边界

这是本次评估最关键的一节。我把"知识库被谁调用"按**调用方**列全：

| 调用方 | 是否使用知识库 | 证据 |
| --- | --- | --- |
| 桌面端「知识库」页 | ✅ 直接用 | `App.tsx` 14 处 `/api/v1/knowledge/*` 请求 |
| API 端点 | ✅ 直接用 | `apps/api/main.py` 10 处 `packages.knowledge` import |
| 富媒体 Worker | ✅ 直接用 | `apps/worker/local.py:18-19` |
| **图驱动规划** | ✅ **间接用**（图谱侧） | `packages/plugin_topology/graph_planning.py` 读 `topology.blueprint_graph_links` |
| **AI 规划器（模型起草）** | ❌ **不用** | `packages/ai_planner/` 全目录 grep `knowledge\|retrieval` **零命中** |
| **审计/组网执行引擎** | ❌ 不用 | `ports_executor.py` / `compiler.py` 不引用知识库 |
| 报告生成 | ❌ 不用 | 报告写作走 `skills/audit-report-builder`，不读语料 |

**结论**：知识库**不是**这套系统的 RAG 底座。它是一条**独立的、面向人的知识工作台**（用户自己上传、检索、管理），外加一条**面向图的能力索引**。审计组网主线既不从知识库取证据，也不从它召回插件。

## 五、实测：检索到底能不能用

### 5.1 三种检索模式的实跑结果

查询串统一用「审计 风险 分类」，服务直连主库：

| 模式 | 结果 |
| --- | --- |
| `keyword` | 0 命中 |
| `vector` | **抛错** `AIClientError: ollama embedding unavailable: <urlopen error [WinError 10061] 目标计算机积极拒绝>` |
| `hybrid` | 0 命中（**未抛错**） |

`hybrid` 之所以不抛错，是因为 `retrieval.py:319-323` 只捕获 `RuntimeError`，而 `AIClientError` 恰好是 `RuntimeError` 的子类（已实测 MRO 确认）——**降级为纯全文检索**。这条设计是对的：向量服务挂了，检索能力退化而不中断。

### 5.2 正向对照：全文检索本身是好的

为排除"是不是检索坏了"，用**语料里确实存在的英文**做正向对照：

| 查询 | 命中 | 首条得分 |
| --- | --- | --- |
| `Revenue Cutoff` | 2 | 0.484 |
| `Control evidence` | 2 | 0.548 |
| `Hello` | 1 | 0.207 |
| `knowledge test` | 2 | 0.517 |
| `审计` | 3 | 0.100 |
| `审计风险` | 2 | 0.006 |
| `风险` | 3 | 0.004 |
| `贵州` / `黔岭` / `约定书` / `专项审计业务约定书` | **0** | — |

**判定**：检索链路本身工作正常；命中低是**语料问题，不是代码问题**。

### 5.3 语料构成（主库 `local-dev` 租户）

| 指标 | 值 |
| --- | --- |
| `semantic.documents` | **166**（159 `staged` + 7 `retired`） |
| `semantic.chunks` | **596**（其中当前版本且非 retired 的**可检索分块 555**） |
| 含中文的分块 | **59 / 555（10.6%）** |
| 样本文档标题 | `memo`、`first`、`missing-key`、`probe` |
| 样本 `source_uri` | `drop://825c8f815f5d3921/nested/memo.md` |
| 样本分块内容 | `# Hello  This is a knowledge test.` / `# Revenue Cutoff  Control evidence.` |
| 唯一的中文"文档" | `README-清单` ——「审计素材资料合集 · 下载清单」（内容为 `G:\数据` 的 GitHub/HuggingFace 下载记录） |

**判定**：主库知识库里**没有真实业务知识**。555 个分块中 89% 是英文测试夹具，唯一的中文文档是一份**数据下载清单**——恰好证明这条管道被真实用过（导入过 19 个链接的下载说明），但导入的不是"知识"。

### 5.4 向量索引：覆盖率 1.4% 且模型是测试模型

| 项 | 值 |
| --- | --- |
| `semantic.chunk_embeddings` | **28 条** |
| 按模型分布 | `test-1024` **20 条**（测试残留）／`qwen3-embedding:0.6b` **8 条** |
| 可检索分块 | 555 |
| 覆盖率（任意模型） | **28/555 = 5.0%** |
| 覆盖率（当前模型） | **8/555 = 1.4%** |
| 当前 embedder | `AI_EMBED_PROVIDER=ollama` → 默认 `qwen3-embedding:0.6b`（`packages/ai/config.py:42`） |
| Ollama 服务 | **当前停止** → `embed_pending` 与 `_vector` 均不可用 |

### 5.5 一个必须指出的误报

`KnowledgeRetrievalService.stats()`（`retrieval.py:175-213`）返回：

```
vector_ready = embeddings > 0      # ← 只数"有没有向量"，不校验"是不是当前模型的"
embedding_model = 最近一条向量的 model_key
```

实测返回 `{'documents': 159, 'chunks': 555, 'embedding_chunks': 28, 'embedding_model': 'test-1024', 'vector_ready': True}`。

于是桌面端统计卡会显示**绿色「向量可用」**，而实际当前模型的可用向量只有 8 条（1.4%）；同时把测试模型的 `test-1024` 当作语料的嵌入模型展示给用户。见 §7 的 P1。

## 六、知识库对「组网」的作用（本报告的核心问题）

拆成三条独立链路看，只有一条真正通了。

### 6.1 ✅ 通了的：知识图谱 → 组网规划的语义索引

这是知识库**唯一进入业务主线**的作用，且是有意设计的：

- 迁移 `0048_graph_driven_planning` 的文档头写明目的：*"Breaks the 'intent -> plan' dead link by turning the knowledge graph into the semantic index for orchestration planning."*
- 机制：`topology.blueprint_graph_links` 把图节点绑到蓝图键（L2 能力 / L3 域空间）；`GraphPlanningService`（`packages/plugin_topology/graph_planning.py`，221 行）读它生成 `plan_only` 计划，并把每次请求作为**追加式证据行**写入 `topology.planning_intents`。
- 闸门：由 `topology.intent.plan` 能力把守（low / write_data，**seed 为 inactive，fail-closed**；`local-plugin-topology-graph-plan` 策略集放行）。
- 端点：`POST/GET /api/v1/topology/planning/intents`（+ 详情）。

**实测数据**：`topology.blueprint_graph_links` **3 行**、`topology.planning_intents` **16 行**。

**双重含义**：
- 正面 —— 这条链**被真实调用过 16 次**，不是纸面设计；图 → 能力 → 计划的桥是活的。
- 局限 —— 只有 **3 条**图↔蓝图绑定（对应 3 个真语义蓝图 `ledger-quality-slot` / `finding-draft-slot` / `research-note-slot`），所以"图作为语义索引"的**覆盖面很窄**：16 次意图都只能落到这 3 个键上。

### 6.2 ❌ 没通的：文档语料 → AI 起草（RAG）

- `packages/ai_planner/` 全目录 grep `knowledge` / `retrieval` / `embed` **零命中** → 规划器不检索语料。
- 规划器的能力召回走 `composer.recall_by_keywords`，匹配的是**插件名/描述/capability**，不查文档库。
- 结论：**"上传一份准则/案例 → AI 起草时参考它" 这条最自然的 RAG 用法，本项目没有实现**。

### 6.3 ⚠️ 口径冲突：知识域插件"实现了但不可执行"

| 插件 | capability | `runtime.py` | 协议 `lifecycle` | 在 `VERIFIED_PLUGIN_IDS` |
| --- | --- | --- | --- | --- |
| `knowledge.document-ingestion` | `knowledge.extract.document` | 111 行 | `contract_only` | ✅ 在 |
| `knowledge.entity-relation-candidate` | `knowledge.extract.relations` | 252 行 | `contract_only` | ✅ 在 |
| `knowledge.graph-proposal-builder` | `graph.proposal.build` | 332 行 | `contract_only` | ✅ 在 |
| `knowledge.retention-recommendation` | `knowledge.retention.recommend` | 204 行 | `contract_only` | ✅ 在 |

**矛盾**：4 个插件共 **899 行 runtime 已实现**、`load_verified_binding()` 全部可加载、也都在可执行允许清单里；但协议声明 `contract_only`。后果是：

```
discover_plugins(domain="knowledge")                       -> 4
discover_plugins(domain="knowledge", lifecycle="verified")  -> 0     ← 默认规划口径
discover_plugins(domain="knowledge", lifecycle="contract_only") -> 4
```

即：任何按 `verified` 过滤的路径（`compose_and_compile(select=VERIFIED)`、AI 起草的能力召回）**看不到知识域**。而实际上它们比多数 `verified` 插件实现得更完整。见 §7 的 P3。

### 6.4 ❌ 通了一半：经验 → 知识的"轻固化"通道

迁移 `0057_experience_solidify` 设计了这条链：人采纳一条关系建议后 → 记为 `knowledge.change_sets`（`change_type='experience'`）→ 经知识发布生命周期（release）变成"已确认关系"。

**实测**：`knowledge.change_sets` 68 行，**全部是 `change_type='graph'`，`experience` 类型 0 行**；`experience.relation_suggestions` 0 行；发布关联字段（`release_id`）无一行非空。

**判定**：**通道已建、从未产出**。知识库在这里的角色是"治理发布通道"（被经验层复用），不是知识来源。

## 七、发现的问题（按严重度，均带证据）

### P1（中）`stats()` 的 `vector_ready` 误报，UI 因此给出错误的可用性信号

- **证据**：`packages/knowledge/retrieval.py:212` `"vector_ready": embeddings > 0`；实测 `vector_ready=True` 而当前模型向量仅 8/555；`embedding_model` 取自"最近一条向量" → 报出测试模型 `test-1024`。
- **影响**：桌面端显示绿色「向量可用」，用户据此以为向量检索正常；实际 `vector` 模式会因 Ollama 未启动而抛错。
- **修法**：判定改为"当前 embedder 模型下的向量覆盖率"，例如
  `count(*) FILTER (WHERE embedding.model_key = <active_model>)`，并与 `chunks` 总量比对；`embedding_model` 同样取当前模型而非"最近一条"。
- **附带**：`test-1024` 这 20 条是测试残留，应清出主库（属测试污染，不是设计问题）。

### P2（中）主库语料是测试残留，无真实业务知识

- **证据**：555 个可检索分块中仅 59 个含中文；文档标题 `memo`/`first`/`probe`/`missing-key`；`source_uri` 形如 `drop://<8hex>/nested/memo.md`；分块内容 `# Hello  This is a knowledge test.`。
- **影响**：任何"知识库用得很好"的印象都来自 UI 完成度，不是数据。同时说明**接口测试直接写入了工作库**（`audit_network`）而非测试库。
- **修法**：为知识库 API 测试加 `audit_network_test` 强制（与 Phase 2.1 第 3 条同类问题，但当年只覆盖了"上传/回收/恢复"路径）；主库做一次语料盘点与清理。

### P3（中）知识域 4 插件 `contract_only` 口径冲突

- **证据**：见 §6.3。`runtime.py` 合计 899 行、绑定可加载、在允许清单内，但 `lifecycle=verified` 下为 0。
- **影响**：知识域在**默认规划口径下不可见**；同时 `contract_only` 又在图谱/域包中占位，形成"既不算可执行、也不是纯声明"的第三种状态。
- **修法**：二选一并保持一致 —— 要么把这 4 个插件标 `verified`（它们已有 runtime 与绑定），要么从 `VERIFIED_PLUGIN_IDS` 移除。**推荐前者**：这正是"把 contract_only 的插件跑成 verified"的现成候选（12 个缺口里最容易兑现的一批）。

### P4（中）RAG 未接入 AI 起草

- **证据**：`packages/ai_planner/` 对 `knowledge`/`retrieval` 零引用；能力召回只匹配插件元数据。
- **影响**：知识库对"审计组网"没有语义增益；上传的准则/案例不会影响 AI 起草。
- **修法**（若要做）：在 `AiPlanner` 的草稿阶段加一路可选召回 —— 用 `KnowledgeRetrievalService.search(mode="keyword")` 取 Top-K 分块塞进 prompt，**只作为上下文，不进入能力白名单/端口契约/数据边界判定**（守住"经验与知识只改变概率分布，不改变权限集合"这条既有约束）。

### P5（中）主库 209 个 active 策略集，其中 182 个疑似测试残留

- **证据**：`policy.policy_sets` 中 `status='active'` 共 **209** 行；按前缀统计 `api-test-*` / `knowledge-api-*` / `phase2-document-lifecycle-*` / `route-audit-*` / `scheduler-*` / `graph-visual-*` / `operations-api-*` 合计 **182** 行。
- **影响**：策略引擎是**跨 active 策略集加性**的（本仓既有结论），因此这 182 个残留集**都在贡献授权**，把主库的授权面撑到远大于设计意图。这已不是"脏数据"，而是**授权面被污染**。
- **修法**：把知识库/图谱类 API 测试强制指向 `audit_network_test`；主库做一次残留集清理并加防污染门禁（可参照 `tests/conftest.py` 既有的 `_policy_grants_do_not_leak`）。
- **说明**：`docs/status.md` 曾把"dev 库 203 条遗留策略集"标为"已接受决策"，本次实测为 209 条（仍在增长），建议重新评估该决策。

### P6（低）中文全文检索对 CJK 不分词，多词查询易 0 命中

- **证据**：`retrieval.py:265-280` 用 `websearch_to_tsquery('simple', query)`；PostgreSQL `simple` 配置不切分 CJK，因此中文长串在 `tsvector` 里是**整段 token**，`@@` 几乎不命中；兜底只剩 `ILIKE '%query%'`（要求整串连续出现）与 `similarity() > 0.05`。实测 `贵州`/`黔岭`/`约定书` 均 0 命中。
- **影响**：中文语境下知识库的可检索性远低于英文字面预期。
- **修法**：引入中文分词（`zhparser` / `pg_jieba` 扩展，或在入库时把 `search_vector` 用分词结果构造），并把 `ILIKE` 兜底改为**分词后逐词 OR**。

### P7（低）冲突与仲裁链路 0 数据

- **证据**：`knowledge.conflict_cases` 0 / `conflict_items` 0 / `arbitration_decisions` 0（主库）。
- **影响**：Phase 6 的"冲突收件箱 + 显式仲裁"从未被真实触发（测试库分别有 60/60/40 行，说明代码路径被测过）。
- **判定**：属"已建成未使用"，与 §6.4 同类。不需要修，但**不要**在汇报里当成"已在运行的能力"。

### P8（低）富媒体解析默认未配置，PDF/图片永远停在 pending

- **证据**：`packages/knowledge/local_extractors.py:19` `MINERU_EXECUTABLE = os.getenv("MINERU_EXECUTABLE", "")`（**刻意无默认值**，注释说明旧默认是作者本机路径）；`.env` 未设置 → `mineru_available()` 为 `False` → `local.mineru` 状态 `waiting_for_local_runtime`。主库 `knowledge.rich_media_jobs` **0 行**（测试库 80 行）。
- **判定**：设计上是"未配置就诚实等待"，不是缺陷；但**用户上传 PDF 后会一直停在待处理**，需要文档化这一预期。
