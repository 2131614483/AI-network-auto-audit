# AI 自动理解并串联「插件 · 技能 · MCP 服务」方案

日期：2026-09-26 · 方向：让 AI 把三类能力**统一理解**并串成能跑通的工作流，且方便迁移

---

## 一、先说三个既有事实（决定了方案不该长什么样）

调研结果如下，**它们把方案的空间压得很小**：

1. **统一插件协议里已经有 `mcp`**：
   `contracts/jsonschema/unified-plugin-protocol.schema.json` 的
   `compatibility.adapters` 枚举 = `["python","node","http","mcp","container","wasm","desktop"]`。
   协议**早已声明**支持 MCP 适配器 —— 缺的是实现，不是概念。
2. **"技能"在本仓库有两个含义**，不能混为一谈：
   * 界面上「技能 123」指 **`plugin.protocol.json`**（与插件同一批文件、另一个视图）；
   * `skills/audit-report-builder/SKILL.md` 是 **Claude Code 技能**（面向 AI 的提示词/流程说明），
     全仓只有这 1 个，且**不在能力目录里**。
3. **插件协议本身就是"AI 可理解的描述"**：`plugin.protocol.json` 带
   `name / description / kind / domains / lifecycle / compatibility / capabilities / governance / resources / provenance`。
   AI 组网现在只读 `capability + 端口`，**这些描述字段没进提示词** —— 所以模型"看不懂"插件想干什么。

> **结论：不新增声明层。** 插件协议就是统一描述面；MCP 与技能都应当是**新的 adapter / 新的 kind**，
> 不是新的品类。再建一套"能力登记"就会有两个事实源，而事实源重复是本项目已经吃过亏的事。

---

## 二、要做的三件事（互相独立，可分别验收）

### 2.1 `mcp` 适配器：把 MCP server 变成目录里的插件

MCP server 暴露的是 **tools**（名字 + 输入 schema + 描述），而插件协议要的是
**capability + 输入/输出端口 + 契约**。所以适配器的职责是**翻译**：

| MCP 侧 | 插件协议侧 |
|---|---|
| `tools/list` 的名字 | `capability` id（如 `mcp.<server>.<tool>`） |
| tool 的描述 | `description`（喂给模型的"理解面"） |
| tool 的 inputSchema | 输入端口 + `schema_ref`（**指向落盘的 jsonschema**，不是内联） |
| tool 的返回 | 输出端口（无声明时按 `artifact-ref` 兜底，并**显式标注为推断**） |

**守住的边界**（与既有设计一致）：
* MCP 是**外部进程** → 必须过策略网关，`risk_class` 按 tool 的副作用声明，**默认 read_only**；
* 端口契约必须落成 `contracts/jsonschema/` 里的真 schema —— **不许内联**，否则 `schema_sha256` 无从校验；
* 推断出来的输出端口要**标出来是推断的**，不能与声明的事实混在一起。

### 2.2 技能（SKILL.md 类）：把"提示词 + 工具"变成有输入输出的节点

`SKILL.md` 是给人/AI 读的流程说明，**没有输入输出契约**，所以它现在无法进 `compile_plan`
（编译器要求端口契约逐字段一致）。要串联它，需要一层**声明式包装**：

```
skills/<name>/skill.manifest.json   ← 新增：声明 inputs / outputs / 依赖的 tool 集合
skills/<name>/SKILL.md              ← 不变：AI 读的流程说明
```

* 包装后，技能在目录里表现为 `kind=agent`（枚举里已有）的一个插件；
* 执行时由既有 isolated 运行时拉起（adapter `python`/`desktop`），**提示词仍来自 SKILL.md**；
* **明确不做**：不让技能绕过策略网关，也不让它直接调 MCP tool —— 它要用的 tool 必须
  作为它的输入端口显式声明出来（这样才可审、可复算）。

### 2.3 理解面：让模型真的"看得懂"（这是本方案的核心收益）

现在 `recall_snapshot` 只渲染 `capability (plugin=… inputs=… outputs=…)`，模型看不到
`description / kind / domains / lifecycle`。实测后果：**5 次自由组网，模型每次只能组出同一条两节点链**。

要做的：

1. `recall_snapshot` 增加 `kind` 与 `description`（截断到固定长度，保持提示词可控）；
2. 端口清单带上**上游/下游提示**（谁产它、谁要它），让模型能顺着契约找路径 ——
   这正是"补链方案"（`docs/插件目录补链方案-20260926.md`）里那条最长链从 2 提到 4 的前置条件；
3. 提示词里显式给出**可用 adapter 种类**（含 `mcp`），模型才知道目录里有 MCP 能力可选。

**收益可验收**：同一目标下，模型能组出的**最长链长度**与**可选节点种类**应显著上升
（现在恒为 2 节点 / 只有 2 种 capability 被选中）。

## 三、迁移性（你说的"方便迁移"）

这一条最容易做砸，因为 MCP 与技能都自带运行时依赖：

| 依赖 | 迁移做法 |
|---|---|
| MCP server | **只能检测+指引，不随包**（与 PostgreSQL 同类）。包内放 `mcp.servers.json` 声明"需要哪些 server、怎么起、探活命令"，解包后 `bootstrap` 检测并如实报告缺哪个 |
| 技能运行时 | 随包（纯 Python/Node 依赖走既有 wheelhouse / node_modules） |
| 声明与契约 | 本来就随包（`contracts/`、`plugins/`、`skills/`） |

**续用既有方案**：`docs/独立化可迁移改造方案-20260912.md` 的
`bootstrap.ps1` + `package-offline.ps1` 已经是"检测不了的给指引、能带的随包"这一形态，
本方案只**追加一节 MCP 检测**，不新建打包机制。

**验收**：在干净环境解包后，`bootstrap` 能明确报告"MCP server X 缺失、技能 Y 可用、
插件 Z 可用"，而不是启动到一半才发现在某个节点上跑不通。

## 四、阶段与验收

| 阶段 | 内容 | 验收 |
|---|---|---|
| A | 理解面（2.3） | 同一目标下模型组出的最长链 **2 → ≥3**；提示词长度增量可测 |
| B | 技能包装（2.2） | 至少 1 个技能能在 `compile_plan` 里作为节点参与组网并真实执行 |
| C | MCP 适配器（2.1） | 至少 1 个真实 MCP server 的工具被登记为 capability、经策略网关执行成功 |
| D | 迁移（三） | 干净环境解包后能如实报告三类能力的可用性 |

**建议顺序 A → B → C → D**：A 是所有收益的前提（模型看不懂就无法串联），B 比 C 风险低
（技能是本地文件，MCP 要引外部进程）。

---

## 五、明确不做

* 不新增"能力登记"类声明层 —— 插件协议就是统一描述面；
* 不让技能/MCP 绕过策略网关或端口契约；
* 不把 MCP server 打进离线包（与 PostgreSQL 同类，只能检测+指引）；
* 不为"能串起来"而给技能编造输入输出 —— 编出来的契约会让整条链的 sha256 复算失去意义。
