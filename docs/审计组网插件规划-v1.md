# 审计组网插件规划 v1

状态：**设计完成，尚未创建或注册本规划中的新运行插件。**  
依据：[总体设计](../超级审计与量化智能中枢总体设计.md)、[模块自治版总体设计](../超级审计与量化智能中枢总体设计-模块自治版.md)、[插件拓扑设计](plugin-topology-orchestration.md)、[统一插件协议](plugin-protocol.md)，以及对 `Audit-Networking` 78 个模块规划的只读审阅记录。

## 1. 决策：不是把 78 个参考模块直接“装成插件”

参考项目的 78 个模块、45 条内部依赖和 39 个外部入口是**蓝图来源**，不是本项目的已验证实现。直接批量导入会把未验证的数据契约、权限、循环、外部连接和成熟度声明一并带入。

本项目采用以下收敛方式：

```text
78 个参考模块 / 现有本地能力
  → 多轴 L0 集群中的 PluginBlueprint（规划槽位）
  → 选出少量高价值、低副作用、可用本地样本验证的 UPP 协议包
  → 一个一个完成隔离运行时、黄金样本和策略白名单
  → 仅由已批准 Workflow 调度；计划、执行、证据相互独立
```

当前的 16 个集群与 10 个 `plan_only` 蓝图保持为控制面目录。新增插件首先补充蓝图/协议，**不因目录里有 Python 文件、模型或参考代码就被视为安装完成**。

## 2. 组网边界：哪些必须是平台服务，不写成插件

下列能力是系统的信任根或跨域协调器，必须由各自的模块服务拥有，不能让普通插件替代或绕过：

| 平台能力 | 所有者 | 为什么不能普通插件化 |
| --- | --- | --- |
| 身份、租户、RLS 与 Policy Gateway | Risk & Policy | 插件不能给自己审批、扩大数据域或修改黑名单。 |
| ArtifactRef、证据链、ChangeSet/Release/回滚 | 各领域模块 + Evidence | 插件只能提交不可变引用或候选，不能直接改写领域真相。 |
| Plugin Topology、Capability Resolver、目录发布锁 | Plugin Topology | 决定“可选什么”，不能由某个候选实现篡改。 |
| Workflow 编译、任务租约、重试、Outbox/Inbox | Agent Orchestrator | 保证 DAG、幂等、补偿与恢复；插件只处理一个受限能力。 |
| 插件 Registry、签名/哈希校验、隔离运行器、健康注册 | Plugin Runtime | 不能让插件自己登记自己、上报可信或决定执行模式。 |
| GUI Shell、审批中心、风险中心、审计日志与 Kill Switch | Desktop Shell / Policy | 插件只能追加到声明插槽，不能覆盖系统治理页面。 |

因此，“插件组网”是：**Agent/Workflow 用已锁定的能力契约连接确定性插件；领域服务负责持久化与治理；Hub 只汇总公共事件和只读投影。**

## 3. 四条首要组网链路

### 3.1 知识—图谱—审计证据链

```text
artifact_ref
  → knowledge.document-ingestion
  → knowledge.entity-relation-candidate
  → graph candidate set（影子 ChangeSet，由 Graph 服务验证/发布）
  → audit.evidence-lineage
  → audit.ledger-quality / audit.journal-anomaly
  → anomaly candidate（由 Audit 服务关联证据）
  → 独立 Reviewer / 人工确认 Finding
```

图谱抽取插件只输出候选实体、关系、来源位置和置信度；它不能直接写活图。审计检测插件只输出可解释候选，不能自行确认 Finding。

### 3.2 量化研究与风险链（独立信息墙）

```text
market_snapshot_ref
  → quant.snapshot-guard
  → quant.factor-compute
  → quant.simulated-backtest
  → quant.experiment-evaluator
  → RiskSignal / champion-challenger proposal
  → 模拟盘或人工研究结论
```

量化链不读取审计客户机密正文；仅可消费经过发布、脱敏和分级允许的公共引用。该链不包含下单能力。

### 3.3 AIOps 观测—归因—验证链

```text
telemetry / alert event ref
  → aiops.alert-correlation
  → aiops.alert-triage
  → aiops.rca-ranker
  → aiops.playbook-proposer
  → Policy + ChangeRequest + 人工审批
  → [未来、独立] 受签名 Executor canary
  → aiops.recovery-verifier
  → postmortem proposal
```

在当前阶段，链路严格停在提案、模拟执行和独立验证；没有生产命令、任意 Shell 或自动修复插件。

### 3.4 审计工作底稿与报告链

```text
EvidenceRef + anomaly candidate
  → audit.investigation-plan
  → audit.finding-draft
  → 独立 QA / 人工复核
  → Audit 服务确认 Finding
  → audit.workpaper-export / audit.report-draft（后续）
```

报告草稿与导出是 Sink 插件，必须保留来源引用、模板版本和生成记录，且不能替代审计发现的人工确认。

## 4. 插件组合与开发优先级

### R0：已有包，不重写

| ID | 状态 | 角色 | 当前边界 |
| --- | --- | --- | --- |
| `knowledge.document-ingestion` | `verified` | 本地文档只读摄入 | 唯一已登记隔离运行时；只能读取声明目录中的 Markdown/TXT/JSON/CSV。 |
| `audit.evidence-lineage` | `contract_only` | 证据血缘查询 | 先保持只读，不能写 Finding。 |
| `quant.simulated-backtest` | `contract_only` | 点时模拟回测 | 永远不含真实交易。 |
| `aiops.alert-triage` | `contract_only` | 告警人工复核提案 | 不连接基础设施，也不执行 Playbook。 |

R0 的三个协议包应先各自补齐正反例、黄金样本与独立 Manifest，再考虑提升为 `verified`；不得同时升级。

### R1：首批应该实现的只读分析插件

R1 选择“输入为已发布引用、输出为候选或分析结果、无外网与无领域直写”的插件。每个插件单独完成从协议到隔离运行时的完整验收后才进入下一个。

| 顺序 | 插件 ID / capability | 输入 → 输出 | 副作用与数据域 | 为什么优先 |
| ---: | --- | --- | --- | --- |
| 1 | `audit.ledger-quality` / `audit.ledger.validate` | `ledger-artifact-ref@1` → `audit-quality-candidates@1` | `read_only`；`audit_confidential` | 可复用现有 CSV 总账质量链，确定性强，能作为第 2 个真实插件样例。 |
| 2 | `audit.journal-anomaly` / `audit.journal.detect` | 已校验总账快照 → `anomaly-candidates@1` | `read_only`；`audit_confidential` | 输出候选和规则命中，不生成 Finding，审计价值高。 |
| 3 | `knowledge.entity-relation-candidate` / `knowledge.extract.relations` | `document-content@1` → `graph-candidate-set@1` | `read_only`；`internal` | 复用当前抽取/冲突机制，但只交给 Graph 服务的影子 ChangeSet。 |
| 4 | `quant.snapshot-guard` / `quant.dataset.validate` | `market-snapshot-ref@1` → `dataset-validation@1` | `read_only`；`restricted` | 把新鲜度、复权、交易日和点时门变为独立可复用闸门。 |
| 5 | `quant.factor-compute` / `quant.factor.compute` | 已验证市场快照 → `factor-artifact-ref@1` | `read_only`；`restricted` | 因子计算与回测解耦，便于复现、缓存与 champion/challenger 对比。 |
| 6 | `aiops.alert-correlation` / `aiops.alert.correlate` | `alert-event@1` → `incident-candidate-set@1` | `read_only`；`internal` | 先解决告警风暴、去重与聚合；不创建 Incident。 |
| 7 | `aiops.rca-ranker` / `aiops.rca.rank` | 事故/拓扑/变更引用 → `rca-candidates@1` | `read_only`；`internal` | 把“根因候选”与修复规划分离，方便独立评价 Top-K 命中。 |

**R1 的共同规则：**插件不得插入 `graph.nodes`、`audit.findings`、`quant.backtests` 或 `aiops.executions`；每个结果由所属领域服务在策略裁决后保存为 Artifact、Candidate 或只读投影。

### R2：提案型插件，只能写影子对象

| 插件 ID / capability | 结果 | 允许写入的位置 | 明确禁止 |
| --- | --- | --- | --- |
| `knowledge.graph-proposal-builder` / `graph.proposal.build` | 包含来源定位的图谱 ChangeSet 草稿 | Knowledge/Graph 的影子 ChangeSet | 活图节点/边直写、自动发布。 |
| `audit.investigation-plan` / `audit.investigation.plan` | 调查步骤、待补证据和反证清单 | 审计计划草稿 | 确认 Finding、修改证据。 |
| `audit.finding-draft` / `audit.finding.draft` | 带 Claim/EvidenceRef 的发现草稿 | 审计候选收件箱 | 代替独立 QA 或人工确认。 |
| `quant.experiment-evaluator` / `quant.experiment.evaluate` | 稳健性、漂移和晋级建议 | 研究提案 | 更新生产模型、生成订单。 |
| `aiops.playbook-proposer` / `aiops.remediation.propose` | Playbook 选择、前置条件、canary、回滚建议 | AIOps 修复提案 | 生成自由 Shell、创建 ChangeRequest 或执行变更。 |
| `aiops.recovery-verifier` / `aiops.recovery.verify` | 基线对比、SLO/业务探针验证结果 | 不可变核验账本 | 自己执行修复、解除熔断。 |

R2 的调用需要 ChangeSet 或领域提案 API；即使能力本身是确定性的，任何 `write_data` 都必须带证据、租户、Trace、幂等键和最小化策略规则。

### R3：受审批的输出插件

这些插件只在 R1/R2 已有稳定证据、版本与回滚链后开发：

- `audit.workpaper-export`：将已确认 Finding 导出为可追溯底稿工件；不覆盖历史报告。
- `audit.report-draft`：基于已确认 Finding 生成报告草稿；报告签发仍由人完成。
- `aiops.ticket-draft`：创建外部工单的草稿/预览；实际发送需要目标系统白名单和人工审批。
- `knowledge.retention-recommendation`：只提出归档/回收建议，不能删除证据。

### R4：暂不开发或永久硬限制

| 能力 | 决策 |
| --- | --- |
| 通用 Shell / “任意命令执行”插件 | 永不作为通用插件提供。 |
| 通用数据库直连或全库 SQL 插件 | 不提供；每个数据源用专用、只读、契约化 Connector。 |
| 图谱活数据直写插件 | 不提供；只能经候选 → ChangeSet → 发布。 |
| 券商下单、真实交易、凭证持有插件 | 当前不开发；未来只能为独立 OMS/Risk Engine 的受签名订单提案适配器。 |
| 生产 AIOps 执行器 | 当前不开发；需要独立生产环境、签名 Playbook、Preflight、Canary、回滚、双人审批和故障注入验收。 |
| 允许插件自注册、自审批、自更新 | 永不允许。 |

## 5. 连接器写法：一源一插件，不做“万能连接器”

外部数据源应以固定边界的 Source 插件接入，例如 `source.local-folder`、`source.audit-ledger-csv`、`source.market-snapshot-file`。每个连接器必须：

1. 只声明一个来源类型、固定可读根目录或固定 host:port 白名单；
2. 输出不可变 `ArtifactRef` / `DatasetRef` 与 SHA256、时间、分级、来源版本；
3. 把原始数据和凭据留在来源所有者，不在事件、图谱或 UPP 内复制；
4. 读取失败时产出结构化失败结果，不能用旧快照冒充新数据；
5. 进入外网、ERP、Git、邮件或券商前，单独完成安全审查、密钥引用、网络白名单与隔离验收。

这能让本地文件、Obsidian、MinerU、已有量化数据和后续企业系统都以相同 ArtifactRef 组网，而不把路径、口令或数据库表耦合到 Agent 提示词中。

## 6. 每个插件应如何编写

### 6.1 先写契约，后写代码

每个新插件按以下顺序交付：

```text
1. L1/L2 Blueprint：能力槽位、集群、输入/输出、风险和来源
2. plugin.protocol.json：UPP 身份、能力、幂等、治理、资源、可观测性、声明式 GUI
3. 正向/反向 JSON Schema 契约样本
4. 黄金样本与失败样本（越界路径、错误 SHA、版本不兼容、重复请求、超时）
5. 隔离运行时实现：只接收固定 JSON 信封，不解析任意命令
6. plugin.manifest.json：固定入口、权限、资源、测试位置
7. plugin.runtime-binding.json：固定 UPP/Manifest/代码 SHA256 与 isolated_subprocess
8. 精确 Policy 发布、领域服务 Adapter、最小 GUI 贡献
9. 单插件 E2E 与跨模块 Saga E2E；记录状态、限制和回滚方式
```

插件目录标准见 [插件开发与接入标准](插件开发与接入标准-UPP-v1.0.md)。建议目录：

```text
plugins/builtin/<plugin-id>/
  plugin.protocol.json
  plugin.manifest.json                 # 通过隔离验证后才增加
  plugin.runtime-binding.json          # 通过哈希绑定后才增加
  ui.contribution.json                 # 可选，且只能声明式
  README.md
plugins/builtin/<python_package>/runtime.py
tests/contract/test_<plugin>.py
tests/integration/test_<plugin>_runtime.py
tests/integration/test_<plugin>_e2e.py
```

### 6.2 运行时与数据规则

- 一个插件以一个明确的主能力为中心；不要把“采集 + OCR + 图谱写入 + 报告发送”塞进一个大插件。
- 输入和输出通过版本化 Ref 传递；运行器校验 `tenant_id`、`trace_id`、文件大小、SHA256、分级、根目录与契约版本。
- 插件进程默认无网络、无数据库直连、无写入领域表；结果经受控 JSON 信封返回给模块服务。
- 长任务使用检查点和可重试的 ArtifactRef；幂等键必须绑定不可变输入与版本，不以时间戳作为幂等依据。
- 分析模型的 Prompt、模型版本、参数、输入/输出哈希进入 provenance；模型输出一律是候选，不是事实或最终发现。

### 6.3 GUI 与策略规则

- GUI 只用 `UIContribution` 的导航、卡片、表格、图表、图谱、表单和动作声明；不注入任意 JavaScript。
- 插件按钮只提交 `capability + typed arguments`，由 Electron 主进程、控制平面和 Policy Gateway 逐层检查。
- `read_only` 可以采用精确白名单自动放行并写审计记录；提案型写入进入审批或 ChangeSet；外部动作、金融动作和不可逆操作不得泛化 AUTO。
- 禁用插件应撤销其导航、路由、缓存、订阅和临时授权，但历史 Artifact、策略裁决和证据仍保留。

## 7. 组网时的路由与失败策略

1. 规划 Agent 先在 L0 按业务域 + 治理区收敛，再交叉能力族 + 运行池；禁止全目录遍历。
2. Capability Resolver 只匹配相同/兼容的契约 ID、主版本、格式、数据分级和副作用；缺能力就输出 `unresolved_capabilities`，不做名称猜测。
3. `PluginRoutingPlan` 必须锁定拓扑发布版本、插件/Manifest 版本、健康快照和 planner 版本，且保持 DAG；反馈回路以新的运行 epoch 表达。
4. 主路径外最多保留 8 条兼容替代路径；替代插件不能悄悄提高数据权限或副作用等级。
5. 任何插件失败只影响其所在 TaskRun：保留输入、输出、错误和 Trace；由 Workflow 按显式 fallback / retry / 人工升级处理，不能吞掉错误或重跑导致重复副作用。

## 8. 推荐的实际开发顺序

### 第一个新增真实插件：`audit.ledger-quality`

选择它作为 `knowledge.document-ingestion` 之后的第二个验证样例：有现成审计域数据和质量检查路径，不需要外网，输出可解释，且不写 Finding。

其最小契约应为：

| 项目 | 设计 |
| --- | --- |
| UPP ID / 版本 | `audit.ledger-quality@0.1.0` |
| Capability | `audit.ledger.validate` |
| 输入 | `ledger-artifact-ref@1`，包含 SHA256、期间、分类、列映射版本 |
| 输出 | `audit-quality-candidates@1`，包含规则 ID、行定位、严重度、证据 Ref、原因码 |
| 副作用 | `read_only`；结果由 Audit 服务保存为候选，不由插件写表 |
| 幂等 | `ledger_sha256 + schema_mapping_version + rule_pack_sha256` |
| 权限 | 仅读取 `audit.ledger.snapshot`；网络 `none`；审计保密 |
| 验收 | 平衡/重复/期间/字段映射正反样本、路径越界、篡改 SHA、重复调用、资源超限、策略拒绝、隔离进程测试 |

完成并验收后，再顺序开发 `audit.journal-anomaly`、`knowledge.entity-relation-candidate`、`quant.snapshot-guard` 和 `aiops.alert-correlation`。每次只提升一个插件为 `verified`，避免同时引入多个未定位的组网故障。

## 9. 规划完成的验收标准

- [ ] 每个候选插件都有 L0/L1/L2 归属、输入输出契约、数据分级、风险和来源 Ref。
- [ ] 任何新插件都不兼任 Policy、Registry、Workflow、ChangeSet/Release 或领域权威存储。
- [ ] R1 全部是无外网、无领域直写、可用本地样本复现的分析插件。
- [ ] R2 全部只提交候选/影子对象；确认、发布和执行由不同身份完成。
- [ ] 连接器一源一插件，无通用 URL、任意 SQL 或任意 Shell 能力。
- [ ] 每个 `verified` 插件具备 Schema、黄金样本、负向安全、幂等、资源、隔离和策略 E2E 证据。
- [ ] 路由计划为可复现、预算受限的 DAG；跨图只传 `artifact_ref`、`capability_contract`、`released_graph_ref`、`health_signal`。
- [ ] GUI 不存在绕过 Policy Gateway 的执行入口；真实交易和生产 AIOps 执行仍在硬限制之内。
