## 3. 数据源：三层，互不相同

这是理解该 demo 最容易混淆的一点 —— **"数据源"其实是三层，用途完全不同**。

### 3.1 第一层：业务输入数据（Step 0 现场合成）

- **不是**读外部文件、也**不是**读数据库；由脚本内 `_ledger_rows()` **硬编码合成** 9 行日记账 CSV。
- 落盘：`.data/demo/staging/inputs/ledger-a.csv`，UTF-8 **with BOM**（`utf-8-sig`）。
- 独立复算（本次）：

| 项 | 声明值 | 本次复算 | 结论 |
| --- | --- | --- | --- |
| sha256 | `1f8e4bfd5e4627d48522e1955b070dabe484e085a0513f86097572f4d3c61be4` | 完全相同 | ✅ |
| size_bytes | 548 | 548 | ✅ |
| row_count | 9 | 9 | ✅ |
| period | 2026-01（脚本常量 `_PERIOD`） | — | ✅ |

- 数据中**故意植入 6 项质量瑕疵**：重复行（E1002 第 3 行）、不平衡凭证（E1003，借 300 / 贷 200）、缺金额（E1004 贷方为空）、超期（E1005 日期 2026-02）、大额（E1006 借贷各 1,500,000 ≥ 阈值 1,000,000，触发 2 次）。

### 3.2 第二层：能力目录（AI 可调用的能力白名单）

- 来源函数：`capability_catalog_from_db(TEST_DB, tenant_id)` = **DB `topology.plugin_blueprints`（status ∈ active/planned）∩ 运行时已验证插件 `RUNTIME_CAPABILITIES`**，DB 优先、运行时兜底。
- 实测规模：DB 侧 **739 行**（全部 status = `planned`），去重后 + 2 个运行时能力 = 目录 **272 项**。
- 其中**绝大多数是 `audit.it-*` 集成测试残留**（如 `audit.it-0439bdc0.produce`），真实业务能力被噪声淹没。
- 脚本因此做了一层**业务域过滤**（`audit.*` / `quant.*` 且非 `audit.it-*`），收敛为 **4 项**交给 AI：

```
audit.finding.draft, audit.ledger.validate, quant.experiment.evaluate, quant.research-note.draft
```

> ⚠️ **口径更正**：`组网业务实战报告-20260909.md` 称"`plugin_blueprints` 命中 **0 行**（测试库该表 status 不含本业务域蓝图）"。本次验证证明这是**假象** —— 该诊断查询（`scripts/demo-grouping-business.py:130-137`）在**同一个连接上执行、但没有先 `set_config('app.tenant_id')`**，被行级安全（RLS）过滤成 0。同一查询在设置租户上下文后返回 **739 行**。即：数据一直存在，是诊断代码缺租户上下文。

### 3.3 第三层：AI 模型通道（组网大脑）

- 通道：OpenAI 兼容 HTTP `POST {base_url}/chat/completions`，`base_url = https://api.commandcode.ai/provider/v1`（客户端自动拼接，避免双拼 404）。
- 模型：`meituan/LongCat-2.0:free`；`temperature=0`、`response_format={"type":"json_object"}`、非流式。
- 鉴权：**只从环境变量** `OPENAI_COMPAT_API_KEY` 读取，缺失即抛错（fail-closed），源码零硬编码。
- 两个必须的实现细节（均为踩坑沉淀）：
  - **必须带浏览器 UA** —— 该端点对 Python-urllib 默认 UA 返回 Cloudflare 1010 拦截。
  - 脚本内置 **3 次有界重试**（退避 `2s × attempt`），云端抖动不直接判死。

### 3.4 授权数据边界

- 脚本向规划器声明 `authorized_sources = {("ledger-a", "ledger")}` —— AI **只能**引用这一个数据源。
- 该边界在 `draft.py` 的闸门中强制：任何不在此集合内的 `seed_inputs` 直接判 `data_boundary_denied` 拒绝，**且该检查在节点存在性检查之前**（最强的安全顺序）。

## 4. 全链路流程：8 步逐步拆解

| Step | 名称 | 输入 | 处理 | 产物 / 证据 |
| --- | --- | --- | --- | --- |
| 0 | 模拟数据 | 无（脚本常量） | `_ledger_rows()` 合成 9 行 CSV | `staging/inputs/ledger-a.csv` + sha256 |
| 1 | 能力目录查询 | 测试库 + 运行时注册表 | DB ∩ 运行时；脚本层业务域过滤 | 272 项 → 4 项可见能力 |
| 2 | 云端 AI 组网 | goal + 4 项能力 + 授权源 | `AiPlanner.plan`：召回 → 模型出草稿 → 闸门校验 → 编译 → 不合格则带错误回灌修订（上限 3 轮） | `ExecutionPlan` 或 gap_report |
| 3 | 策略裁决与落库 | ExecutionPlan + seed | `TopologyService.start_plan_run`：Policy 裁决 → 幂等键 → 节点/边短事务 → outbox | `run_id` / `trace_id` / `execution_hash` |
| 4 | 真实插件执行 | 编译后的 DAG | `PortBoundExecutor` 按 `(节点实例, 输出端口)` 逐边取产物，子进程隔离执行 | 每个 attempt 的 `input_bindings` / `output_refs` + sha256 |
| 5 | 画布投影 | run_id | `service.canvas_projection` 统一事实源 | nodes / edges 投影（UI 与证据共用） |
| 6 | 证据导出 | 投影 + 磁盘产物 | 打包 zip + sha256 manifest，随后离线复验 | `evidence/{run_id}.zip` |
| 7 | 三层下钻 | 同一 trace_id | 数据层（DB）/ 日志层（spool）/ 代码层（adapter + 磁盘） | 三层均可互相追溯 |
| 8 | 业务结论 | 两个产物 JSON | 汇总质检 summary 与回测评估 | 最终业务结论 |

### Step 2 内部（AI 组网的真实机制）

```
能力召回（白名单 4 项）
   → 模型输出结构化 JSON 草稿（nodes / edges / budget / plan_key）
   → 闸门 validate_draft：封闭 schema + 能力白名单 + 端口契约逐字段一致 + 数据边界
   → 确定性编译器 compile_plan：无环 / 必填端口 / fan-in / 预算 / 适配器
   → 失败 → 把结构化错误回灌模型重出草稿（最多 3 轮）
   → 3 轮仍失败 → 输出 gap_report（诚实缺口报告，绝不伪装成功）
```

**关键设计属性**：模型**永远不能**自授权。它不能发明插件名（能力白名单）、不能发明端口（端口契约目录）、不能引用未授权数据（数据边界）、不能绕过编译器（`_MAX_REVISION_ROUNDS=3` 上限后只能给缺口报告）。

### Step 4 内部（真实执行，非模拟）

- 执行前每个节点由 `AttemptStore.begin_attempt` 开一条短事务记录。
- `PortBoundExecutor` 按 `outputs[(node_instance_id, output_port_id)]` 取上游产物 —— **不是**"拓扑序里的上一个节点"（这是 CW1 修复的旧缺陷）。
- 插件以 Python `-I` 子进程、最小环境变量、只读根白名单（`AUDIT_PLUGIN_READ_ROOTS`）运行。
- 质检插件在**读取时**复核产物 `size_bytes` 与 `sha256`，与引用不符即拒绝 —— 输入不可篡改。

## 7. 本次实跑暴露的缺陷（核心章节）

### D1 【P0】Demo 脚本只在"降级模板"路径下能跑完

**现象**：本次实机重跑，云端 AI **成功产出可通过编译的草稿**（`status=draft_ready`, `revisions=3`，节点为 `audit.ledger.validate` + `audit.finding.draft`），随后脚本在 Step 3 崩溃：

```
RuntimeError: producer artifact not ready for edge e1:
  ('ledger-validate-001', 'audit-quality-candidates')
```

**根因**：seed 绑定硬编码了模板的节点名。

- `scripts/demo-grouping-business.py:259` 写死 `seed_inputs={("ledger-a", "ledger"): seed}`
- 而 `PortBoundExecutor._bind_inputs`（`ports_executor.py:375-385`）用 `(node_instance_id, port_id)` 作键查种子
- AI 按**提示词明确要求**使用语义化命名（`planner.py:72`：`ledger-validate-001` 这类，且**禁止** `node1/consumer1` 占位名），于是键不匹配 → 种子注入失败 → 质检节点无输入而失败
- 模板路径下节点名恰好是 `ledger-a`，所以**只有降级路径能过**

**隔离变量对照实验**（本次新增，`scripts` 外临时脚本，只改节点名与种子键）：

| 组 | 计划节点名 | 种子绑定键 | 实测结果 |
| --- | --- | --- | --- |
| A | `ledger-a` / `consumer-x` | `("ledger-a","ledger")` | ✅ `status=succeeded`（两节点均 succeeded） |
| B | `ledger-validate-001` / `backtest-eval-001` | `("ledger-a","ledger")` | ❌ 复现崩溃：`producer artifact not ready for edge e1: ('ledger-validate-001','candidates')` |
| C | `ledger-validate-001` / `backtest-eval-001` | `("ledger-validate-001","ledger")` | ✅ `status=succeeded`（两节点均 succeeded） |

**结论**：**引擎（编译器 + 执行器）本身完全正确**，缺陷**只在 demo 脚本的种子绑定**。同时说明该 demo 的"AI 成功路径"**从未被真正验证过** —— 2026-09-09 那次走的是降级模板，掩盖了这个问题。

**修复建议**：不要硬编码节点名。应从编译后的计划里**推导**需要注入种子的 `(node_instance_id, port_id)`，或直接采用 `AiPlanner._auto_seed_inputs()`（`planner.py:106-142`）已经算好的自动绑定结果，并把它随 `ExecutionPlan` 一起传给 `start_plan_run`。

> 补充：`tests/integration/test_ai_direct_flow_execution.py:122,128` **已经**正确使用了 `("ledger-validate-001","ledger")` 的绑定方式 —— 也就是说引擎侧用例是覆盖到位且通过的，**漏的是 demo 脚本这一层没有集成测试**。

### D2 【P0】上游节点失败后，下游用未捕获异常中断整条运行，并留下悬挂状态

**现象**：D1 的失败并非"优雅失败"，而是抛出未捕获异常终止整个进程。

**证据链（DB 直查）**：

```
ledger-validate-001 | failed  | plugin_failed | RuntimeError: required input 'ledger' of node
                                                ledger-validate-001 has no bound producer artifact
finding-draft-001   | running | NULL          | finished_at = NULL   ← 永久悬挂
```

- 该 `trace_id` (`232afb49-…`) 在 `topology.execution_runs` 中**查询结果为 0 行** —— 运行级记录根本不存在。
- 测试库中当前共有 **5 条**滞留在 `running` 的 attempt（含本次 1 条），说明这不是偶发。

**根因**：

1. `ports_executor.py:271` 的 `bindings = self._bind_inputs(node, outputs)` 位于 **`try` 块之外**，而 `:284` 的 `except` 只包住 `_build_payload` + 插件调用。
2. `_bind_inputs` 在 `:366` 抛 `RuntimeError`（上游产物未就绪）→ **冒泡出 `_run_one`**，该节点的 attempt 永远不会写终态。
3. `service.py:1467` 的 `outcome = executor.execute()` **没有 try/except** → 异常继续冒泡出 `start_plan_run` → run 级记录从未提交。
4. 附带一个错误分类问题：上游节点真正的失败原因是"种子绑定缺失"（输入装配问题），却被记成 `error_kind = plugin_failed`（`:285` 只区分 `ValueError` 与其它），**把装配错误伪装成插件错误**，会误导排障。

**影响**：直接违背 AGENTS.md「每个读取必须携带租户和 Trace ID；每次写入都必须具备幂等键与可回溯的执行历史」以及设计文档 §7.2「异常路径必须有独立事务追加终态」。在 24×7 无人值守下，这会持续累积"僵尸 attempt"并制造不可解释的运行缺口。

**修复建议**：把 `_bind_inputs` 纳入 fail-closed 捕获范围；`start_plan_run` 包 try/except 并在异常路径用**独立新事务**写入 attempt 终态与 run 终态；细化 `error_kind`（区分 `input_binding_missing` / `plugin_failed` / `budget_exceeded`）。

### D3 【P0】AI 可控字符串路径穿越（`plan_key` / `node_instance_id`）

**现象**：AI 草稿中的 `plan_key` 与 `node_instance_id` 会直接拼进落盘路径，但**只做了"非空 + 唯一 + 前缀"校验，没有字符集校验**。

- 落盘点：`ports_executor.py:175`

```python
node_dir = self.staging_root / "chains" / self.plan.plan_key / instance_id
```

- 闸门对 `plan_key` 的唯一约束：`draft.py:196-197` 仅要求 `isinstance(str)` 且 `startswith("plan-")`。

**实测（本次构造并解析真实路径）**：

| 输入 | 编译结果 | 解析出的落盘路径 | 是否逃出 staging 根 |
| --- | --- | --- | --- |

| `node_instance_id = "../../../../escaped"` | 编译**通过** | `D:\pythonpro\audit_network\.data\escaped` | **是** |
| `node_instance_id = "n/../../../../escaped"` | 编译**通过** | `D:\pythonpro\audit_network\.data\demo\escaped` | **是** |

**旁证**：本次实跑真的在 `.data/demo/staging/chains/` 下留下了名为 **`plan-`** 的目录 —— 证明 `plan_key` 确实按模型原样输出充当了路径段（本次模型输出了退化值 `plan-`）。

**影响**：模型（或任何能影响草稿的输入，包括被投毒的文档资料）可以把产物写到 staging 根目录之外。这直接违背设计文档 §11「不给浏览器任意本地路径读取能力」、§6.2「无脚本、SQL、shell、任意 URL」，以及 AGENTS.md「不删除或覆盖用户文件」的意图。虽然写入内容受插件输出限制、并非任意内容写入，但**任意位置**写入 + 覆盖同名文件（`output-<port>-<sha>.json`）已足够构成风险。

**修复建议**：对 `plan_key` 与 `node_instance_id` 施加严格字符集白名单（如 `^[A-Za-z0-9._-]+$`、禁止 `..` 与路径分隔符），在 `validate_draft` 与 `compile_plan` 双向强制；落盘时用 `Path.resolve()` 复核 `is_relative_to(staging_root)`，不满足即拒绝。

### D8 【P1】测试库污染导致 fail-closed 用例假失败

**现象**：本子集唯一失败项 —— `test_api_planning_fail_closed_without_capability`。该用例把策略集 `local-plugin-topology-graph-plan` 置为 `inactive`，期望网关 fail-closed 返回 403/409，实测得到 **200**。

1. 该策略集**确实存在且被成功置为 inactive**（本次直查：`('local-plugin-topology-graph-plan','inactive')`）。
2. 但策略引擎是**跨策略集累加**的 —— `apps/api/main.py:2376-2391` 的 `_load_policy` 明确注释 "Policy sets are additive"，其 SQL 是 `WHERE tenant_id=%s AND status='active'`，即**合并该租户全部 active 策略集**。
3. 测试库里仍有**另外 7 个 active 策略集**声明允许 `topology.intent.plan`，全部是历史用例残留：

```
cw5-chat-20fb4b / cw5-chat-idem-879f77 / cw5-chat-mal-00043b / cw5-chat-out-e241d6
cw5-chat-rev-1b4c47 / cw5-chat-ss-7c0e80 / cw5-chat-ss-err-9627df
```

4. 只停用 1 个集合，其余 7 个仍授权 → 网关**按设计正确地放行** → 200。**产品行为没错，是测试的前置清理不完整。**

**测试库污染规模（本次实测）**：

| 表 | 行数 | 说明 |
| --- | --- | --- |

**影响**：任何在共享测试库上做的"全量绿灯"声明都**不可复现**；这类失败会随残留积累而随机出现（且方向是"该拒未拒"，正好掩盖真实的安全回归风险）。这与设计文档 §13「测试数据优先在 `audit_network_test` 合成并使用**每轮独立命名空间**…不能通过不断提高列表 limit 来掩盖历史测试数据污染」的要求相悖。

3. 为 `policy.policy_sets` / `plugin_blueprints` 增加测试库定期清理脚本（**需显式人工确认后执行**，不自动删）。
