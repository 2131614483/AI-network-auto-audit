# 项目说明 · 超级审计、量化与 AIOps 智能中枢

> 项目代号：`audit_network`
> 开发周期：2026-09-02 起持续迭代（截至 2026-09-11 已完成 Phase 0–9 + CW0–CW7 全部里程碑）
> 交付形态：本机私有化部署的「控制平面 + 桌面驾驶舱」，非 SaaS、非 Demo 动画
> 文档性质：项目对外说明，所有数字均来自仓库实测（代码/迁移/测试/数据库直查）

## 一、项目定位（一句话）

**不是"一个什么都能干的 AI Agent"，而是"一个可靠中枢 + 三个专业领域脑 + 一个确定性风控内核 + 一套可插拔的插件网络"。**

把审计、量化、智能运维三个专业领域的能力，统一收敛到一条**可授权、可追溯、可复算、可回滚**的执行链路里：AI 负责"提出方案"，确定性编译器与策略网关负责"审核方案"，隔离沙箱负责"执行方案"，证据链负责"证明结果"。

核心命题是解决 AI 落地审计/财务场景时最致命的三个问题：

| 痛点 | 传统做法的问题 | 本项目做法 |
|---|---|---|
| AI 会胡说 | 让模型直接给结论 | 模型只能**填槽位**，不能发明能力名、端口、数据源 |
| AI 会越权 | 靠 prompt 约束 | 策略平面独立于 LLM，`deny-first` + 未知能力直接拒绝 |
| 结果不可信 | 只输出一份报告 | 每个产物锁定 `sha256`，证据包可**离线独立复算** |

## 二、要解决的问题（业务背景）

审计与财务数字化中最难的不是"把数据算出来"，而是**让过程能被复核**：

- 审计准则要求证据链完整、可追溯、不可篡改 —— 而 LLM 的输出天然是黑箱；
- 财务数据涉及客户非公开信息 —— 必须做租户隔离与跨域信息防火墙；
- 审计动作（抽样、函证、定性、整改）有严格的权限层级 —— 不能让 AI 自己给自己授权；
- 结论要能"自证" —— 复核人必须能脱离原系统，独立重算出同样的结果。

这三个约束直接决定了本项目的技术路线：**确定性优先、AI 兜底、可验证收口**。

## 三、总体架构

### 3.1 四类平面必须分开

这是整个项目最重要的一条架构决定：

1. **控制平面** —— 决定做什么、谁做、何时做（不碰大数据）
2. **数据平面** —— 插件/Agent 读数据、计算、产出工件
3. **策略平面** —— 决定某动作能否执行，**独立于 LLM 的意愿**
4. **观测平面** —— 记录发生了什么、花了多少、如何回放

只要把"策略"从"执行"里切出来，AI 的权限问题就从一个"提示词工程问题"变成一个"可测试的软件问题"。

### 3.2 三脑一核

```
认知控制平面（目标拆解 / 工作流编译 / 持久调度 / 共享黑板）
         │
         ▼
   策略执行点（Policy Enforcement Point）
   白名单 · 黑名单 · 权限 · 路径 · 数据分类 · 副作用 · 风险预算
         │
   ┌─────┼──────────┬──────────┐
   ▼     ▼          ▼          ▼
审计脑  量化脑     AIOps脑    平台治理脑
   └─────┴──────────┴──────────┘
         ▼
  知识 · 证据 · 信念层（六图分治：claim–evidence 模型）
         ▼
PostgreSQL 16 + pgvector + 内容寻址工件存储 / 不可变动作与审批账本
```

**信息防火墙**（对应券商/投行语境下的「信息隔离墙」Information Barrier）：审计客户的非公开信息，不得进入交易信号、回测样本或下单链路；跨域只允许传递经脱敏、授权、标记用途的数据产品。这条边界在代码里是硬约束，不是文档口号。

## 五、核心模块

### 5.1 策略平面：让"能不能干"变成可测试的问题

**能力命名规范** `<domain>.<object>.<verb>`，例如 `topology.chain.approve`、`knowledge.embedding.write`。

**风险分档**：`read_only / low / medium / high / critical` → 分值 `5 / 20 / 50 / 75 / 100`。

**决策顺序（deny-first，短路求值）**：

```
deny / freeze 规则（永胜）
  → 显式 deny 通配
  → require_approval
  → allow
  → AUTO 策略仅放行 low / read_only
未知 CAP 或未知风险等级 → 直接 DENY（critical, 100）
```

**关键工程细节**：

- `require_policy` 在 API 层被调用 **105 次**，默认参数就是 `risk_class="high"`、`side_effects="write_data"` —— **默认从严**，想放行必须显式声明。
- 非 `ALLOW` 时：`REQUIRE_APPROVAL` → HTTP 409，其余 → HTTP 403。**fail-closed**：拿不到裁决就不执行。
- 账本表 `policy.tool_calls` / `policy.decisions` **只授予 INSERT，无 UPDATE / DELETE 权限** —— 数据库层面保证审计轨迹不可篡改。
- 幂等键 `Idempotency-Key` 与策略决策绑定；重放时参数不一致直接 409，防止"同一张单子被改着重复提交"。

### 5.2 AI 组网流水线：六道闸门，模型永远不能自授权

这是项目最有价值的一段设计。用户输入一句自然语言目标，系统要把它变成一张**真正能跑的执行 DAG**：

```
① 能力召回        只从 DB 蓝图 ∩ 运行时已验证能力里取白名单
                  ↓
② 模型出草稿      LLM 输出结构化 JSON（nodes / edges / budget / plan_key）
                  ↓
③ 草稿闸门        封闭 schema（禁止多余字段）
  validate_draft  能力白名单（不得发明插件）
                  端口契约逐字段一致（不得发明端口）
                  数据边界（不得引用未授权数据源）★ 该检查在节点存在性检查之前
                  ↓
④ 确定性编译器    无环 / 必填端口 / fan-in 扇入 / 预算 / 适配器
  compile_plan    产出 ExecutionPlan + execution_hash
                  ↓
⑤ 失败回灌        把结构化错误喂回模型重出草稿，上限 3 轮
                  ↓
⑥ 诚实收口        3 轮仍不合格 → 输出 gap_report（缺口报告），绝不伪装成功
```

**为什么值得讲**：模型在整个链路里只是一个"填槽位的"，它不能发明插件名、不能发明端口、不能引用未授权的数据源、不能绕过编译器。**把 LLM 的不可控性关进了一个可测试的盒子里。**

### 5.3 插件体系：UPP v1.0 统一插件协议

- **契约先行**：`contracts/jsonschema/` 下 **86 份** Draft 2020-12 Schema，`unified-plugin-protocol.schema.json` 定义 **UPP v1.0**，强制顶层 14 个字段，`additionalProperties: false` —— 明文**禁止** entrypoint、命令行、URL、密钥出现在协议包里。
- **四层对象分离**：协议包 / Manifest / 蓝图 / 运行时绑定必须分开，能力声明必须**三方一致**（protocol、manifest、runtime-binding），且比对三方 `sha256`。
- **幂等依据强制声明**：每个能力必须声明自己凭什么幂等（不可变工件 SHA256 / 策略哈希 / 行情快照哈希）。
- **副作用只有 5 档**：`none / read_only / write_data / external_action / financial_execution`。
- **插件规模**：审计业务网络 **100 个已验收插件**，按三层组织 ——
  - **数据支撑层 18 个**：业务数据标准化、加密存储、脱敏、全文检索、数据血缘追踪、主数据映射、元数据管理、多源采集、权限管控、可视化分析、工作流引擎…
  - **核心业务循环层 76 个**：覆盖立项 → 计划 → 现场实施 → 风险识别 → 证据底稿 → 问题定性 → 报告输出 → 整改闭环八个阶段
  - **治理优化层 6 个**：项目质量评分、审计成效评估、典型案例库更新、问题趋势分析、规则库迭代、审计方法沉淀
  - 另有跨域插件（AIOps 7 / 量化 5 / 知识 4 / 文档解析类 7）

  > 注：按当前 `plugins/builtin/` 契约目录实测（2026-09-11），`audit-*` 命名空间下共 103 个契约目录（支撑 18 / 治理 6 / 其余分布在八个业务阶段），较 100 个验收口径多出的部分为验收后的增补件。此处数字以插件目录实测为准，与阶段验收文档口径的差异已如实标注。

### 5.4 隔离执行与证据链：让结果"可以被别人重算"

**执行隔离**（`packages/plugin_runtime/runner.py`）：

- 以 `python -I` 启动**独立子进程**（`-I` 隔离模式：忽略环境变量、不加载用户 site-packages）
- 只透传 `PYTHONUTF8 / SYSTEMROOT / COMSPEC` 与只读根白名单 `AUDIT_PLUGIN_READ_ROOTS`
- 严格超时（取 manifest 的 `resources.timeout_seconds`）
- 输入输出走 JSON envelope，ASCII 化以避免 GBK 乱码
- 输出 sha256 落盘为 `output-<sha[:16]>.json`，账本记录 `input_sha256 / runtime_code_sha256 / output_checksum`

**端口绑定执行**（`PortBoundExecutor`）：

- 以 `(node_instance_id, output_port_id)` 为**唯一句柄**取值 —— 不是"拓扑序里的上一个节点"（这是旧实现的真实缺陷，已修复）
- 每个节点单独授权：`PolicyEngine(allow=[capability])`
- 幂等键 = `f"{idempotency_key}:{node_instance_id}"`，重跑不会重复落数
- 插件读取时**复核**上游产物的 `size_bytes` 与 `sha256`，不符即拒绝 —— 输入不可篡改

**证据包**：运行结束后打包 zip（`plan.json` / `attempts.json` / `edges.json` / `manifest.json` / 各节点产物），并支持**离线复验** `verify_evidence_bundle`。实测对 6 个历史证据包做离线校验，全部 `ok=True, checked=5, missing=(), mismatched=()`。

### 5.5 数据库与多租户

- **16 个 schema**：`iam / policy / catalog / control / event / artifact / semantic / graph / knowledge / belief / audit / quant / aiops / risk / ops / experience`，合计 **113 张表**。
- **行级安全（RLS）**：29 张核心表 `ENABLE + FORCE ROW LEVEL SECURITY`，策略统一为 `tenant_id = NULLIF(current_setting('app.tenant_id', true),'')::uuid`，全库累计 33 条 RLS 策略。`FORCE` 意味着**表属主也绕不过**。
- **分级权限**：迁移角色 `audit_migrator` 与应用角色 `audit_app` 分离；`audit_app` 只有 `USAGE + SELECT / INSERT / UPDATE`，**没有 DELETE、没有 DDL、没有 BYPASSRLS**。
- **最小授权**：Worker 角色对 `event.outbox` 只授 `SELECT, UPDATE`，对 `ops.pending_outbox` 只授 `SELECT`。

> 一个真实踩坑：诊断脚本查询 `plugin_blueprints` 返回 0 行，看起来像"表里没数据"；实际是**该连接没设 `app.tenant_id`，被 RLS 过滤掉了**，设上租户后是 **739 行**。这个坑后来被写进验证报告作为典型案例。

### 5.6 知识图谱与经验积累

- **六图分治**，而不是一张无限膨胀的大图；`claim–evidence` 模型承载"主张—证据"。
- **知识生命周期**：`change_sets → validate → approve → release → activate → rollback`，走版本化治理，不直接改生产图谱。
- **经验动态更新**（本项目自研的统计层）：
  - 节点/边的权重 = `log1p(n) × Wilson 95% 置信度下界`（z = 1.96）
  - 时间衰减：半衰期 **90 天**（λ = ln2 / 90），在读取层实时计算，**不回写行**
  - 候选关系走 `proposed → accepted / dismissed` 状态机，终态冻结、同决策幂等重放
  - 运行事实自动投影为经验证据（独立短事务 + 吞异常，**投影失败绝不影响业务运行**）
- **检索**：向量 + 全文 + 图谱混合，RRF（Reciprocal Rank Fusion）融合排序；多图谱按预算路由，防止海量图检索"炸掉"。

> 注：经验态图层当前只服务于知识星云的可视化与人工决策。把它**回流到 AI 组网**以提升组网准确度、成功率与效率的通道设计，见 §5.10。

### 5.7 桌面驾驶舱（Electron + React 19）

**13 个工作台视图**：概览 / 运行 / 知识 / 图谱 / 插件 / 审计 / 量化 / AIOps / 审批 / 策略 / 日志 / Run 画布 / AI 设置。

三个亮点：

1. **Run 画布（ComfyUI 式「过程可见」数据流可视化）**
   纯前端只读、零后端写面。把 AI 组网与运行过程变成可播放的动画：
   - `topoOrder()`：Kahn 拓扑排序 + 沿拓扑序**单趟**最长路径分层（环上节点不丢、层级不膨胀）
   - `buildTimeline()` / `buildFrame(t)`：虚拟时钟时间线，节点相位 `idle → active → done`，边数据包进度 0..1
   - `flowLayout()`：端口化布局，节点高度随端口数自适应，cubic 边精确连左右端口锚点
   - 播放/暂停/单步/0.5–4× 变速/拖动进度条；边三态（未导通灰 → 流动金 → 导通青绿虚线，失败红）
   - 下钻面板逐条列出「数据从哪传入(N)」与「产出/中间结果(N)」，每条带 `sha256` 与本地路径
   - 全部为**纯函数**，可脱离 React 单测（11 个 vitest）
   - 期间修复了一个**真实死循环**：最长路径分层原用 `while(changed)` 松弛，纯环图上每轮层级 +2 永不收敛（进程 CPU 飙到 272 秒）；改为沿拓扑序单趟 DP 后线性终止

2. **知识星云**：Canvas 2D 电子云轨道 + 星座网络；插件节点按运行经验染色（成功率红→黄→绿），边宽 ∝ 衰减后权重；候选连线三态（proposed 金虚线 / accepted 金实线 / 已发布青绿实线）。

3. **星图态势**：Three.js 的 EVE 风格 3D 星图，叠加 Mission → Workflow → Task → Agent 四级运行状态。

**Electron 主进程安全设计**（关键：GUI 不能绕过策略）：

- **IPC 白名单**：`assertTrustedSender()` 校验 `event.senderFrame.url` 只允许 `file:` 或 `http://localhost:`
- **路径白名单**：约 50 条声明路径 + UUID 子资源正则；`controlPlaneRequest()` 首行即 `throw "桌面端拒绝未声明的控制平面接口"`
- **幂等键自动注入**：`headersFor()` 对 POST / PUT 自动补 `Idempotency-Key`，并统一注入 `X-Trace-Id` / `X-Tenant-Id`
- **多窗口**：全部 `contextIsolation: true, sandbox: true`，通过 `contextBridge` 只暴露 `auditControl`

### 5.8 统一 AI 接入层（一份配置 / 一个网关 / 可记忆 / 桌面可填）

把此前散落三处的模型接入（画布助手、AI 组网规划、知识库向量化各自 new 客户端、各自读环境变量、各自捕获异常）收敛为一个包：

- **配置解析顺序**：`AI_*` → 旧变量（`OPENAI_COMPAT_*` / `OLLAMA_*`）→ 内置默认。**provider 专属旧变量只在 provider 匹配时参与** —— 环境里有 `OLLAMA_URL` 不会把云端通道指向本地（这是最容易踩的坑，已用单测钉死）。
- **调用时读取而非 import 时读取**：设置页写 `.env` 同时更新进程 `os.environ`，下次调用即生效，**无需重启**。
- **密钥安全**：只回传 `api_key_set` + 掩码尾 4 位；策略账本只记**键名不记值**；`.env` 原子写（临时文件 + `os.replace`，覆盖前留 `.env.bak`），值含换行直接拒绝（否则等于允许注入任意环境变量行）。
- **探针**：`POST /api/v1/ai/test` 通道不通时返回 **200 + ok=false + 原因**，而不是 HTTP 错误 —— 让界面能渲染失败原因。

### 5.9 可观测性与三层下钻

同一个 `trace_id` 贯穿三层，且三层可互相追溯：

| 层 | 载体 | 实测 |
|---|---|---|
| 数据层 | `control.node_attempts WHERE trace_id = …` | 2 行，均 succeeded |
| 日志层 | `SegmentedSpool` 分段 spool 按 trace 检索 | 2 帧，`spool_integrity = complete` |
| 代码层 | 端口适配器注册 + 磁盘产物 | 数据 sha256 与输入一致；跨节点走适配器 |

日志侧还有：独立 Collector 服务、结构化 envelope、stdout/stderr 分流、spool 分段归档索引、按日归档、敏感键值（authorization / token / api_key / password）自动脱敏为 `***`。

### 5.10 知识图谱驱动组网：让"经验"回流，提升准确度 / 成功率 / 效率

这是本项目最重要的一条**演进主线**，也是把"知识图谱"和"AI 组网"真正连起来的地方。

#### （1）现状：双图层已经建好，但只连了一半

| 图层 | 来源 | 性质 | 当前用途 |
|---|---|---|---|
| **设计态图层** | 从插件契约目录推导 —— "理论上谁能连谁" | 静态、确定性、纯函数 | 支撑组网连线（按 `schema_ref` 契约相等自动连线） |
| **经验态图层** | 从真实运行账本投影 —— "实际谁和谁配合过、效果如何" | 动态、随业务增长 | **目前只服务于可视化与人工决策** |

经验态这一侧，闭环其实是完整落地的：

```
业务链 run 结束（success / failed 落定）
  → ExperienceProjector 读该 run 的全部节点台账与输入绑定
  → 提取每一条"实际数据交接"：source_plugin → target_plugin @ contract
  → 与设计态边集合比对：命中 = declared，未命中 = 设计外协作
  → 写 append-only 观测行（幂等，重复投影不翻倍）
  → 从全部观测重算聚合统计（增量与全量重建等价）
  → 权重 = log1p(n) × Wilson 95% 置信度下界，读取时叠加 90 天半衰期衰减
  → 设计外协作自动生成「候选关系」（proposed）
  → 人工采纳 / 驳回（状态机终态冻结、同决策幂等重放）
  → 采纳后写入知识治理流水线（change_sets → release）成为「已确认关系」
```

并且做了严格的**三级安全分级**：

| 级别 | 内容 | 谁能触发 | 影响范围 |
|---|---|---|---|
| **L0 自动统计** | 使用次数、成功率、耗时、最近使用、产物指纹 | 系统在 run 终态自动投影 | 只改变边的粗细 / 颜色 / 排序，**不改关系集合、不授权、不执行** |
| **L1 候选关系** | 设计外协作（实际交接了数据，但契约里没有这条边） | 系统自动发现 | **不直接进图**，状态 `proposed`，前端画金色虚线 |
| **L2 人工固化** | 采纳 / 驳回候选，或沉淀为正式契约 | 人（必须经策略门 + 幂等） | 关系集合**只在人工确认后**改变，驳回也留痕不硬删 |

#### （2）缺口：经验还没有回流到"下次该怎么组"

组网这一侧的输入，目前是四样东西：

1. 能力目录 = DB 蓝图 ∩ 运行时已验证能力
2. 关键词召回（匹配名称 / 描述 / 能力）
3. 契约相等连线（`source.schema_ref == target.schema_ref`）
4. **静态硬编码模板**（`packages/ai_planner/templates.py` 的 `TEMPLATES`，人工写死的完整 JSON 示例）

也就是说：**系统已经在积累"哪些组合真的跑成功过"，但这些经验还没有回流到组网决策。** 而 L0 的定义里明确限定了它"不改关系集合、不授权、不执行"——它是一条**没有闭环回去的经验链**。这是一个明确的、可量化的增强点。

#### （3）提案：三条回流通道

> 总原则：**经验只改变概率分布，不改变权限集合。**

**通道一 · 召回排序（提效率）**
能力召回从"纯关键词匹配"升级为"关键词 × 经验权重"：用 `node_stats` 的成功率（Wilson 下界）、最近使用时间（衰减后权重）、平均时延对候选排序，把**被真实验证过**的能力送进 prompt 前排。真实环境里候选噪声很大（实测测试库里有 272 项，其中大量是集成测试残留），候选排序更准 = 喂给模型的候选更少 = token 更省、决策更快、选错概率更低。

**通道二 · 连线先验（提准确度）**
用 `edge_stats` 中**高成功率 + 高样本量**的 `(source_plugin → target_plugin @ contract)` 三元组作为**推荐连线**，在草稿阶段作为提示注入，或作为 composer 自动连线的优先级依据。其中 L2 已固化的「已确认关系」尤其有价值 —— 那是**人工确认过的真实通路**，比模型自己猜的连线可信得多。这条通道等于把"人工采纳"的成果真正变成了组网的生产力。

**通道三 · 失败规避（提成功率）**
把长期失败 / 低成功率的 `(插件, 能力)` 组合降权或标记为"不推荐"，并把 `node_stats` 的错误分布作为 prompt 中的**已知风险提示**，减少模型重复踩同一个坑。

**附带 · 模板动态化**
现有模板是人工写死的静态 JSON 示例。可以把"同类目标下的历史成功执行计划"沉淀为**动态模板**，让模型参考一次真实成功的结构，而不是人工构造的样例。

#### （4）安全边界（不可越线）

- 经验只影响**候选排序与提示内容**，不得新增能力、不得新增端口、不得放宽数据边界、不得绕过编译闸门与策略网关
- 注入前必须过统计门槛：**Wilson 置信下界 ≥ 阈值且样本量 ≥ N** —— 这正是当初引入 Wilson 下界与 90 天半衰期衰减的原因（避免"一次成功就满分"）
- 经验数据受 RLS 与租户隔离约束，**不得跨租户污染先验**
- 每次回流决策留痕可回溯：哪次组网用了哪条经验、权重多少、来源哪个 run

#### （5）验收方法（脚手架是现成的）

`tests/evaluation/test_ai_planning_intents.py` 已有 **≥ 20 个固定评测意图**（带分类、带闸门行为断言、带全局安全断言），可直接做成开关对照实验：同一批意图跑**"关经验回流" / "开经验回流"**两组，其余变量固定。

| 目标 | 指标 |
|---|---|
| **准确度** | 草稿**首次通过闸门率**（first-pass rate）、20 意图的分类通过率 |
| **成功率** | 真实 run 的成功率、失败分类计数 |
| **效率** | 达到 `draft_ready` 的**平均修订轮数**（当前上限 3 轮，实测曾用满 3 轮）、端到端时延、喂给模型的候选数量与 token 量 |

#### （6）为什么这条路线值得做

它提升准确度、成功率、效率，**却不需要放宽任何一条安全约束** —— 因为它优化的是概率分布，不是权限边界。这与整个项目"策略平面独立于 LLM"的原则完全一致：**模型依然不能自授权，只是被喂了更好的先验。**

## 七、端到端实战案例（真实跑通，非演示动画）

**目标**：让 AI 自己组一条"质检 + 回测"的链并真实执行。

| 步骤 | 内容 | 实测结果 |
|---|---|---|
| 0 | 现场合成 9 行日记账 CSV，**刻意植入 6 项质量瑕疵** | sha256 `1f8e4bfd…`，548 B，9 行 |
| 1 | 能力召回（DB 蓝图 ∩ 运行时已验证能力） | 272 项噪声 → 业务域过滤后 **4 项**可见能力 |
| 2 | 云端 AI 组网（召回 → 出草稿 → 闸门 → 编译 → 失败回灌） | 经 3 轮修订后 `status=draft_ready`，**通过编译闸门** |
| 3 | 策略裁决 + 落库（幂等键 / 短事务 / outbox） | 产出 `run_id` / `trace_id` / `execution_hash` |
| 4 | `PortBoundExecutor` 子进程隔离执行 | 每个 attempt 有 `input_bindings` / `output_refs` + sha256 |
| 5–6 | 画布投影 + 证据包导出 | `evidence/{run_id}.zip`，离线复验 `ok=True` |
| 7 | 同一 `trace_id` 三层下钻 | 数据/日志/代码三层均可追溯 |
| 8 | 业务结论 | 见下 |

**质检输出**（`audit.ledger.validate`）：

```json
{"total_rows":9,"candidate_count":6,"duplicate_rows":1,"unbalanced_entries":1,
 "out_of_period_rows":1,"truncated":false}
```

6 项疑点：不平衡凭证（E1003，high，0.85）、重复行（medium）、缺金额（medium）、超期（medium）、大额×2（low）。

**回测输出**（`quant.experiment.evaluate`）：`recommendation = hold`（不做生产变更）+ `max_drawdown = -0.05` + `positive_period_ratio = 0.75`。

**最硬的一条证据**：不复用项目任何代码，**自行实现 6 条质检规则重算**，得到与插件产物**逐条一致**的 6 项候选 —— 这就是"结论可被独立复算"的含义。

## 十、沉淀的工程方法论（可迁移）

1. **把"信任"变成"可验证"**：不争论 AI 可不可信，而是让每个产物带 sha256、每个结论能离线复算。
2. **默认从严，放行需声明**：`require_policy` 默认 `high` 风险；未知能力直接拒绝。安全设计的成本不该由"记得加检查"来承担。
3. **AI 只做"填槽"，不做"决定"**：能力白名单 + 端口契约 + 数据边界，三道闸门把模型关进可测试的盒子。
4. **先写契约测试，再写实现**：每个阶段先红后绿，接口先行。
5. **独立复算胜过自测通过**：自己写的测试只能证明"符合预期"，独立重算才能证明"结论正确"。
6. **诚实收口**：做不到就输出缺口报告（`gap_report`），绝不伪装成功 —— 这在审计场景里是底线。
7. **对作品做对抗性验证**：主动找自己的缺陷，比等别人发现更有价值。
