# 案例数据接进项目组网（2026-09-24）

把三份审计案例数据集（对照 / 实验组 / 高难度）接入**产品自身的组网链路**，让它们从
"案例自带的脚本资产"变成"产品的端到端测试资产"。

驱动：`scripts/run-case-network.py`；派生数据与产物落在 `.data/case-network/`（**不改案例一个字节**）。

```
案例 CSV → 契约适配 → compile_plan → 策略网关 → start_plan_run（隔离运行时）
        → 运行账本（control.node_attempts）→ 经验层（experience.*）
```

---

## 一、结果：32 次运行全部成功

| 案例 | 运行数 | 分录 | 凭证 | 状态 | 候选 |
|---|---|---|---|---|---|
| 对照-基础 | 10 | 178 | 89 | **10/10 succeeded** | `large_amount` 176 |
| 实验组 | 10 | 200 | 100 | **10/10 succeeded** | `large_amount` 198 |
| 高难度 | 12 | 235 | 116 | **12/12 succeeded** | `large_amount` 199 |

**落进产品的证据**（查库实测）：

```
control.node_attempts   plan_key LIKE 'case-%'  →  33 个 run / 66 条 attempt，全部 succeeded
experience.edge_observations                    →  1102 → 1135（+33）
experience.node_observations                    →  1726 → 1792（+66）
```

即案例数据现在会**自动进入运行账本与经验层**——上一轮打通的七环闭环，从这一批数据开始
就有真实的案例证据可吃。

**另外三条"零"值得单独说**：32 次运行产出的候选里 **`unbalanced_entry` / `duplicate_row` /
`out_of_period` / `missing_or_invalid_amount` 全部为 0**。这不是程序没跑，而是产品侧的台账检查
与案例自带的完整性声明**独立地对上了**——案例设计里凭证"逐张借贷相等"、日期金额完整，
产品读同一批数据得出了同样的结论。

## 二、接的过程中修掉的产品缺陷：台账期间被写死

**症状**：直接把案例数据喂进去，`out_of_period` 会对**每一行**报警。

**根因**：`packages/plugin_topology/ports_executor.py::_ledger_artifact_value` 把期间写成了常量：

```python
"schema_mapping_version": "1.0.0",
"period": "2026-01",          # ← 写死
```

而插件的 `out_of_period` 规则按 `date[:7] != period` 判定 —— 于是产品**实际上只能吃
"刚好落在 2026-01"的台账**，任何其他月份的真实数据都会被逐行判错。

**修法**（4 处，全部向后兼容）：把期间做成工件自带的属性，一路贯通
`ArtifactInput.period` → `ArtifactRef.period` → `_ref_to_artifact_input` → 载荷构建器；
缺省仍回落到 `"2026-01"`，既有调用方行为不变。刻意**没有**把 `period` 放进 `as_payload()`：
合同里 `period` 在信封层、不在 artifact 对象里，而 `as_payload()` 的形状被投影与报告依赖。

**验证**：修复后 32 次运行 `out_of_period` **= 0**；修复前同一批数据会产出 613 条。

## 三、两个"映射必须做对"的决定（错一个结果就没意义）

| 决定 | 为什么 |
|---|---|
| `entry_id` 取**凭证号**，不取行号 | 借贷平衡规则按 `entry_id` **分组求和**。一行一个 id 会让每一行各自"不平"，613 条分录会刷出上百条假候选，且看起来像真实发现 |
| 借贷金额**空白填 `0.00`** | 借方分录没有贷方金额是正常记账。留空会被 `missing_or_invalid_amount` 判为缺金额，同样刷一半假候选 |

另一个口径问题：插件是**按月**台账质检，而案例是**全年**凭证 —— 所以驱动**按月拆分**，
每月一次组网（10+10+12=32 次），而不是把一年塞进一个月。

---

## 四、仍然存在的缺口（未修）

**`amount_threshold` 同样不贯通**。契约里有这个字段，但 `_ledger_artifact_value` 不设置它，
插件回落到默认 100 万 —— 对一个总资产 115 亿的集团，**613 条分录里有 573 条（93%）超标**，
`large_amount` 规则因此不具区分度。

与 `period` 是同一类缺口（口径参数没有贯通路径），修法同上：让阈值随工件/端口传入。
本轮**未动**，因为它需要先定"阈值从哪来"（合同字段？端口契约？能力参数？）——
`contracts/capability-parameters.json` 已有"声明式能力参数"的机制，可能应当走那里。

## 五、复现

```bash
python scripts/run-case-network.py                        # 三份案例全部月份（32 次运行）
python scripts/run-case-network.py --case 高难度          # 只跑一份
python scripts/run-case-network.py --limit-months 1       # 每份只跑最近一个月
```

只读案例目录；派生 CSV、产物与 `summary.json` 全部写在 `.data/case-network/` 下。
