# 插件目录补链方案（第 5 项）

日期：2026-09-26 · 对应 `docs/接入AI组网-开发测试-20260926.md` 第九节第 5 项

---

## 一、问题：自动组网的深度被目录卡死

**实测现状**（`packages/catalog/connectivity_view.py` + `discover_plugins`）：

| 指标 | 值 |
|---|---|
| 插件数 | 107 |
| 契约边 | **69** |
| 完全孤立节点 | **35** |
| **不可填输入契约** | **54** |
| 死端输出契约 | 58 |

**最被需要、却无人生产的输入契约**（括号内为在等它的插件数）：

```
workpaper-draft (5)      project-snapshot (5)     clean-finance-set (3)
final-issue-set (3)      photo-evidence (2)       evidence-index (2)
anomaly-candidates (2)   remedy-ledger (2)        schedule-plan (2)
high-risk-area (2)       finding-set (2)          report-approved (2)
```

**后果**（今天的实测佐证）：让云端模型自由组网 5 次，它**每次都只能组出同一条链** ——
`audit.ledger.validate → quant.experiment.evaluate`。不是模型不会组，是**目录里只有这一条链连得起来**。
**自动组网再聪明也组不出一条目录里不存在的链。**

---

## 二、根因

1. **每个 `contract_id` 只有一个产出者**（状态文档已登记：*"123 个插件里每个 contract_id 只被 1 个插件产出"*）——
   没有冗余，也没有"同一个中间产物被多个下游消费"的扇出。
2. **103 个端口无人生产**（按端口计），其中 54 个是**必填**输入 —— 这些插件的输入永远悬空。
3. **58 个产出无人消费** —— 链条在末端断掉，终端节点过多（实测 51 个终端节点）。
4. 三者叠加的结果就是"一条主链 + 大量并行独立分析"，而不是一张网。

---

## 三、目标与验收闸门

**目标不是"把孤立节点数压到 0"**。`packages/ai_planner/connectivity.py` 的文档里已经写明：
早期为了压孤岛数曾按 `schema_ref` 相似度**强连**节点，后来被否 —— 那是在编造关系。
所以本方案的目标是**补真产出者与真消费者**，验收也据此：

| 闸门 | 现在 | 目标 |
|---|---|---|
| 不可填输入契约 | 54 | 逐域收敛；**每个被补的契约都有真实产出者** |
| 最长可组链长度 | 2（唯一那条） | ≥ 4 |
| 有入有出的中间节点占比 | 低（35 孤立 / 107） | 明显上升 |
| **口径** | — | 连通性报告（`scripts/report-connectivity.py`）作基线对比；**基线不可回退** |

`report-connectivity.py --write-baseline` / `--baseline` 已经是 CI 闸门形态，直接用它冻结"补链前"的口径。

---

## 四、补法（按"每单位工作量解锁的链长"排序）

### 4.1 优先补"最被需要的输入" —— 一次解锁多条

`workpaper-draft`（5 个插件在等）与 `project-snapshot`（5 个）是最高杠杆的两个。
补上它们的产出者，等于**一次让 5 条边成立**。

做法：为每个高需求契约，检查现有插件里是否**已经有能力产出同类产物**（只是端口名/schema 不同），
有则**修正端口声明**（这是改声明，不是编造）；没有则**新增一个最小插件**。

### 4.2 把死端输出接到需要的输入 —— 不新增插件，只补边

58 个死端输出里，若某个产出与某处悬空输入是**同一业务对象**（`schema_ref` 相同），
那这条边本就该存在，缺的只是**声明**。这类是"零成本补链"：只改插件清单，不写新插件。

**判据必须是业务对象同一性（同一 `schema_ref`），不是名字相似** —— 后者正是被否过的强连。

### 4.3 逐域闭合（按 `by_domain` 分组推进）

现有分域（实测）：`audit 107 / aiops 7 / knowledge 4 / quant 5`。按域把
"输入 → 处理 → 输出"闭合，比跨域乱连更可控；跨域只允许经**已登记的四类桥接**。

### 4.4 补链的声明落在哪

沿用本项目已有的声明风格（`contracts/input-mappings.json`、`capability-parameters.json`、
`networking-quality-gate.json`）：

* **新增插件** → 走既有 `plugins/builtin/<plugin>/plugin.manifest.json` + `plugin.protocol.json`
  （**不要**新造格式）；
* **修正端口声明** → 同样改 manifest，不需要新文件；
* **补链进展** → 用 `docs/status.md` 的登记 + 连通性基线 JSON 冻结，不另建台账。

**明确不新增**：不建"补链清单"这类新声明文件 —— 端口关系的事实源已经是插件清单本身，
再建一份就有了两个事实源。

---

## 五、边界（不许越过）

1. **不按相似度强连**：`schema_ref` 不同就是不同业务对象。连通性好看但关系是编的，会被删掉。
2. **不为连而连**：有些孤立是**设计使然**（`按设计吃外部输入` 的 scheduler / validator 类）。
   连通性报告已把它们分类，**只处理"真缺口"那一类**（实测当前真缺口只有 1 个：
   `audit.evidence.evidence-archive` 应有上游但全库无生产者 —— 这类才是目标）。
3. **不新增能力以迎合组网**：补的必须是审计业务里真实存在的处理步骤，不是为了让图好看。
4. **不动执行器语义**：补链只改目录与声明，不改 runner / 隔离运行时 / 策略。

---

## 六、顺序与验收

| 阶段 | 内容 | 验收 |
|---|---|---|
| 0 | 冻结基线 | `report-connectivity.py --write-baseline .data/connectivity-baseline.json` |
| 1 | 补 `workpaper-draft` / `project-snapshot` 的产出者 | 不可填输入 54 → ≤44；边 69 → ≥79 |
| 2 | 零成本补链：同一 `schema_ref` 的死端输出↔悬空输入 | 边数上升且**无新增孤立** |
| 3 | 逐域闭合（audit 优先，占 107 个插件里的绝大多数） | **最长可组链 ≥ 4**；连通性闸门无回归 |
| 4 | 回归 | `--baseline` 无回退 + 全量测试通过 |

**第 3 阶段完成时才是"自动组网能组出深网"的起点** —— 在那之前，模型能组出的深度由目录决定，
不由模型决定。

---

## 七、为什么这件事只能在这里做

编排侧（触发层、质量门、经验回流）已经做完，但它们解决的是"**该不该跑、跑得对不对**"；
**"能跑出什么"完全由目录决定**。今天的实测已经把这条因果链摆得很清楚：
同一套编排、同一个模型，5 次组网只产出同一条两节点链 —— 因为目录里只有那一条。
