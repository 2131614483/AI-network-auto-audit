## 1. 结论与本轮边界

建议把现有项目演进为：**AI 负责选择插件、生成连线和修订方案；确定性编译器负责检查；统一调度器负责运行；画布负责展示与干预；独立日志服务负责完整留痕。**

模仿 ComfyUI 的节点、端口、连线、分组、运行队列和节点预览，但不复制其执行系统，更不把画布本身当成执行权限入口。用户的默认操作应是“选文件／数据源 → 说明目标 → AI 自动组网 → 查看结果”，手动连线是高级功能，不是使用前提。

现有项目值得保留，不需要推倒重写：有 23 个内置插件实现映射、M1–M10 拓扑治理、真实子进程调用、产物校验和、运行验证及证据锚定。但目前还不能等同于“AI 自动组织任意 DAG、可靠流转数据并保存全部日志”。优先修复以下基础，再开放持续自动运行：

1. 静态画布与真实目录分离，导致图上内容不一定代表可运行内容。
2. 隔离链主要传递“紧邻上一个输出”，不是逐条数据边解析输入。
3. 发布锁尚未保证规划、物化全过程都读取同一份冻结快照。
4. 长事务包住子进程执行，异常路径可能回滚已经写下的失败证据。
5. 日志有轮转淘汰、4000 字截断、stderr 未保存和桌面关闭后聚合中断等缺口。

本轮只做文档与静态审查，没有启动插件、修改数据库、部署服务或开放新权限。用户所写 `D:\pythonpro\audit\_network\docs` 在本机不存在；本次依据实际工作区 `D:\pythonpro\audit_network\docs` 与对应代码。

## 3. ComfyUI 应借鉴什么，技术上如何落地

ComfyUI 工作流格式包含节点、链接、分组和版本等信息，适合作为交互参考；本项目需要额外支持租户、审计证据、受控执行及长期恢复，因此建立自己的执行契约，不承诺直接运行 ComfyUI 工作流。[官方 Workflow JSON](https://docs.comfy.org/specs/workflow_json)

ComfyUI 有开始、进度、错误、缓存等运行消息，可以借鉴事件驱动界面；其 `executed` 消息并不代表每一个节点都完成，不能直接用来证明本系统审计事件完整。本文另定义“结果与证据已提交”的节点完成语义。[官方 Server Messages](https://docs.comfy.org/development/comfyui-server/comms_messages)

### 3.1 技术决策

| 层 | 建议 | 边界 |
| --- | --- | --- |
| 应用外壳 | 保留 Electron 37、React 19、Ant Design、纯 CSS 变量 | 不退回浏览器启动页，不引入新路由体系。 |
| 二维工作流画布 | 优先做 `@xyflow/react` 小规模兼容性验证，再决定引入 | 这是针对节点编辑、端口和连线的专项依赖；本轮不安装，不承诺未经验证的版本组合。 |
| 知识图谱／集群总览 | 保留 ECharts 与已有 Three.js 探索层 | 它们用于关系探索，不保存执行真相，不承担工作流编辑器。 |
| 前端状态 | 使用已安装的 Zustand，拆分目录、草稿、运行投影、日志查询状态 | 现有 App 大量局部状态不继续膨胀；只订阅当前节点或视口需要的数据。 |
| 后端 | 保留 Python 服务、PG16 + pgvector、现有 Policy Gateway 与插件运行时 | 不以 Docker、Redis、Kafka 或新工作流平台作为首版前置条件。 |

React Flow 的多端口可通过唯一 handle ID 与 `sourceHandle/targetHandle` 绑定，适合本项目的实例端口模型；这只是界面能力，契约与权限仍由后端校验。[官方 Handles](https://reactflow.dev/learn/customization/handles)

不直接依赖已归档的 `Comfy-Org/litegraph.js` 仓库：其官方说明已合入 ComfyUI 前端。照搬完整前端会增加现有 React 架构的适配范围。[官方仓库状态](https://github.com/Comfy-Org/litegraph.js)

新增画布库前必须记录许可、锁定版本、Electron 兼容、打包与离线运行验证。业务颜色、边框、字号继续走全局 CSS；画布引擎计算的坐标／尺寸是几何状态，不要求为每个坐标生成 CSS 类，也不能借此恢复业务组件硬编码样式。性能上采用节点 memo、局部订阅、子图折叠和限制可见复杂度。[官方性能指南](https://reactflow.dev/learn/advanced-use/performance)

### 3.2 不可混为一谈的三张画布

1. **能力目录图**：谁能做什么、可接收什么、属于哪个集群；展示候选关系，不代表发生过调用。
2. **工作流草稿图**：某个任务选择了哪些插件实例、参数、端口和条件；可以由 AI 或人修改。
3. **运行实例图**：某个冻结版本在某次运行中的状态、数据和日志；只读投影，不能被拖线改写。

同一个插件可以在一个工作流中出现多次，各有独立 `node_instance_id`。插件 ID、蓝图 ID、能力 ID 和节点实例 ID 不得混用。

## 4. 目标架构：AI 规划，确定性执行

```text
用户目标 + 已授权数据引用
          │
          ▼
多级能力目录检索 ──→ AI Planner 输出 GraphPatch / WorkflowDraft
          ▲                         │
          └── 结构化缺口与编译错误 ──┤  有预算的修订
                                    ▼
                      确定性编译器 + 策略预检
                                    │
                                    ▼
                     冻结 WorkflowRelease / ExecutionPlan
                                    │
                                    ▼
                     持久调度器 → Runtime Adapter → 插件
                                    │                  │
                                    └──── ArtifactRef ─┘
                                    │
                                    ▼
                        运行事件 / 日志归档 / 证据索引
                                    │
                                    ▼
                       Electron 画布、节点检查器、历史回放
```

复用关系：M10 的图谱检索用于候选召回；M1–M3 的目录、发布、计划与接线用于编译；M4–M8 的审批、运行、验证和处置用于治理；M9 的锚定用于证据核验；`control.scheduler` 补成唯一持久调度内核。旧拓扑运行接口通过适配层转交该内核，并保留历史 run/ledger 可读。

禁止同时让旧 `IsolatedChainExecutor` 与新调度器拥有同一 run 的执行权。迁移期间显式标记 `execution_backend`，一个 run 只有一个所有者；历史同步接口逐步兼容到异步运行 ID，不悄悄改变响应契约。

### 4.1 多级、多集群与有限跨图关联

- L0：业务域、能力族、运行资源池、治理区的聚合入口。
- L1：任务模板与插件蓝图；只展开与当前目标有关的模板。
- L2：能力、版本化端口、允许的转换器和兼容关系。
- L3：被授权且与任务相关的领域知识子图。
- L4：运行、产物、日志和证据引用；按 run 按需下钻，不把所有历史实例铺入能力目录。

延续现有 T／W／O／E 分治：插件能力拓扑 T、工作流 W、领域本体与知识图 O、证据血缘 E 分开存储与投影，通过版本化引用连接，不复制成一张无限增长的万能图。运行状态与日志是独立观测投影，关联 W／E，不重新定义 O 的含义。

路由顺序为：治理区／业务域过滤 → 能力索引召回 → 局部有界关系展开 → 端口可连接检查 → 资源预算检查。初版可沿用现有有界检索，不为了“更智能”直接扫描全部图谱。未找到路径时返回缺失能力、缺失适配器或授权不足，不把无关高分插件拼进结果。

跨域仍限制为已有的 `artifact_ref / capability_contract / released_graph_ref / health_signal`。Ref 只是传输形式，不自动赋予读取权限。审计机密不能因为输出恰好是 JSON 就交给量化或外部模型。现有“总账质量 → 量化研究笔记”演练桥不能当作合理业务分析的证明。

## 5. 统一契约：画布、AI 和执行器说同一种语言

以下是**拟新增或扩展的逻辑契约**，不是现有 API 已支持的字段。先写 JSON Schema、正反样本与编译测试，再实现服务。

| 对象 | 核心内容 | 不变量 |
| --- | --- | --- |
| `NodeDefinition` | 插件／能力版本、绑定状态、命名输入输出端口、参数 Schema、资源、数据等级、UI 声明 | 从服务端验证后的目录生成，AI 不能发明定义。 |
| `WorkflowDraft` | 工作流 ID、draft revision、目录发布引用、目标、节点实例、数据边、控制边、输出要求 | 可修订但保留历史；修改使用 base_revision 做并发检查。 |
| `GraphPatch` | 对指定 revision 的有限增删改操作、原因、引用证据 | 无脚本、SQL、shell、任意 URL；修改越界必须拒绝。 |
| `WorkflowRelease` | 编译通过的 DAG、插件包／契约／转换器快照、参数、预算、执行哈希 | 不可变；必须可以不读取当前目录而还原。 |
| `ExecutionPlan` | 发布引用、逐端口输入映射、依赖与就绪规则、重试、缓存、资源池、审批关口 | 唯一可执行中间表示（IR）；所有执行器消费同一版本。 |
| `CanvasLayout` | 位置、缩放、分组、折叠、视角、注释 | 与执行定义分离；拖动节点不改变执行哈希。 |
| `ArtifactRef` | 受控产物 ID、SHA256、字节数、Schema、版本、数据等级、来源及保留状态 | 不可变内容引用；调用前检查归属、权限、存在性与哈希。 |
| `RunEvent` | 运行状态变化、策略、数据交接和日志引用 | 追加式；状态投影能从事件重建。 |

### 5.1 端口与数据边

每个端口至少包含：`port_id`、`direction`、`schema_ref`、`schema_version`、`schema_sha256`、`media_type`、`required`、`cardinality`、`classification`、`transport`。业务需要时补单位、币种、时区、时间点口径与排序要求。

数据边明确为：`edge_id + from(node_instance_id, port_id) + to(node_instance_id, port_id)`。输出相同契约到两个消费者是合法 fan-out；一个输入接多个生产者只有在声明 list 或确定性 join 规则时才合法。重复边、未知端口、必填输入悬空均拒绝。

不能把 `audit-quality-candidates@1` 改名就当作 `anomaly-candidates@1`；不能把 `incident-candidate-set@1` 当作 `incident-proposal@1`；不能把快照校验报告当作 `factor-input@1`。这些在当前插件协议中确实是不同输入输出，必须显式转换并保留来源，或保留为独立支路。

旧 UPP 中部分输入只有数组顺序和契约名，且可选性写在描述中。升级时通过审核后的能力适配定义补稳定端口名和 required 标记；有歧义的定义返回 `definition_incomplete`，不让 AI 自行猜测。新增定义采用版本化扩展，保留旧协议与旧运行可读。

### 5.2 编译检查顺序

1. 校验草稿 Schema、revision 和允许的节点种类；节点定义来自指定目录快照。
2. 验证插件绑定、包／依赖／契约版本、每条边的来源与目标。
3. 校验必填端口、字段语义、数据域、适配器和跨域授权。
4. 校验无环、目标产物可达、所有业务需求被覆盖；首版不支持无限循环或动态任意扩图。
5. 校验条件和 join 的明确语义、节点／字节／时间／CPU／GPU／模型调用预算。
6. 策略预检并列出待审批关口；预检通过不替代运行时裁决。
7. 生成不可变发布与执行哈希，输出逐节点输入来源和可解释错误列表。

错误至少带 `code/node_id/port_id/edge_id/evidence_ref/suggested_action`。示例错误包括 `missing_required_input`、`contract_mismatch`、`unsupported_feature`、`budget_exceeded`、`capability_unavailable`、`data_boundary_denied`。AI 可根据错误改下一版，但不能把验证开关关闭。

执行哈希覆盖语义相关图、参数、冻结定义与插件包、Schema、转换器、运行环境、策略约束和输入绑定规则；实际输入内容哈希加入 run／缓存身份。布局、选中节点和缩放不加入执行哈希。审批引用确切版本和数据范围，语义修改后重新评估。

## 6. AI 如何自动组网，而不是让用户自己拖线

### 6.1 默认流程

1. 用户选择文件、知识库文件夹或已登记数据库快照，描述目标和允许范围。
2. 输入适配层生成 ArtifactRef 和结构化资料摘要；不默认向模型发送全部文件。
3. 候选检索器使用现有多图索引召回可用插件、转换器、模板和历史成功案例。
4. AI 只输出结构化 GraphPatch、选型理由、数据来源、预期产物、缺口和预算。
5. 编译器返回确定性结果；AI 在固定修订轮数内修正，例如初始建议最多 3 轮，超限转为缺口报告。
6. 生成画布和运行预览：哪些部分能自动执行、哪些关口待确认、哪些依赖未就绪。
7. 允许范围内自动运行；用户从节点、连线或结果直接下钻证据，不需要逐个手工接线。

本地模型作为首选可插拔规划后端；实际模型名、结构化输出能力、上下文上限和响应稳定性需重新探测。M10 当前是零 LLM 的确定性匹配，不能更名后宣称已具备 AI 规划。外部模型仅作为未来显式授权的数据出口，本方案不默认开启。

### 6.2 自动化与审批的分界

| 模式 | 可做 | 不可做 |
| --- | --- | --- |
| 仅规划 | 生成、校验和展示草稿，提示缺口 | 不执行插件，不新增权限。 |
| 授权范围内 AUTO | 自动运行精确允许的只读／影子草稿能力，自动重试可重试失败 | 不越过数据域、包版本、资源预算和最终业务确认门。 |
| 关口审批 | 在发布、确认 Finding、正式导出等规定关口暂停，确认后继续合法下游 | 审批不能把整条链永久改为无限制 AUTO。 |

降低调试摩擦的方式是预置**仅测试库、指定输入根和已验证能力的开发策略包**，一次选定范围后不在每个只读节点重复弹窗；不是关闭 Policy Gateway。拒绝时界面说明具体能力、规则和解决方式。

AI 不可自授予白名单，不自动安装缺失插件，不生成并执行临时 Python／shell 转换器。遇到真实生产修复、交易、外发等当前范围外动作，应停留在提案，不能因为整个任务叫 AUTO 就执行。

输入文档、检索结果和插件说明作为不可信任务资料使用，不能修改系统规则或授予新能力。读取的数据里出现“忽略限制／调用某命令”等内容，不成为组网指令；数据出口、能力和补丁仍由编译器及策略检查。

### 6.3 多 Agent 的合理分工

- Planner：拆任务并选择候选。
- Contract Reviewer：解释编译失败、识别缺失输入和语义转换。
- Domain Reviewer：审核业务假设与证据引用，不把异常候选升级成确定结论。
- Run Supervisor：读取运行事件，建议重试、替代路径或新版本。

最终执行授权来自确定性策略与用户约定，不来自多个 Agent 投票。Agent 通过同一工作流 revision 和任务账本协作，修改冲突用 CAS／补丁合并解决。成功案例可进入版本化模板库，但新模板／新插件／新策略必须通过测试和发布，不能在线改写自身生产代码。

## 7. 数据流执行与 24 小时可靠运行

### 7.1 唯一调度器与真实端口输入

以现有 `control.scheduler` 为基础，扩充输入映射和运行时适配，不复制新的队列表。拓扑发布编译成控制任务；节点调度同时要求：前置控制条件满足、必填数据产物已提交、策略允许、资源池有配额。

运行时输出索引为 `outputs[(run_id, node_instance_id, output_port_id)] = ArtifactRef`。下游始终按编译结果取指定生产者端口；不能使用“上一个节点”或列表位置。所有输出先由宿主做 Schema 与 SHA 校验，再提交可消费状态。

大 CSV、PDF、图片、音视频不复制到每条边或数据库日志正文；用受控内容寻址产物存储。第一版先支持完整产物的批处理 DAG，流式端口必须另有序号、水位、背压和结束信号契约，不能拿文件不断变大的路径假装不可变 ArtifactRef。

条件分支与 join 显式区分：

- `all_required`：指定必填支路成功并有产物才启动。
- 未选分支为 `skipped`，不冒充成功，也不能无限等待。
- 上游失败按配置令依赖节点 `blocked`；允许独立支路继续时，整图最终标记部分失败。
- 空集合是合法值还是错误，由端口 Schema 定义；“没有传到数据”不是空集合。
- 暂不支持的 join 类型或任意表达式，编译期直接拒绝。

### 7.2 短事务、恢复与幂等

1. 短事务创建 run、节点计划、attempt、策略引用与开始事件并提交。
2. 事务外启动子进程；宿主持续写日志、更新心跳和续租。
3. 插件输出写受控临时产物，完成校验与原子固化。
4. 短事务验证当前 fencing token，提交输出引用、attempt 终态、节点事件、outbox 通知。
5. 失败使用独立新事务追加终态；DB 暂不可用时在持久 spool 保存待补记录，不声称成功。
6. 重启扫描 `running/unknown/retry_wait`，依据租约、宿主状态、产物收据判定恢复，不默认把失联都当成未执行。

节点建议状态为 `pending → ready → running → succeeded`，并有 `waiting_approval / retry_wait / failed / cancelled / blocked / skipped / unknown`。重试建立新 attempt；同一逻辑节点和幂等效果身份保持稳定。明确区分业务拒绝、策略拒绝、输入错误、超时、崩溃和结果未知。

采用 at-least-once 投递加幂等效果，不宣称任意外部副作用 exactly-once。GUI 的逻辑操作 ID 由主进程托管，网络重发复用同一个键；新运行才新建操作身份。同键不同语义载荷必须 409。

租约令牌随认领递增；旧 worker 即使晚到也不能覆盖新 attempt 结果。fencing 只能约束受控制的提交，不能抹掉已经发生的外部副作用，因此当前仍不开放生产命令与真实交易。

### 7.3 资源、缓存与隔离

- 心跳／续租独立于耗时插件；恢复扫描和重试调度真正接入后台循环。
- CPU、GPU、本地模型和 IO 分池排队；按租户与工作流限并发，不为 23 个插件各常驻一个进程。
- 磁盘、日志积压和数据库健康纳入背压；无日志落盘保障时暂停新执行。
- 缓存只用于声明可复现、只读的节点；key 包含输入 SHA、参数、包／依赖／Schema／模型版本。命中仍重新检查读取权限，并保存命中事件及来源 run。
- 模型结果不能仅因固定 seed 就宣称严格可复现；记录模型版本与参数，区分逐字一致和业务质量验证。
- 当前内置 Python 插件先补宿主日志、进程树清理、超时与资源计量；不可信第三方插件接入前需独立账户／ACL、进程资源限制及网络限制等专项验证。无 Docker 要求不等于无隔离要求。
- 暂停默认停止认领新节点；取消请求传给宿主并保存实际取消结果。没有终结证据时显示 unknown，不显示已取消。

## 8. “保存全部日志”的可验收定义

### 8.1 必须保存什么

完整留存所有已接受任务的规划修订、编译结果、插件与发布版本、策略／审批、节点各次尝试、数据边交接、输入输出引用、stdout/stderr、异常／退出码、重试／缓存／取消、人工修改、验证、处置和导出事件。

AI 记录模型名／版本、参数、可见输入输出、检索证据、结构化计划、选择说明和工具调用；**不要求或声称能够保存模型隐藏思维链**。密钥、令牌等不进入日志。需要留存的敏感原件通过单独受控产物保存，普通日志放脱敏摘要、哈希与授权引用。

“全部”不等于无限磁盘，也不包括尚未启用采集时已经被删除的历史内容。默认不自动删除长期证据归档；保留期限与容量由显式配置决定。高容量 DEBUG 如需不同策略，必须在任务开始前声明，不能采集后悄悄丢弃。UI 可截短预览，但不得据此截断已接受的归档正文。

### 8.2 三层存储

| 层 | 保存内容 | 建议落点 |
| --- | --- | --- |
| 业务事件与索引 | run／node／attempt 状态、策略引用、边交接收据、采集覆盖率 | PostgreSQL 追加事件与可重建查询投影；复用现有业务账本作为来源。 |
| 原始运行日志 | API、Worker、插件 stdout/stderr、桌面事件的结构化记录 | 独立 Collector 管理的本地持久 spool、分段 JSONL；不依赖桌面窗口存活。 |
| 长期证据归档 | 封存日志段、内容寻址产物、运行发布、代码／包清单 | 压缩归档 + manifest + SHA256；后续可配置独立盘或异地副本，但本轮不自动写入其他磁盘。 |

热日志轮转顺序：封段 → 校验内容 → 归档副本落盘 → 索引／manifest 提交确认 → 才允许淘汰热副本。不能让 RotatingFileHandler 先覆盖旧段，再希望后台补救。

每段至少保存 `segment_id/producer_id/producer_epoch/first_seq/last_seq/bytes/sha256/codec/created_at/archive_state`。索引记录时间窗和 trace／run 范围，内容引用使用受控 ID，不给浏览器任意本地路径读取能力。

业务日志优先按租户分段，共享宿主日志归独立系统治理域。混合租户的旧日志段不能仅对索引做 RLS 后整段下载；必须由服务端逐记录鉴权导出，普通租户不能取得原始混合段。哈希和段 ID 不是读取授权。

### 8.3 统一事件与关联字段

事件包至少包含：

```text
event_id, event_type, schema_version
tenant_id, trace_id, span_id, parent_span_id
workflow_release_id, run_id, node_instance_id, node_run_id, attempt_id
invocation_id, producer_id, producer_epoch, producer_seq
occurred_at, ingested_at, severity
policy_decision_id, approval_ref, code_manifest_ref
input_refs, output_refs, payload_ref, message_preview
```

字段按事件类型有条件必填：宿主健康日志未必属于某个节点，但必须有来源、时间和级别；节点事件不能缺 run／node／attempt。一次请求的 trace 和长期 run 分开：run 是永久关联主键，初版根 trace 贯穿短任务；后续调度／恢复产生的新 trace 通过 run 和因果引用关联，不能只靠一个长期 trace 字符串查所有历史。

进程内 ContextVar 不会自动跨队列和子进程，必须在 envelope 显式传递。重试使用新 attempt/span；运行身份不依靠文件名推断。事件传输可以重复，通过 `event_id` 或生产者序号去重；不要按时间戳去重或假定各进程时钟严格一致。

数据库为运行投影提供单调提交游标；原始日志保留各 producer 序号。两者职责不同，不伪造一个不存在的跨进程“真实发生全序”。需要回放时按已提交事件顺序与因果关系投影。

提交游标不能直接使用 PostgreSQL `nextval` 或 `max(id)`：低号事务可能晚于高号事务提交。应使用串行投影提交水位，或可证明安全的已确认连续窗口；存在序号空洞时不能推进到会跳过晚提交记录的位置。

### 8.4 插件日志协议与持久保障

- 保留 stdout 的受约束结果协议，诊断日志使用独立通道或结构化 stderr；宿主并行读取两路，避免缓冲区填满死锁。
- 分块写 spool，不一次性把全部输出捕获到内存；记录启动、PID／宿主实例、退出码、超时、取消和结果协议错误。
- 结束事件区分 `not_started / started / exit_unknown`。策略允许不等于执行成功，运行失败不能塞成“策略拒绝”。
- 进程崩溃、无效 JSON 和非零退出也必须能查到此前日志。达到输出预算时终止或背压，并保存已接收字节数、终止原因和明确边界，不返回“日志完整成功”。
- 关键调度状态在持久提交后才向外确认；日志先持久 spool 再异步归档。恢复按游标补交并去重。
- 磁盘满、spool 写失败或归档不可用时显示降级／暂停，停止新启动需留证节点。无法保证的硬件掉电尾部应在恢复后标明缺口，不能承诺软件可保存尚未落盘的数据。

“持久确认”必须定义刷盘屏障与最后确认水位：写入进程缓冲或操作系统缓存不等于持久 ACK。可采用配置化批量刷盘，但未过屏障的尾部不计入已确认范围；恢复只接纳完整记录和校验通过的段。容量耗尽时，对正在输出的子进程也要背压或受控终止，保留已接收／已持久字节边界，不能只停止新任务却任由存量任务继续丢日志。

现有桌面文件追踪过渡期也要处理文件身份、轮转、增量 UTF-8 解码、半行残留及读取 offset；不能继续只跟随当前 `.log` 文件和文件大小。完成 Collector 后桌面退出不影响 API／Worker／插件日志采集。

### 8.5 查询、完整性与恢复

trace 查询从“返回两个日志路径建议”升级为“真实事件／归档索引查询”，支持租户、run、node、attempt、级别、时间窗、关键词和分页游标。结果包含 `complete/partial/unavailable`、已入库水位、缺失来源和归档状态；查询成功但没有记录与数据库故障不是同一个结果。

完整性判据限定为**指定采集策略、指定水位、已封存区间**：run 登记预期 producer，结束时各 producer 提交 seal，包含最后序号、持久确认水位与字节数；汇总核对日志段、收据和缺口。进程崩溃缺 seal 或尾部范围未知时，显示 `partial` 并标记 `unknown_tail`，不能仅因眼前序号连续就判定全部完整。尚在运行的区间显示当前持久水位，不提前作最终完整性承诺。

M9 哈希锚定继续引用原账本，并纳入日志段 manifest 与代码／产物清单。哈希链可验证已纳入内容，不证明没有漏采，也不抵御拥有全部存储权限的管理员重写；更高强度要求独立锚定或不可变存储专项建设。

备份不能只有 PG：需闭合数据库快照、事件水位、产物、日志段、工作流发布、插件包和代码清单之间的引用。恢复演练需验证哈希、权限、引用可读与 trace 下钻，记录 RPO/RTO；“恢复后有多少张表”不算完整恢复验收。

## 9. GUI 设计：一个任务，一个可追踪的运行画布

```text
┌──────────────────────────────────────────────────────────────┐
│ 工作区 / 目标输入 / AI 自动组网 / 校验 / 运行或暂停 / 历史版本  │
├─────────────┬───────────────────────────────┬────────────────┤
│ 插件与模板  │ 目录图 / 草稿图 / 运行图        │ 节点检查器     │
│ 数据文件夹  │                               │ 参数与端口     │
│ 多集群导航  │  节点—端口—连线—折叠子流程    │ 输入输出预览   │
│ 搜索与缺口  │  平移 / 缩放 / 定位 / 小地图   │ 策略与证据     │
├─────────────┴───────────────────────────────┴────────────────┤
│ 运行队列 / 时间线 / 所选节点日志 / 数据流收据 / AI 规划记录     │
└──────────────────────────────────────────────────────────────┘
```

画布默认由 AI 排布；用户可改参数、锁定节点、指定必选／禁用插件，或手工拖线。修改产生新草稿；运行中的定义不变。AI 改图展示差异和原因，不自动覆盖用户刚修改的 revision。

节点展示插件版本、实际绑定状态、资源池、输入输出端口、运行／审批／日志状态。点击边查看来源节点、产物类型／大小／哈希、交接时间和消费结果。边动画仅在收到真实交接事件后出现，不能用动画冒充已经传输的数据。

右侧表单来自插件声明的参数 Schema 和受限 UI hints，由宿主已登记组件渲染。插件可声明字段、分组、表格列和产物预览方式，不加载任意 JS、Electron API 或远程页面。框架保持业务中立；具体审计／量化／AIOps 规则属于插件和领域服务。

交互要求：

- 左侧目录、右侧检查器、底部日志分别可滚动；中间画布滚轮缩放并有重置视角。光标在表单或日志时滚轮不被画布抢走。
- 保留窗口最大化、最小化、关闭按钮；关闭 GUI 不默认终止后台运行，需清楚告知运行仍在继续。
- 全中文空态、加载态、错误态；明确区分未安装、未登记、无权限、等待数据、等待审批和运行异常。
- 历史回放只重建画面，不调用插件、不重新写业务数据。“重跑”是另一个经授权的新 run。
- 清屏仅清当前视图筛选／缓存，不删除日志或证据。
- 使用“快照水位 + after_seq 补拉”，避免快照覆盖新事件；断线显示滞后时间，重连不重新执行。
- Zustand 按目录、草稿、运行和日志拆分；切换租户取消旧请求，旧响应不得写回新工作区。
- 图实例保持稳定；容器 ResizeObserver 驱动重排，隐藏页暂停不必要动画。日志分页／窗口化，不把全部历史装入前端。

桌面通过现有 contextBridge 与精确 IPC 白名单访问控制平面。未来事件订阅由主进程托管，先用分页补拉验证正确性，再增加长连接；无论传输方式如何，都必须从持久游标恢复，renderer 不获得任意地址访问能力。

## 10. 插件怎么写、先做哪条业务链

### 10.1 先盘活 23 个实现包，不急着增加数量

| 领域 | 当前实现映射数量 | 当前可复用插件 ID |
| --- | --- | --- |
| 知识 | 4 | `knowledge.document-ingestion`、`knowledge.entity-relation-candidate`、`knowledge.graph-proposal-builder`、`knowledge.retention-recommendation` |
| 审计 | 7 | `audit.ledger-quality`、`audit.journal-anomaly`、`audit.investigation-plan`、`audit.finding-draft`、`audit.evidence-lineage`、`audit.workpaper-export`、`audit.report-draft` |
| 量化 | 5 | `quant.snapshot-guard`、`quant.factor-compute`、`quant.simulated-backtest`、`quant.experiment-evaluator`、`quant.research-note-draft` |
| AIOps | 7 | `aiops.alert-correlation`、`aiops.alert-triage`、`aiops.rca-ranker`、`aiops.playbook-proposer`、`aiops.recovery-verifier`、`aiops.ticket-draft`、`aiops.postmortem-draft` |

这里的数量按源码映射统计，不代表业务深度相同。确定性规则、模拟回测、模板草稿与真正模型推理要分别标注；“有输出 JSON”不等于审计、量化或根因判断已达到生产准确率。

### 10.2 首条真实端口闭环：日记账异常 → 调查计划 → 发现草稿

下面使用真实已有插件和契约名称；短端口名是待补的端口别名，不是声称现有运行时已经支持该 DAG。

```text
宿主输入：journal-artifact-ref@1
               │
               ▼
audit.journal-anomaly@0.1.0
               │ anomaly-candidates@1
               ├─────────────────────────────────┐
               ▼                                 │
audit.investigation-plan@0.1.0                    │
               │ investigation-plan-draft@1      │
               ▼                                 ▼
             audit.finding-draft@0.1.0（两个明确输入）
                               │ finding-draft@1
                               ▼
                     宿主保存受治理的草稿产物
```

必须验证 `finding-draft` 同时收到指定异常集合和对应调查计划，且能追溯同一输入快照。这条链天然覆盖 fan-out 与多输入汇合，比单纯串联两个插件更能检验真实数据流。

调查计划可选的 `audit-evidence-index` 按实际参数 Schema 显式处理；缺少证据时输出待补证据，不能造证据。进一步流向 `audit.workpaper-export`／`audit.report-draft` 前，必须形成真实已确认的 `finding-set@1`，不能把 `finding-draft@1` 冒充已确认集合。当前 `packages/audit/pipeline.py:121` 的确认服务接收数据库异常候选 ID，返回 finding ID，尚未见插件草稿直接接入与 finding-set 物化闭环。因此“草稿候选受治理入库／映射 → 人工确认 → 已确认集合不可变物化”是待补的领域服务适配，不是现成可用链路；首轮验收止于发现草稿。

`audit.ledger-quality` 可作为独立质量支路和后续控制门；若要将其候选汇入异常集合，单独设计审核后的转换器，保留规则类别、证据和不确定性，不随手改契约名。

### 10.3 真正缺少的是窄适配能力

优先根据上述链的编译缺口补齐：宿主 ArtifactRef 到旧插件参数的适配、经过审核的候选格式转换、集合拆分／聚合、数据库快照物化、必要的表格预览。每个转换器都应有固定版本、Schema、来源保留规则、正反样本和失败语义。

通用控制节点（输入、审批、条件、join、子流程、产物输出）属于宿主编排能力，不伪装成可自行授权的业务插件。真实业务插件原则上只做一项稳定能力；声明资源和输入输出，由宿主调度、取数、持久化、记日志。

每个插件交付包继续遵守既有 UPP：协议、manifest、runtime binding、运行实现、输入输出 Schema、黄金样本、单元／契约／策略／端到端测试。新增端口与日志协议需版本化兼容旧包；不能直接修改已发布包后沿用原 SHA。

后续领域链均先编译验证契约，再组合：知识链终止于图谱提案待治理；量化链保持点时数据与仅模拟；AIOps 链终止于修复／工单草稿及模拟核验，不连接真实基础设施。

## 11. 数据库与接口增量设计

不新建第二套业务数据库，不迁移到新数据库产品。以下为逻辑模型候选；实施前与现有表逐列比对，优先加列、关联和投影，避免重复维护真相。

| 逻辑对象 | 复用／拟落点 | 关键约束 |
| --- | --- | --- |
| 版本化节点定义 | 扩展 topology 蓝图、契约、发布快照 | 定义快照哈希；runtime 状态与协议 lifecycle 分开。 |
| 草稿与补丁历史 | topology 下工作流草稿／修订／布局对象 | `(tenant_id, workflow_id, revision)` 唯一；CAS；回滚产生新修订。 |
| 可执行发布 | 复用 topology 发布与 control 工作流版本的显式关联 | 一个执行哈希锁住完整 IR，不查询当前蓝图补历史定义。 |
| 运行与节点尝试 | control 作为执行权威，关联既有 topology execution_runs／ledger | run、node、attempt 分层；fencing；逻辑操作幂等；历史记录保留。 |
| 端口产物绑定 | 扩展现有 artifact 元数据和节点输入输出引用 | tenant＋run＋node＋port；生产 attempt；SHA；提交状态；禁止跨租户外键错配。 |
| 运行事件与订阅投影 | 复用 outbox，增加统一 run event 及游标投影 | 追加事件；producer 去重；提交与投递分开；可重建快照。 |
| 日志分段与 trace 索引 | ops 下专用 log segment／cursor／trace reference 元数据 | 原文不塞单行 JSONB；归档状态、哈希、覆盖率、最后序号。 |
| AI 规划记录 | 扩展 topology.planning_intents 的关联记录 | 模型／提示版本／检索证据／各版草稿／编译结果独立引用；原记录不覆盖。 |

所有含租户数据的表启用并验证 RLS／FORCE RLS，应用角色不得 BYPASSRLS。租户上下文来自已验证身份及其授权映射，不能把任意请求头的租户值本身视为授权。引用表使用租户一致性约束，不能只在 UI 过滤。证据事件与历史不硬删；草稿回收、保留策略和清屏不是删除审计历史的授权。

索引优先覆盖 `(tenant_id, run_id, sequence)`、`(tenant_id, trace_id, time)`、`(tenant_id, node_run_id, attempt)` 和队列状态／可执行时间；追加大表根据实测增长再决定时间分区，初版不要因想象中的海量引入复杂分片。

未来 API 建议能力分组：定义查询、草稿补丁、编译预览、发布、运行提交／查询／暂停／取消、运行事件补拉、节点产物预览、日志查询／归档导出。路径在契约阶段统一确定并同步 Electron 白名单，不在本文把拟议路径写成已经可调用的接口。

所有读取经过租户和相应 read 策略；写入绑定 trace、逻辑操作幂等键及内容指纹。运行提交返回持久 run ID，不让 HTTP 请求长时间等待整链结束。暂停／取消表示请求已接受，实际终态由运行事件确认。

## 12. 开发路线：一次一个里程碑，先测再写

CW 编号只服务本方案。开始某个里程碑时，应先明确该轮范围并更新项目阶段说明；本文件不授权实现后续所有能力，不改变生产执行边界。

| 里程碑 | 交付与主要代码落点 | 必须通过的退出条件 |
| --- | --- | --- |
| **CW0：基础真实性修复** | 租户化 trace/code-map 查询、失败证据短事务、真正快照锁；统一目录统计和旧文档状态说明。落点：API、topology service、runner、桌面目录模型。 | 两租户隔离；数据库故障不伪装空成功；故障后已提交账本仍在；目录修改不改变旧发布解释。 |
| **CW1：端口契约与执行 IR** | 先补 Schema／样本；稳定命名端口、GraphPatch／Draft／Release、确定性编译器；明确旧链适配。 | 缺输入、错契约、循环、重复 node_instance_id／同节点重复 port_id、超预算、不支持字段均有失败测试；同插件多实例合法；同输入可复现哈希，布局不改哈希。 |
| **CW2：日志持久底座** | 独立 Collector、结构化 envelope、stdout/stderr 分流、spool／segment／归档索引与查询；先于扩大自动执行。 | 轮转与重启连续性、UTF-8 半行、重复投递去重、GUI 关闭继续采集、日志写失败暂停准入。 |
| **CW3：统一 DAG 执行闭环** | control 调度器输入映射、真实插件 Adapter、短事务节点提交、outbox、心跳续租／恢复、重试和资源预算。 | 首条日记账链真实多输入通过；worker kill／迟到写回／重复提交可控；每条数据边和每个 attempt 均可追溯。 |
| **CW4：真实桌面画布** | 服务端定义投影、二维画布、检查器、历史／队列／日志面板；拆 App 状态；主进程订阅与幂等重试。 | 打包版截图与交互：滚轮、最大化、缩放、选边查产物、租户切换、断线补拉；画布与持久 run 状态一致。 |
| **CW5：AI 自动组网** | 本地模型适配、能力召回、结构化草稿、编译反馈修订、预算和模板复用；不新增执行权限。 | 模型生成的图确实通过编译并驱动 CW3；未知插件、提示注入、越权数据、修订超限均安全失败；不暗中回退成假运行。 |
| **CW6：综合验收与长期运行** | 多领域小样本演示、真实持续运行、故障注入、备份恢复与证据导出。 | 先完整 24 小时实测，再开展 7 天观察；报告真实起止时间、成功率、P95、资源曲线、日志缺口、恢复结果与剩余限制。 |

不建议先继续堆插件或先做大型炫酷画布。**下一轮最合适的是 CW0：先用回归测试锁定发布快照、事务证据和跨租户日志问题。** 此后才把画布连接到可信的运行事实。

同一里程碑内可安排三个开发 Agent 分工：契约／后端、桌面／投影、测试／故障注入；共享 Schema 与接口冻结后再并行，避免同时改 API 大文件。审查 Agent 不用实现 Agent 的“自报全绿”代替运行测试。

建议逐步将 API 路由按 topology／runs／observability 拆分，桌面按 Canvas／Runs／Logs 拆分；拆分与功能改动分批提交，保持现有精确路径和响应兼容，避免大范围重构掩盖行为变化。

## 13. 验收矩阵：没有这些证据就不能写“完成”

所有数值是**待验证目标或测试规模，不是当前性能成绩**。初次性能运行记录硬件、数据规模和冷／热缓存，之后再冻结基线。

| 类别 | 最小验收用例 | 通过证据 |
| --- | --- | --- |
| 目录真实性 | 本地 23 个实现映射与服务端实际可用项分别展示；移除测试绑定 | 画布不能把缺失绑定显示成可运行；不要求每个租户都恰好有 23 项。 |
| 发布不漂移 | 发布后修改蓝图、契约、参数、插件包 | 旧运行仍使用冻结内容或在包缺失／篡改时拒绝，不能悄悄使用最新版。 |
| 数据流 | A 同时喂给 B、C，C 再接 B；另测两独立生产者汇合及同插件双实例 | 各端口 SHA 与预期生产者一致；断一条必填边必须失败。 |
| 事务耐故障 | 第一节点已提交后杀宿主／触发后续异常／断 DB | 已提交 run、attempt 与产物证据仍可查；恢复不重复提交逻辑效果。 |
| 幂等与租约 | 网络超时重发、双 worker 认领、过期旧 worker 迟到 | 同逻辑操作只有一个有效结果；旧 fencing 提交被拒并留痕。 |
| 日志完整 | 强制多次轮转，超 4000 字、跨块中文、stderr、超时、非零退出、无效 JSON | 原文／字节边界与序号核对；退出 GUI 后仍采集；缺口或截断明确标记。 |
| 日志故障 | 模拟 spool 满、归档失败、索引延迟、文件不可写 | 告警与背压；不把未留证运行显示为完整成功。 |
| 持久确认 | 分别在日志写入后确认前、持久确认后杀进程 | 已确认记录可恢复；未确认尾部明确标注；缺 seal 不判最终完整。 |
| 补拉游标 | T1 低号事务阻塞，T2 高号先提交并被读取，随后 T1 提交 | T1 晚提交记录仍能补拉；快照／实时合并不漏不重。 |
| 权限 | 两租户同 trace 检索、无策略读取、过期 artifact、越界路径／符号链接 | 不跨租户泄露、不越界读文件；拒绝事件可追踪。 |
| 归档权限 | 两租户同 producer 同时产生日志，再做查询与归档导出 | 不能因共享日志段泄露另一租户原文；系统段读取有独立授权。 |
| AI 组网 | 至少 20 个固定业务意图，含含糊、缺插件、错数据域与恶意文档指令 | 有目标覆盖和产物质量检查；工具执行仅来自合法计划；记录每次修订与失败原因。 |
| GUI | 1280×720 与常用大屏、最大化／恢复、所有面板滚轮、关闭重开、API 重启 | 打包 Electron 实际截图与交互断言；不是只测开发页或静态渲染。 |
| 性能 | 从 50／150 可见节点、500 条边测试；更大图先折叠，日志 10 万条后分页查询 | 无全量加载；交互和查询延迟有实测。图规模若超过当前上限，先编译拒绝或拆子流程。 |
| 长期运行 | 独立测试租户真实持续 24 小时；长任务、重启、退避与队列积压 | 真实时长与心跳曲线；运行事件计数守恒；不能用三轮循环冒充 24 小时。 |
| 备份恢复 | 在独立目标环境恢复 DB＋日志＋产物＋版本包 | 哈希和引用闭合、RLS 有效、历史 trace 可下钻、RPO/RTO 报告。 |

测试数据优先在 `audit_network_test` 合成并使用每轮独立命名空间；如需参考 `G:\数据`，只读抽样并记录来源，样本输出写项目测试产物目录。不得清空主库或其他数据库，也不能通过不断提高列表 limit 来掩盖历史测试数据污染。

每个实现里程碑运行契约／单元／集成／对应 E2E，以及 Python 静态检查和桌面类型检查；修改 GUI 时增加生产构建与视觉测试。真实模型、MinerU、24 小时测试等 opt-in 检查，未运行就写“未运行”，不能把 skipped 算成通过。

## 14. 给后续执行 AI 的任务约定

执行前先读 `AGENTS.md`、本文、当前 `docs/status.md`、对应 M 文档和涉及代码。先重新确认工作区变更、当前 API 契约及迁移头，不覆盖其他 AI 或用户已有修改。

每轮仅选择一个 CW 里程碑，按以下交付：

1. 列出本轮范围、现有行为、契约差异和不做的事项。
2. 先新增会失败的回归／契约测试，证明缺口真实存在；再实施最小改动。
3. 数据库迁移显式执行在经确认的本项目测试库，应用启动不自动迁移；保留可恢复方案。
4. 验证正向、拒绝、重试、崩溃、跨租户和旧版本兼容；运行命令与结果写入验收记录。
5. 交付修改清单、测试证据、未运行项、剩余问题和下一轮入口；更新 status 但不混用 R／M／Phase 编号。

禁止以静态演示图替代真实目录，以“前一个输出”替代端口输入，以 `release_id` 替代完整快照，以路径提示替代查到日志，以缓存／模拟输出替代真实执行，以绿色测试数量替代真实持续运行证据。
