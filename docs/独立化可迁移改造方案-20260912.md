# 独立化 / 可迁移改造方案（2026-09-12）

**目标**：把项目复制到另一台电脑后，能自己把环境拉起来 —— 没有环境就自动装，装不了的说清楚缺什么。

**已确定的前提**（用户选择）：
1. 分发方式 = **离线打包拷贝**（不做 GitHub 拉取）
2. PostgreSQL = **检测 + 指引安装**（不尝试全自动安装）
3. 本轮 = **只出方案，不改代码**

## 一、直接回答「项目是不是只能用虚拟环境」

**事实上在用，但没有被约束。** 而且离「复制过去能自己拉起」还差得远。

### 做对的部分（已核实）

| 项 | 实测值 |
| --- | --- |
| 虚拟环境 | `.venv`，uv 0.11.26 创建 |
| Python | 3.12.12，**uv 自己管理的 CPython**（不依赖系统 Python） |
| 隔离 | `include-system-site-packages = false` ✅ |
| 依赖锁定 | `uv.lock`（355 KB）存在 |
| 项目安装方式 | editable（`__editable__.audit_network-0.1.0.pth`），venv 内 51 个包 |
| uv 可用性 | 本机 PATH 上 `uv 0.11.26` |

### 没做对的部分（已核实，逐条有据）

| # | 问题 | 位置 | 影响 |
| --- | --- | --- | --- |
| 1 | **启动脚本用裸 `python`** | `scripts/run-dev.ps1:12` | 走 PATH 上任意 Python，**完全不碰 `.venv`** |
| 2 | **fallback 写死本机路径** | `scripts/start-brain.ps1:24` → `C:\Users\he\...Python311\python.exe` | 换机器永不命中 |
| 3 | **Anaconda 路径写死** | `scripts/init-test-postgres.ps1:22`、`scripts/register-phase1-plugin.ps1:19` → `C:\ProgramData\Anaconda3\python.exe` | 而 `start-brain.ps1` 自己的注释写着「Anaconda3 is not used anymore」——脚本之间自相矛盾 |
| 4 | **PostgreSQL 客户端全写死** | `backup-db.ps1:26`、`restore-db.ps1:24-27` → `C:\Program Files\PostgreSQL\16\bin\*` | 对方装 17/18 或装在别处 → 直接抛错 |
| 5 | **外部数据根写死** | `G:\数据`（`AUDIT_PLUGIN_READ_ROOTS` / `EXTERNAL_DATA_ROOT` 默认值） | 对方无 G 盘 |

| 7 | **无任何环境自举** | 全仓 grep 不到 `uv sync` / `uv venv` / `python -m venv` | 新机器没人替你建环境 |
| 8 | **文档无安装章节** | `README.md` 只有「启动桌面中枢」，`uv` 一次未提 | 对方不知道要装 uv |

## 二、核心障碍：venv **不能直接拷贝**

这是整个方案的关键，也是最容易被想当然的地方。实测证据：

```
$ cat .venv/pyvenv.cfg
home = C:\Users\he\AppData\Roaming\uv\python\cpython-3.12-windows-x86_64-none   ← 本机专属绝对路径

$ grep -oE "[A-Za-z]:[\\/][^'\"]*audit_network[^'\"]*" \
       .venv/Lib/site-packages/__editable___audit_network_0_1_0_finder.py
D:\\pythonpro\\audit_network\\apps        ← editable 安装嵌了本机项目路径
D:\\pythonpro\\audit_network\\packages
D:\\pythonpro\\audit_network\\plugins
```

外加：Windows venv 的 `Scripts\*.exe`（`alembic.exe`、`uvicorn.exe` 等）是启动器，**内嵌 python 解释器的绝对路径**。

**结论**：把 `.venv` 拷过去一定跑不起来（即使目标机装了同样的 Python，`home` 路径也不存在）。
离线包必须带 **Python 运行时 + wheels**，在目标机上**重建** venv。

## 三、离线依赖清单（按能否自动装分类）

### A. 可以随包自带、目标机零下载

| 组件 | 体积（实测） | 说明 |
| --- | --- | --- |
| `uv.exe` standalone | ~30 MB | 单文件，无需安装 |
| CPython 3.12 运行时 | ~50–70 MB | 用 python-build-standalone 或 uv 管理的 CPython，整目录随包 |
| Python wheels (wheelhouse) | ~100–150 MB | 关键：`psycopg2-binary` 是 `win_amd64` 平台 wheel，**必须同平台** |
| `desktop/node_modules` | **647 MB** | 含 `electron/dist/electron.exe`（实测存在）→ 直接打包，跳过 `npm install` |
| 根 `node_modules` | 49 MB | 同上 |

**关于 Electron**：`npm install` 时 `electron` 包会**从 GitHub 下载二进制**，离线必失败。本机已有
`%LOCALAPPDATA%\electron\Cache`，但最省事可靠的方案是**直接打包 `desktop/node_modules`**（647 MB 换零风险）。

**关于 wheelhouse 生成**（打包机上执行一次；第一条命令**已实测通过**，输出 33 个包）：

```powershell
# 已实测：需带 --no-emit-project，否则会输出 `-e .`，pip download 无法处理
uv export --format requirements-txt --no-hashes --no-emit-project > requirements-lock.txt

# 待 P2 实做时验证（标准 pip 用法，需 --only-binary=:all: 才能配 --platform）
pip download -r requirements-lock.txt -d wheelhouse `
  --platform win_amd64 --python-version 3.12 --only-binary=:all:
```

### B. 装不了、只能检测 + 指引

| 组件 | 实测 | 难点 |

| **pgvector** | 已装 0.8.0 | ⚠️ **EDB 官方安装包不含 pgvector**，Windows 需单独装（预编译 zip 或源码编译）——**这是最大的坑** |
| `pgcrypto` / `pg_trgm` / `ltree` | 已装 1.3 / 1.6 / 1.2 | 随 PostgreSQL 主包提供，通常无需额外操作 |

> **更正一处旧说法**：此前（含我在别处的表述）提到需要 **pgRouting** —— 经核实**本项目根本没用到**
> （全仓无 `pgr_*` 函数调用、文档亦未提及）。实际必需扩展只有上表四个。

## 四、打包清单

**总目录 1.3 GB**，实测构成：

| 项 | 体积 | 是否入包 | 理由 |
| --- | --- | --- | --- |
| `.venv/` | 126 MB | ❌ | 不可迁移，目标机重建 |
| `.data/` | 157 MB | ❌ | 运行态（日志/证据/临时产物），且已在 `.gitignore` |
| `.git/` | 13 MB | ❌ | 若做本地提交可另存 |
| `desktop/node_modules/` | 647 MB | ✅ | 换零下载，避免 Electron 离线失败 |
| `node_modules/` | 49 MB | ✅ | 同上 |
| `desktop/out/` | 5.4 MB | ❌ | 构建产物，目标机重建 |
| `desktop/out.phase3-previsual-20260904/` | 5.0 MB | ❌ | ⚠️ **未被 `.gitignore` 覆盖**，会误入包 |
| `desktop/out.phase4-previsual-20260904/` | 5.0 MB | ❌ | 同上 |
| `cankao/` | 32 MB | ❌ | 参考料，已 gitignore |
| 源码（apps/packages/plugins/等） | ~290 MB | ✅ | |

**离线包净体积估算**：源码 ~290 MB + node_modules 696 MB + 运行时 ~150 MB ≈ **1.1 GB**。

若嫌大，可把 `node_modules` 换成「npm 离线缓存 + Electron 缓存」，但复杂度显著上升，不推荐首选。

## 五、自举流程设计（`scripts/bootstrap.ps1`）

目标机上双击一个入口，按顺序做以下事，**每步失败都给可执行的下一步**：

```
[1] 检测 uv        → 没有则用随包的 uv.exe；都没有则提示放置路径
[2] 检测 CPython   → 用随包运行时；或 uv 本地已有 3.12；否则提示离线包缺失
[3] uv sync --offline --find-links wheelhouse/   → 建 .venv 并装依赖（含 editable 项目）
[4] 桌面依赖       → 若随包带了 node_modules 则跳过；否则 npm ci --offline
[5] 复制 .env.example → .env（若不存在）
[6] 检测 PostgreSQL：
      · 探测 psql：Get-Command psql → 多版本 glob C:\Program Files\PostgreSQL\*\bin\psql.exe
      · 版本 ≥ 16
      · 四个扩展可用性：SELECT name FROM pg_available_extensions WHERE name IN
        ('pgcrypto','pg_trgm','ltree','vector')
      · 任一缺失 → 打印分步安装指引（含 pgvector 单独安装的说明），**不继续**
[7] 建库建角色 + alembic upgrade head
[8] 检活：/health + migration head，输出「就绪」或「缺什么」
```

**同时要做的代码改造**（消除硬编码，否则自举在目标机仍然会断）：

| 改造 | 从 | 到 |
| --- | --- | --- |
| 统一解释器 | 各脚本混用裸 `python` / Anaconda / 硬编码 Python311 | 一律用 `<项目根>\.venv\Scripts\python.exe`，缺失则明确报错 |
| psql 探测 | `C:\Program Files\PostgreSQL\16\bin\psql.exe` | `Get-Command psql` → 多版本 glob → 报错并给指引 |
| 外部数据根 | 默认 `G:\数据` | 默认空 / `.data\drop`，由 `.env` 显式配置 |
| MinerU | 保留 env 覆盖，默认值改空 | 未配置时明确提示「该能力未启用」 |
| 文档 | README 无安装章节 | 补「前置要求 / 离线安装 / 常见故障」三节 |

## 七、风险与未决问题

| 风险 | 说明 | 建议 |
| --- | --- | --- |
| **pgvector 在 Windows 上难装** | EDB 安装包不含它，需单独取预编译包或自行编译。这是 P3 最可能卡住的地方 | 先在一台干净机器上单独验证 pgvector 安装路径，再写进指引 |
| **python-build-standalone 与 psycopg2-binary 的兼容** | 平台 wheel 与运行时必须匹配（均为 win_amd64、CPython 3.12） | wheelhouse 生成时固定 `--platform win_amd64 --python-version 3.12` |
| **Electron 647 MB 让包变大** | 接受，或用缓存方案换取体积 | 首选直接打包 |
| **目标机 PostgreSQL 数据目录** | 新机器要初始化 cluster、建角色、设密码 | 自举脚本里给出 `initdb` + `CREATE ROLE` 的具体命令 |
| **清理脚本里的 Anaconda 依赖是否有隐含用途** | 两处脚本仍在用 Anaconda，需确认不是历史包袱 | P1 改造时逐个验证 |
| **`.data/` 里 157 MB 历史数据不随包** | 目标机是干净库，无历史证据 | 如需迁移历史，另做数据库 dump/restore（已有 `backup-db.ps1` / `restore-db.ps1`，但它们的路径要先按 P1 改造） |
