## 1. 总体结论（TL;DR）

项目在**只读展示与静态演示数据**层面是完整的，但离用户提出的三条标准差距明显，核心结论：

1. **数据支撑（不合格）**：演示数据全部为一次性脚本/测试污染产物，无重复可执行的供给管线；数据是静态快照，24 小时后仪表盘数字不会变化；且状态自相矛盾（missions 全部 planned、workflows 全部 pending，但 tasks/agents 全部 completed —— 真实调度器永远产生不出这种状态）。
2. **下钻链路（半通）**：UI→API→服务→数据行 这条线基本打通（血缘端点、evidence chain、operations 四级下钻都在）；但**数据行→日志层断裂**（日志不含 trace_id，无法反查），**日志/数据→代码层完全缺失**（无源码映射、无服务版本指纹），`/health` 不能当探针，日志无轮转无保留。
3. **24×7 无人值守（不成立）**：无进程监督（API/Worker 挂掉无人拉起，status.md 已记录"长时间后台运行后被环境回收"）；无任务执行循环（调度器只是状态库，mission 永远不会推进）；调度无租约/心跳，崩溃即永久卡死；无定时任务引擎；无告警通道；审计表以每天 3 万行的速度无上限增长。

按对 24×7 目标的阻断程度分级：**P0 级缺陷 6 项、P1 级 10 项、P2 级 12 项**（见第 4 节矩阵与第 5 节路线图）。

### A. 数据支撑类缺陷（D）

#### D1. 【P0】演示数据不可复现：无数据供给管线，全新环境 = 空 UI

- **现象**：主库当前有 28 missions、43 alerts、94 backtests 等演示数据，但**没有任何迁移种子或可重复执行的 seed 脚本**能重新生成它们。`migrations` 只种 iam.tenants/projects、policy.policy_sets、topology.plugin_clusters 等骨架。
- **证据**：`grep "INSERT INTO (control.missions|aiops.alerts|quant.backtests|audit.engagements|semantic.documents)" migrations/` 无命中；演示数据来自已被删除的 `.data/m10_seed_backfill.py` 等一次性脚本与测试污染（见 D4）。
- **影响**：换机器/重建库/回滚后，所有桌面视图（星图、AIOps、量化、审计）回到空态；"每个功能都有数据支撑"无法成立，24×7 无人值守的第一前提（数据供给）缺失。
- **建议**：新增 `scripts/seed-demo.ps1|py`（幂等、带租户上下文、可重复执行）作为演示数据唯一权威入口；数据生成逻辑收敛到 `packages/demo/`（当前空），并用测试覆盖"空库→seed→所有 UI 端点非空"。

#### D2. 【P0】演示数据是静态快照，24×7 下不会产生任何新数据

- **现象**：没有任何进程或定时任务在持续生成告警/事件/回测/审计数据；AIOpsEngine.ingest_alert 只被测试调用。Worker 心跳实测 `published=0 processed=False`。
- **证据**：`packages/aiops/engine.py` 的 ingest_alert 无生产调用方；`apps/worker/local.py` 主循环不含数据生成逻辑；全部 28 missions 状态为 `planned` 且无人推进（见 O2）。
- **影响**：一台机器跑 24 小时，星图/告警/事件数字纹丝不动——这不是"自动运行"，是"静态展示"。无人值守场景下用户无法判断系统是否还活着（数据活性为零）。
- **建议**：在 Worker 或独立 daemon 中加入**数据生成器**（按周期合成新告警→incident→修复提案→ChangeRequest→canary 执行→验证/回滚，全部走 Policy Gateway + trace_id + 幂等键，与真实执行共用同一套代码路径），形成可观测的"数据心跳"。

#### D3. 【P0】演示数据状态自相矛盾（planned mission + completed tasks）

- **现象**：28 missions 全部 `planned`、27 workflow_runs 全部 `pending`，但 81 task_runs 与 81 agent_runs 全部 `completed`。28 个 mission 只有 27 个 workflow_run，存在孤儿 mission。
- **证据**：`SELECT m.status, w.status ... JOIN` 实测：`planned|pending|27` 组合下挂 81 个 completed tasks；`grep "UPDATE control.(workflow_runs|missions) SET status"` 0 处。
- **影响**：任何"按状态流转推导数据"的下钻/统计都会得出错误结论；星图"运行中/已完成"口径失真；且该状态**无法通过系统自身 API 复现**（系统根本写不出"planned mission + completed task"的组合）。
- **建议**：① 先补齐状态机终态转移（见 D3b/L 系列）；② 修正 seed 数据，使状态组合与真实流转一致；③ 加数据一致性断言测试（mission/workflow/task/agent 状态链）。

#### D4. 【P1】审计/策略日志无保留策略，6 天膨胀至 6.3 万行

- **现象**：policy.decisions + policy.tool_calls 在 local-dev 租户下已达 63,352 行；9/7 一天 +28,377、9/8 一天 +33,165，日均 3 万行。
- **证据**：按日 GROUP BY 实测（见 0.1）；无分区、无归档、无保留期配置；`policy.policy_sets` 222 行 vs 迁移种子约 16 行，多出的约 200 行来自脚本/测试在**主库**反复写入。
- **影响**：24×7 运行一个月 ≈ 90 万行；磁盘持续增长，查询变慢，无人值守下无预警即爆盘。
- **建议**：decisions/tool_calls 按月分区 + 归档任务（保留期例如 90 天）+ 磁盘水位告警；禁止测试/演示脚本直连主库写策略（走专用测试库 + 隔离租户）。

#### D5. 【P1】事件总线存在孤儿事件（指向已删除任务的 task.ready）

- **现象**：outbox 157 行中含 `task.ready` 事件，其 aggregate_id 对应的 task_run 已被删除（missions 被清理后残留）；inbox 52 行无人消费也无过期机制。
- **证据**：outbox 采样 `task.ready` 事件存在且 `published_at` 已置位；对应任务行不复存在；worker 无消费逻辑（published=0）。
- **影响**：一旦未来接入任务执行器，孤儿事件会导致"处理不存在任务"类错误；inbox 无限累积成为隐藏存储增长点。
- **建议**：事件清理/归档任务；task.ready 消费端做存在性校验；写"孤儿事件检测"作为健康检查项。

#### D6. 【P1】演示数据只有成功态，无失败/超时/漂移样本

- **现象**：alerts 41 low / 1 medium / 1 high（无 critical、无恢复）；incidents 69 全部 open（无 resolved）；findings 35 全部 medium；backtests 94 全部 completed；task/agent_runs 无 failed。
- **证据**：0.1 状态分布实测；status.md 亦承认"当前模拟数据无失败任务"。
- **影响**：星图"红色闪光"、告警联动、回滚/验证失败路径等代码已就绪，但**无数据可验收**——这是"每一层都能展开"的死角（有代码无数据）。
- **建议**：数据生成器（D2）内置故障注入：失败任务、超时任务、medium/critical 告警、回滚记录、验证失败样本，让每条失败路径都有对应数据与日志可下钻。

#### D7. 【P2】测试库污染与租户累积

- **现象**：`audit_network_test` 中 iam.tenants 累积 563 行（每次测试新建租户不清理）；部分测试/脚本曾直连主库（63K decisions 的来源之一）；CI 中 `DATABASE_URL == TEST_DATABASE_URL`（同一库，无隔离）。
- **证据**：`SELECT count(*) FROM iam.tenants`（test 库）= 563；`.github/workflows/quality.yml` 的 pytest 环境变量两个 URL 相同。
- **影响**：测试与演示数据互相污染；无法区分"演示数据"与"测试残留"，削弱数据可信度。
- **建议**：测试基建：test 库租户复用/清理钩子；CI 分离 TEST_DATABASE_URL；演示数据只来自 seed 脚本（D1）。

### B. 下钻链路类缺陷（L）

#### L1. 【P0】日志层与数据层断裂：日志不携带 trace_id

- **现象**：trace_id 存在于请求头、policy.tool_calls.decisions、workflow_runs/task_runs 等数据行，但 **api.log / worker.log 的日志行格式不含 trace_id**，无法从任意数据行反查到产生它的日志。
- **证据**：api/main.py 日志格式 `%(asctime)s %(levelname)s %(name)s: %(message)s`（无 trace）；trace 中间件只注入请求头与响应头；桌面统一日志窗口按文件+级别展示纯文本行，无 trace 过滤。
- **影响**：用户要求的"每一层展开到底层日志层"核心断裂——数据行→日志行需要人工按时间盲猜。
- **建议**：日志格式加入 `trace_id`（middleware 注入 ContextVar + 格式化器读取）；uvicorn.access 同理会话 ID；桌面日志窗口增加按 trace_id 过滤。

#### L2. 【P0】代码层下钻完全缺失

- **现象**：UI/数据/日志三层之间没有任何到**代码层**的映射：无源码文件/行号引用、无服务版本指纹（除 backtest/plugin 的 code_sha256 外）、无"跳转到产生该数据的代码"能力。
- **证据**：全仓无 source-map/lineage-to-code 机制；observability 包为空（见 L6）。
- **影响**："展开到底层代码层"无法实现；排障只能靠人工翻代码。
- **建议**：最低成本方案：为每个服务/插件记录 `code_sha256` + 版本号（数据行、日志行同时带），并生成"代码定位索引"（文件→行→端点→表映射表），桌面提供"查看源码"只读入口。

#### L3. 【P1】API 无全局异常处理器，500 错误无 trace、无结构化记录

- **现象**：`grep exception_handler` 无命中；未捕获异常走 FastAPI 默认 500，仅 uvicorn 记一行，无 trace_id、无请求上下文。
- **证据**：api/main.py 仅一个 trace middleware；无 `@app.exception_handler`。
- **影响**：无人值守下，一次 500 的排障等于大海捞针；且异常上下文（租户/幂等键/参数）全部丢失，违反"每个读取携带租户和 Trace ID"的约束精神。
- **建议**：加全局 exception handler：500 → 结构化错误日志（trace_id、tenant、route、idempotency_key）+ 稳定错误码响应；DB 异常与业务异常分类处理。

#### L4. 【P1】/health 不是真探针

- **现象**：`/health` 只返回 liveness（进程活着）+ `database_configured`（仅判断 URL 字符串非空），不检查 DB 连通、迁移版本、Worker 心跳、outbox 积压。
- **证据**：`/health` 实现（main.py 1957 行附近）：`database_configured=bool(config.database_url.strip())`。
- **影响**：DB 挂掉时 /health 依然 200；无人值守场景没有可靠的存活探针。
- **建议**：升级为 readiness：DB ping + alembic head 校验 + worker 最近心跳时间（>N 分钟判定失联）+ outbox 积压量，返回结构化健康详情。

#### L5. 【P1】日志无轮转无保留

- **现象**：api.log/worker.log 单文件 FileHandler 无限增长（api.log 已 735KB，且随 24×7 必然膨胀）；桌面 unified-YYYY-MM-DD.log 按日切分但**无清理策略**，旧文件永不清除。
- **证据**：api/main.py FileHandler 无 RotatingFileHandler/TimedRotating；desktop 主进程每日一文件但无 retention 删除。
- **影响**：磁盘被日志吃满只是时间问题；无人值守下无预警。
- **建议**：日志统一走轮转（按大小+按天双保险）与保留期（例如 30 天）；清理任务纳入运维。

#### L6. 【P1】可观测性包为空：无统一 metrics/tracing

- **现象**：`packages/observability`、`packages/db`、`packages/artifact`、`packages/belief`、`packages/iam` 五个目录**为空**（无任何文件），与总体设计"模块自治"的声明不符。
- **证据**：`Get-ChildItem packages/observability -Recurse` 无文件。
- **影响**：无统一埋点（每个请求的耗时/状态码/DB 调用）、无链路追踪聚合；"展开到日志层"只能靠拼文件。
- **建议**：先落地最小 observability 包：trace_id ContextVar、请求耗时/状态码计数、慢查询记录、结构化日志封装；db 包统一连接与会话（当前各 service 各自 psycopg2.connect，重复且无统一超时/重试）。

#### L7. 【P2】血缘下钻已通到数据行，但缺最后一环（数据行→日志→代码）

- **现象**：audit/quant/aiops lineage、topology evidence_chain（含 source_table/source_pk）已能下钻到数据行——这条线是通的（这是做得最好的部分）；但下钻到数据行后即止。
- **证据**：/api/v1/audit/engagements/{id}/lineage、topology.evidence_chain_anchors（20 行）等实测存在。
- **影响**：50% 完成度的下钻体验：能看"是什么"，不能看"为什么发生/哪段代码产生"。
- **建议**：在现有血缘响应上追加 `trace_id` 与 `log_file|log_line` 定位字段，再叠加 L1/L2 的日志与代码映射，即可闭环。

#### L8. 【P2】桌面端控制类端点不可达，数据只能外部驱动

- **现象**：桌面 allowedPaths 白名单约 60 条，API 全量约 95 条；missions/workflows/runnable-tasks/claim/complete/plugins/invoke、图谱/知识写端点等约 35 条**桌面不可达**（HTTP 403 by design）。
- **证据**：desktop/electron/main.ts allowedPaths 与 API 路由清单比对；status.md 亦说明桌面为只读。
- **影响**：桌面演示的"运行"数据无法通过桌面产生或推进——与 D2/O2 叠加，桌面只能看静态快照。
- **建议**：若 24×7 的目标是"桌面工作台自主运转"，需在桌面增加受控的只读驱动能力（或后台执行器）；否则明确桌面定位为"监控台"并在文档声明。

#### L9. 【P2】ops.audit_log 死表 / ops.pending_outbox 无用视图

- **现象**：ops.audit_log 由迁移 0005 建表但全仓无任何写入者（0 行）；ops.pending_outbox 是迁移 0009 的视图，也无消费者。
- **证据**：grep `ops.audit_log` 仅迁移定义；实测 0 行。
- **影响**：schema 冗余、误导后人（以为有审计日志层）；与"证据不可硬删除"的审计叙事冲突。
- **建议**：删除或明确标注 deprecated；若需要系统审计日志（区别于业务审计），用 L6 的可观测性包重建。

#### L10. 【P2】桌面日志窗口无结构化过滤

- **现象**：统一日志窗口按来源/级别过滤，但无 trace_id 过滤、无时间范围、无关键词高亮；行解析靠正则猜级别（inferLogLevel）。
- **证据**：desktop/src/model/log.ts 全文为文本行级解析。
- **影响**：数据下钻到日志后，用户无法用 trace_id 聚合一次请求的完整日志。
- **建议**：日志窗口支持 trace_id 过滤（配合 L1 结构化格式）。

### C. 24×7 无人值守类缺陷（O）

#### O1. 【P0】无进程监督：API/Worker 挂掉无人拉起

- **现象**：`scripts/start-brain.ps1` 启动 API+Worker 后即退出，无 watchdog、无服务注册、无 Task Scheduler/计划任务、无自动重启；status.md 已记录"服务进程在长时间后台运行后可能被环境回收（API/Worker 同时消失，无崩溃日志）"。
- **证据**：start-brain.ps1 为一次性启动脚本；系统无相关计划任务注册逻辑；worker.err.log 中曾出现 `ModuleNotFoundError: No module named 'psycopg2'`（环境漂移导致启动失败，亦无自愈）。
- **影响**：24×7 的第一前提（进程永远在）不成立；环境回收后系统静默死亡，无人值守下无感知。
- **建议**：① 注册为 Windows 计划任务/服务（重启策略 AlwaysRestart）；② 增加 watchdog（探活 /health + worker 心跳，失联即拉起）；③ 启动脚本捕获环境漂移（python 探测固化到 venv 绝对路径）。

#### O2. 【P0】无任务执行循环：调度器只是状态库，mission 永远不会推进

- **现象**：Scheduler（packages/control/scheduler.py）只负责建任务/置状态/发事件；**没有任何进程消费 `task.ready` 并执行 claim→complete**。Worker 只做 outbox→inbox 与富媒体。
- **证据**：worker/local.py 主循环无 claim/complete；`grep claim_task|complete_agent` 仅在测试与 .data 脚本命中；心跳日志 `published=0 processed=False`；桌面不可达 claim/complete（L8）。
- **影响**：这是"24 小时不间断自动运行"的**核心缺失**——系统根本没有"运行"。"运行投影"全靠 seed 与手工驱动。
- **建议**：在 Worker 中加入调度执行器：消费 task.ready → 逐节点执行（走 Policy Gateway + 幂等键）→ claim/complete → 级联就绪任务 → 终态转移（配合 D3b）；执行器必须带租约/心跳（复用 rich_media_jobs 模式，见 O3）。

#### O3. 【P0】调度无租约/心跳/超时恢复：崩溃即永久卡死

- **现象**：`claim_task` 直接把 task_runs 置为 `running`，无 lease_token、无 lease_expires_at；进程崩溃后任务永远 `running`，无人回收。
- **证据**：packages/control/scheduler.py claim_task 实现无租约字段；对比 knowledge/rich_media_service.py 有完整的 lease 领取/校验/过期重领（这是全仓唯一正确的后台执行模式）。
- **影响**：一旦执行器上线（O2），任何一次崩溃都会造成任务永久卡死、统计失真。
- **建议**：task_runs 增加 lease 机制（claim 时写 lease_token+lease_expires_at；reclaim 条件 `status='running' AND lease_expires_at < now()`），并加"卡死任务检测"健康项。

#### O4. 【P1】无定时任务/周期调度引擎

- **现象**：全仓无 cron/periodic 机制；控制调度迁移（0025）只是 workflow 状态机，不是周期调度。
- **证据**：`grep -i "cron|schedule|APScheduler"` 无业务命中（除 doubao 外部 Skill）。
- **影响**：24×7 需要的周期动作（数据生成、归档、健康巡检、报告）无处挂载。
- **建议**：引入轻量周期调度（如 APScheduler 或自研 DB 驱动的 ticker），纳入控制平面受管（带租户/trace/幂等）。

#### O5. 【P1】桌面无自动重连/退避：恢复需人工介入

- **现象**：星图 5 秒轮询失败时静默保持上一帧（catch 后不重连、不指数退避、不重新注册 workspace）；API 恢复后需人工点击"切换工作区"。
- **证据**：desktop/src/App.tsx 轮询 catch 逻辑；status.md 已记录该操作步骤。
- **影响**：无人值守时桌面与控制平面断连后永远停留在旧数据。
- **建议**：轮询失败指数退避 + 自动重连（重新 loadWorkspace）+ 顶部状态徽标（已连接/重连中/失联时长）。

#### O6. 【P1】无告警通道：系统失联无人知晓

- **现象**：无邮件/桌面通知/Webhook/日志告警；只有桌面右上角连接失败横幅（且需人工打开桌面）。
- **证据**：全仓无告警发送逻辑。
- **影响**：深夜 API 挂掉、DB 满、任务卡死，次日才发现——24×7 无人值守失去意义。
- **建议**：健康巡检 + 告警通道（桌面通知 + 可选 Webhook/邮件）；告警本身留审计记录。

#### O7. 【P1】无容量/磁盘监控

- **现象**：日志无轮转（L5）+ 审计表无保留（D4）叠加，磁盘增长无上限；无磁盘水位检查。
- **证据**：0.1 表增长 + L5 证据。
- **影响**：24×7 数周后磁盘耗尽，系统整体不可用。
- **建议**：磁盘水位巡检（纳入 O6 告警）；配合 D4/L5 的保留策略。

#### O8. 【P2】Worker 环境漂移风险

- **现象**：worker.err.log 曾现 `ModuleNotFoundError: No module named 'psycopg2'`（用了错误的 python 解释器启动）；status.md 记录"当前终端默认 python 指向 Hermes 环境"。
- **证据**：.data/worker.err.log 历史内容；status.md 已知问题。
- **影响**：重启脚本在错误环境执行即静默失败，24×7 自愈链路脆弱。
- **建议**：start-brain.ps1 用 venv 绝对路径启动；启动时自检（import 探针 + 版本打印）；失败时输出明确指引。

#### O9. 【P2】无备份/快照策略

- **现象**：无 PG 备份脚本、无 PITR/归档配置（status.md 亦将灾备列为未完成）。
- **证据**：scripts/ 无备份脚本；status.md 未完成项。
- **影响**：数据累积越多，一次故障损失越大；审计类数据丢失不可恢复。
- **建议**：每日 pg_dump 到本地归档 + 保留 N 天；文档化恢复演练。

#### O10. 【P2】长稳/自愈测试缺失

- **现象**：tests/e2e、tests/golden、tests/security、tests/migration 四个目录**为空**；无 soak/long-run/自愈测试（杀进程→自愈→数据恢复）。
- **证据**：目录实测为空；README 声称的测试分层与实际不符。
- **影响**：24×7 的关键特性（自愈、幂等、租约回收）没有任何自动化防线。
- **建议**：至少补：① 自愈 e2e（杀 worker→watchdog 拉起→任务不被卡死）；② 幂等重放测试；③ 长稳 soak（连续 N 小时数据生成，断言无孤儿/无泄漏）。

## 4. 修复路线图（按 24×7 目标排序）

> 原则：先让系统"有数据、会推进、能自愈、可下钻"，再谈增强。每步都遵循项目约束（先契约与测试、显式迁移、Policy Gateway、租户+trace+幂等键）。

**R0 里程碑（数据支撑，对应 D1/D2/D3/D6/D7）**
1. 建 `packages/demo/`：幂等 seed 脚本 `scripts/seed-demo.ps1|py`，空库→全功能演示数据（含失败/回滚样本），测试断言"seed 后所有 UI 端点非空"。
2. 数据生成器：Worker 周期合成 AIOps 告警→事件→修复→canary→验证/回滚闭环数据（走 Policy Gateway）。
3. 修正状态一致性：seed 数据状态组合与真实流转一致；加状态链一致性测试。
4. 测试库隔离与清理钩子；CI 分离 TEST_DATABASE_URL。

**R1 里程碑（执行与状态机，对应 O2/O3/O4/D3b）**
1. Worker 调度执行器：消费 task.ready → claim（带 lease）→ complete/fail → 级联 → workflow/mission 终态转移（补齐 0 处 UPDATE 的缺口）。
2. 租约/心跳/超时回收（复用 rich_media_jobs 模式）+ 卡死任务健康检测。
3. DB 驱动周期调度 ticker（数据生成、归档、巡检挂载点）。

**R2 里程碑（进程与运行保障，对应 O1/O5/O6/O7/O8/O9）**
1. 进程监督：Windows 计划任务/服务 + watchdog（/health 探测 + worker 心跳）+ 自动重启 + 环境自检（venv 绝对路径）。
2. 桌面自动重连（指数退避）+ 连接状态徽标。
3. 健康巡检：磁盘水位、outbox 积压、卡死任务、审计表增长 → 告警通道（桌面通知/Webhook）。
4. 每日备份 + 恢复演练。

**R3 里程碑（全链路下钻，对应 L1-L6/L10）**
1. trace_id 进日志（ContextVar + 格式化器）+ uvicorn.access 带会话 + 全局异常处理器。
2. 日志轮转与保留期。
3. /health 升级为 readiness 探针（DB/迁移/worker 心跳/积压）。
4. 服务版本指纹 code_sha256 + 代码定位索引；桌面"查看源码"只读入口 + 日志窗口 trace 过滤。
5. 实现最小 observability/db 包（统一连接、超时、结构化日志、慢查询）。

**R4 里程碑（验收与卫生，对应 O10/Q1-Q8/L7-L9）**
1. 自愈 e2e、幂等重放、长稳 soak 测试补齐空目录。
2. 血缘端点追加 trace_id/log 定位；清理死表与 .data 脚本；API/桌面单体拆分。
