# 知识库管理界面 · 统一信息中枢设计

- **设计日期**：2026-09-15
- **设计目标**：把系统现有的**六类信息**（产物 / 报错 / 文档 / 经验 / 建议 / 决策）收敛到**一个界面**里统一管理与下钻，并让「运行 → 事实 → 统计 → 建议 → 决策 → 发布 → 回流」这条闭环真正通电，使系统具备**可审计的自我进化**能力。
- **设计依据**：本仓实测（`docs/知识库应用程度与作用评估-20260915.md`）+ 既有铁律（`AGENTS.md`、`docs/经验图谱机制图-20260911.html`、`docs/status.md`）
- **性质声明**：**设计提案，未实现**。本文只描述目标形态、落地路径与验收口径；所有现状数字来自 2026-09-15 对主库 `local-dev` 租户的实测。

---

## 一、结论速览

| 问题 | 答案 |
| --- | --- |
| 为什么现在需要一个统一界面 | 六类信息**都已落库/落盘**，但只有「知识库」一个页面（且只覆盖文档一半），其余靠翻文件、翻日志、翻 SQL |
| 核心设计选择 | **不建六个页面，建一个"信息条目"模型**；六个面是同一模型的六种投影，靠「溯源锚」互相下钻 |
| 与既有界面的关系 | 复用 desktop（React 19 + antd 5 + echarts + zustand）与既有 39 个知识/图谱端点，**新增聚合读端点，不新增真值源** |
| 「自我进化」怎么落地 | 7 环闭环；**系统自动积累事实（环 1–3）+ 人确认结构（环 4–6）+ 回流只改概率分布（环 7）**。实测：前 3 环已通，后 4 环**全部断** |
| 最该先做的三件事 | ① 报错诊断台（63 条失败 attempt 已带 `error_kind`，但零界面）② 统一搜索（跨产物/文档/经验的单一入口）③ 进化台（把断点可视化，让"从未产出"不再隐形） |

1. **报错已分类，但零聚合**：`error_kind` 分布是 `plugin_failed` 54 / `lease_expired` 9——这是现成的错误聚类素材，目前**没有任何界面按错误类型聚合**，也没有「同一 `error_kind` 反复出现」的告警。

## 三、设计目标与铁律

### 3.1 目标

1. **一处可查**：任何一条信息（一次失败、一个产物、一份文档、一条建议）都能在同一个入口被找到。
2. **一键下钻**：从任意条目出发，能沿「条目 → run/trace → 节点 → attempt → 产物文件 → 证据哈希」一路走到底。
3. **闭环可见**：自我进化的 7 环贴在界面上，**哪一环是空的就显示它是空的**。
4. **写面唯一**：界面只有一个写动作——**对人的决策落账**（采纳/驳回/审批），且全部经 Policy Gateway。

### 3.2 铁律（沿用项目既有约束，不可协商）

| # | 铁律 | 来源 |
| --- | --- | --- |
| R1 | **界面是投影，不是第二真值源**。后端提供只读聚合，前端只读不算真值；画布上的手动修改只进 localStorage，不回写后端 | 既有 nebula 设计 |
| R2 | **声明归声明，观测归观测**。版本/契约是声明（设计期），运行/建议/项目归属是观测（运行期）；两者不混存 | 经验层设计 |
| R3 | **经验只改变概率分布，不改变权限集合**。回流不得新增能力/端口、不得放宽数据边界、不得绕过闸门 | `AGENTS.md` |
| R4 | **写操作必须经 Policy Gateway**，带租户 + trace + 幂等键 | 既有 `local-*` 策略集 |
| R5 | **诚实状态优先**：数据缺失/降级/未产出，界面上必须显式标注，不得用"看起来正常"掩盖 | 本轮评估 P1/P2/P7 |
| R6 | 新增顶层目录需显式理由；新能力长进已有包 | 可迁移性整改既定结论 |

## 四、统一信息模型：`InfoItem`

### 4.1 为什么不建六个页面

六个面若各自建页，会立刻出现三件坏事：① 同一件事在多个页面重复出现且口径各异（如"失败率"）；② 无法回答跨面问题（"这条建议是哪些失败 run 推出来的？"）；③ 每加一类信息就要加一个页面与一套查询。

因此先定**一个条目模型**，页面只是它的过滤器。

### 4.2 条目字段（统一 schema）

| 字段 | 说明 | 例 |
| --- | --- | --- |
| `item_id` | 全局唯一（`<类型>:<原生主键>`） | `attempt:416b0efc…:finance-clean-001#2` |
| `kind` | 信息类（6 值 + 派生类） | `artifact` / `failure` / `document` / `observation` / `suggestion` / `decision` |
| `tenant` | 租户（RLS 不可跨） | `local-dev` |
| `anchor` | **溯源锚**：指向真相所在的那一行/那个文件 | `{schema,table,pk}` 或 `{path,sha256}` |
| `run_ref` | 关联 run / trace（可空） | `run=416b0efc…`, `trace=…` |
| `occurred_at` | 事实发生时间（非入库时间） | `2026-09-12T14:03:11+08:00` |
| `status` | 条目状态（语义随 kind 变） | `succeeded` / `failed` / `staged` / `proposed` / `released` |
| `evidence_sha256` | 证据哈希（产物/文档/证据包） | `d77431c2…` |
| `provenance` | 该条目**从哪来**的显式标注 | `L0 自动` / `L1 建议` / `L2 人工` |
| `relations[]` | 见 4.3 | `[produced_by, evidenced_by, derived_from, used_in]` |

### 4.3 三类关系（把六个面缝成一张网）

```
derived_from   建议/统计 ← 观测 ← run          （事实链：越往上越确定）
evidenced_by   条目 ← 证据包/文件哈希          （证据链：可离线复验）
used_in        插件/产物 ← 业务项目            （项目锚：待 archive_links 通电）
```

**关键**：`relations` 是**算出来的**（由后端聚合查询），不是存的。存关系会变成第二真值源（违反 R1）。

## 五、界面设计

### 5.1 总体布局

```
┌─ 顶部条：统一搜索框 ─ 域切换(audit/aiops/quant/knowledge) ─ 租户 ─ 健康灯 ─┐
├─ 左导航 ─┬─ 主区（条目列表：筛选 + 排序 + 批量选择） ─┬─ 右详情抽屉 ──────┤
│ 总览台   │  条目行 = 类型徽标 · 标题 · 溯源锚 · 时间   │ 溯源锚（可复制）  │
│ 产物库   │           · 状态 · 证据哈希前 12 位         │ 关系（可下钻）    │
│ 诊断台   │                                            │ 证据（可复验）    │
│ 文档与规则│                                            │ 唯一写面：决策    │
│ 进化台   │                                            │                   │
└─────────┴────────────────────────────────────────────┴───────────────────┘
```

- 复用 antd 5 的 `Table / Card / Tag / Drawer / Space`，与现有 `App.tsx` 风格一致，不引入新组件库。
- 图表用已有 `echarts`（趋势、分布），不引入新依赖。
- 语言与文案沿用现有中文风格（含确认弹窗 + 空态文案）。

### 5.2 五个工作台

#### 台① 总览台 —— 回答"系统现在什么状态"

| 区块 | 内容 | 数据来源 | 状态 |
| --- | --- | --- | --- |
| 信息地图 | 六类条目计数 + 近 7 日增量 | 各表 count + 时序 | 需新增聚合读 |
| 健康灯 | 4 个诚实指标：**向量覆盖率**、**证据包完整性**、**建议通道有无产出**、**策略集是否干净** | `chunks vs chunk_embeddings`；evidence zip 校验；`change_sets` by type；active 策略集计数 | 需新增（当前仅 UI 层误报） |
| 失败趋势 | 按 `error_kind` 的日线 | `node_attempts` | 需新增 |

> 健康灯是**修 P1 的正式方案**：`vector_ready` 改为"当前嵌入模型下的覆盖率"，并把 `向量可用 / 全文降级` 做成显式状态而非装饰。

#### 台② 产物库 —— 回答"跑出了什么、能不能复验"

- 列表：`run_id / plan_key / execution_hash / 节点数 / 成功失败 / 证据包大小+哈希 / 归档时间`。
- 筛选：按业务项目（待 `archive_links` 通电）、按插件、按时间、按"仅失败"。
- 操作（**全部只读或经策略**）：在线展开证据包清单（`plan.json` / `attempts.json` / `edges.json` / `artifacts/*`）、**一键离线复验**（复用 `verify-evidence-bundle`）、复制复现命令。
- 数据来源：`/api/v1/observability/evidence/{run_id}`（已有）+ `.data/evidence` 索引（需新增只读列举）。

#### 台③ 诊断台 —— 回答"为什么失败、还会不会再犯"

这是当前**完全缺失、但素材最齐**的一台：

- **错误聚类**：按 `error_kind` 聚合（实测 `plugin_failed` 54 / `lease_expired` 9），点进去列出该类型的全部 attempt。
- **定位链**：attempt → `node_instance_id` → `plugin_id` + `plugin_version` + `runtime_code_sha256` → 该插件的其他失败/成功记录。
- **一键复现**：给出该 run 的 `plan_key` + `execution_hash` + 复现命令（计划已封存，可重放）。
- **回归提示**：同一 `(plugin_id, error_kind)` 在修复后若再次出现 → 标红"回潮"。
- 数据来源：`node_attempts.error_kind/error_message`（**列已存在，零新表**）+ `/api/v1/observability/trace/{trace_id}`（已有）。

> 这一台的价值最高：**信息已经在库里躺了 63 行，只是没人给它一个界面。**

#### 台④ 文档与规则 —— 回答"系统知道什么、还缺什么"

- 语料：文档/分块/向量三列并排，**逐文档显示 `已向量化/总分块`**（现有 `knowledge` 页已做一半）。
- 规则库：把现行的"契约 / 策略 / 报告模板 / 技能"集中登记为一类条目（`kind=document, subtype=rule`），让"系统按什么规则做事"可查。
- 缺口清单：把本轮评估发现的缺口做成条目——中文分块占比、未配置的适配器（`local.mineru` 等待本地运行时）、`contract_only` 的知识域插件。
- 数据来源：`knowledge/stats|documents|batches`（已有）+ 新增"规则登记"读端点。

#### 台⑤ 进化台 —— 回答"系统在变聪明吗"

见 §六，把 7 环闭环做成一个**状态看板**：每环显示"已通 / 半通 / 断"，断的环显示"缺什么才能通"。

### 5.3 关键交互：溯源链下钻

任一条目 → 右抽屉的「关系」区 → 点任一关系跳到对面条目。例：

```
建议 suggestion:audit.ledger-quality→quant.experiment-evaluator
  ├ derived_from → observation:run=416b0efc/edge=…
  ├ evidenced_by → evidence:416b0efc.zip (sha256 d77431c2…)
  ├ used_in     → project:黔岭酒业2025年报审计   ← 待 archive_links 通电
  └ decision    → 采纳 / 驳回（唯一写面，经策略网关）
```

**下钻深度上限 3 跳**，避免无限展开；超过则提示用统一搜索续接。

## 六、自我进化闭环：7 环设计

### 6.1 七环定义

| 环 | 动作 | 谁执行 | 写面 |
| --- | --- | --- | --- |
| 1 | **运行发生**：插件执行 → attempt 落账（含产物 SHA） | 执行引擎 | `node_attempts` |
| 2 | **事实投影**：run 终态 → 经验观测（append-only） | 投影器（独立短事务，失败不影响业务） | `*_observations` |
| 3 | **统计聚合**：次数/成功率/Wilson 下界/时间衰减 | 系统自动，可重建 | `*_stats` |
| 4 | **建议产生**：设计外协作 → 候选关系（proposed） | 系统自动，需过统计门槛 | `relation_suggestions` |
| 5 | **人工决策**：采纳 / 驳回（留痕不删） | **人** | suggestion 状态机 + `control.approvals` |
| 6 | **知识发布**：ChangeSet → 校验 → Release | 人批准后系统发布 | `change_sets` / `releases` |
| 7 | **回流生效**：召回排序/连线先验/RAG 上下文 | 系统自动，**仅改概率分布** | —（只读消费） |

### 6.2 当前断点（实测，必须显示在界面上）

| 环 | 状态 | 实测证据 | 界面呈现 |
| --- | --- | --- | --- |
| 1 运行发生 | ✅ **已通** | `node_attempts` 1,726 行（1,663 成功 / 63 失败） | 绿色 |
| 2 事实投影 | ✅ **已通** | 写路径已接（`start_plan_run` 成功+异常两路径） | 绿色 |
| 3 统计聚合 | ✅ **已通** | `*_stats` 可重建；会话级清理已就位 | 绿色 |
| 4 建议产生 | ⚠️ **半通** | 表与状态机在，主库 `relation_suggestions` **0 行** | 黄色 + "从未产出" |
| 5 人工决策 | ⚠️ **半通** | 同上，无一条 `accepted`/`dismissed` | 黄色 + "等待第一条建议" |
| 6 知识发布 | ❌ **断** | `change_sets` 68 条**全为 `graph` 类，`experience` 类 0 条** | 红色 + "通道已建未产出" |
| 7 回流生效 | ❌ **断** | `ai_planner/` 对 `knowledge`/`retrieval` **零引用**；经验读路径未接组网 | 红色 + "读路径未接线" |

**这张表是整个设计的核心价值**：它把"系统看起来什么都有"变成"系统明确告诉你哪一环是空的"。**不显示断点，就是最严重的自我欺骗。**

### 6.3 一条不可逾越的约束

环 7 的"回流"必须是**只改概率分布**：影响的只能是**候选排序 / 连线先验 / 提示上下文**，不得新增能力或端口、不得放宽数据边界、不得绕过闸门与策略网关。界面在环 7 上直接标注这条约束，避免后来者（包括 AI）把它误做成"自动改权限"。

## 九、安全与边界

1. **只读为主**：除"决策落账"外，所有面板只读；标为"需新增"的端点全部是 `GET`。
2. **唯一写面**：`suggestion.decide` / `approval.decide`，经 Policy Gateway + 租户 + trace + 幂等键（R4）。
3. **不跨租户**：所有查询带 `app.tenant_id`；`experience` / `knowledge` / `semantic` 表均为 RLS FORCE，实测应用角色**无** BYPASSRLS。
4. **不建第二真值源**（R1）：关系与统计一律算出来；画布手动编辑只进 localStorage。
5. **不新增可执行面**：本设计不新增插件、不新增能力、不新增端口；诊断台的"一键复现"只是**给出命令**，不代执行。
6. **诚实标注**（R5）：降级、未产出、0 行、残留，全部显式呈现。

## 十、反模式（明确不做）

| 反模式 | 为什么不做 |
| --- | --- |
| ❌ 为六类信息各建一个页面 | 同一事实多口径，跨面问题无法回答；加一类信息就要加一个页面 |
| ❌ 把 `relations` 存进表 | 变第二真值源，与 R1 冲突，且必然与源数据漂移 |
| ❌ 界面直接连数据库查 | 绕过 Policy Gateway 与租户隔离，破坏 R4 |
| ❌ 把"向量可用"做成装饰性徽标 | 就是本轮 P1 的成因；必须按当前模型算覆盖率 |
| ❌ 让"一键复现"直接执行 | 越过闸门，违反"不代执行"与既有安全边界 |
| ❌ 把断点藏起来等以后补 | 断点不可见 = 系统会对自己撒谎，这是最贵的一种债 |
| ❌ 在界面里做"自动调权/自动改图" | 违反 R3：回流只改概率分布，不改权限集合与关系集合 |

## 十二、信息架构决策：诊断台与进化台放在哪里

> 本章回答一个具体问题：*新增"诊断台/进化台"，是把知识库页扩成多标签，还是新增顶层项？*
> **本章结论已被 §十三 取代**（保留作为决策过程记录）：用户指出"东西很多、需要多拆几页"，内容量实测支持这个判断。**最终方案见 §十三（两级导航 / 8 组 37 页）**。
> 本章仍有价值的两点：12.1 的事实纠正、12.5 的职责边界（图/表/因）在 §十三 中被继承。

### 12.1 先纠正一处事实错误（我上一轮说错了）

上一轮我说"`App.tsx` 现有 13 个一级导航已接近信息密度上限"——**不准确**。实测 `desktop/src/App.tsx:114-141`：

- `viewKeys` 确有 13 个键，但 **`log` 没有菜单项**（由顶栏「日志」按钮另开独立窗口，`App.tsx:1845`），**真实菜单是 12 项**。
- **菜单已经是分组结构**（不是平铺列表）：

```
概览        · 运行总览
协同运行    · 任务编排 / 图谱管理 / Run 画布
知识与插件  · 知识库 / 插件工作台
业务中枢    · 审计工作台 / 量化工作台 / AIOps 工作台
治理        · 审批中心 / 风险模拟
系统        · AI 设置
```

所以"信息密度"**不是主要矛盾**——12 项分 5 组、每组 1–3 项，结构是健康的。真正的问题是**概览位置那一项几乎是空壳**。

### 12.2 三个决定答案的实测

| 事实 | 证据 | 为什么关键 |
| --- | --- | --- |
| **`overview` 只有 5 行** | `App.tsx:1567-1571`：标题 + `metrics` 卡片区 + 一张"安全执行边界"说明卡 | **升级它零破坏**——现有内容可原样成为"总览"标签的第一屏，不丢任何信息 |
| **知识库页已经是多标签** | `App.tsx:1732-1809`（78 行），`<Tabs>` 含「文件导入」「文档管理」「处理批次」，另有页顶 metric cards + 「知识工厂」Card | 再往里加"诊断/进化"是**语义越界**：那是运行面的问题，不是文档生命周期的问题 |
| **加视图/加深链成本极低** | `renderView()` 是纯 `if` 链（`App.tsx:1295-1877`）；`App.tsx:115` 已在读 `window.location.search` 的 `view` 参数 | 技术成本不构成选择依据——应完全按信息架构选 |

顺带一个规模参照：`plugins` 视图 **218 行**、`knowledge` **78 行**、`overview` **5 行**。**`overview` 是唯一一个"有位置、没内容"的项。**

### 12.3 三个方案的对比

| 方案 | 改动 | 优点 | 致命点 |
| --- | --- | --- | --- |
| **A 新增两个顶层项** | 菜单 12 → 14 | 发现性最好 | 「诊断台」将与「Run 画布」并列，形成"运行面三分天下"（画布/编排/诊断），**统一搜索与一键下钻无处安放** |
| **B 塞进知识库页多标签** | 菜单不变 | 零新增项 | **语义越界**：运行诊断 ≠ 文档知识库；该页已 78 行 + 7 个状态切片，继续膨胀会变成第二个 `plugins`（218 行） |
| **C 升级 `overview` 为「信息中枢」** | 菜单 **12 项不变**；改 1 个 key/label；加 5 个页内标签 | 零新增项；"统一入口"成立；复用既有状态切片与端点；现内容不丢；`overview` 空壳问题顺手解决 | 需明确与「Run 画布」「知识库」的职责边界（见 12.5） |

**推荐 C。**

### 12.4 推荐形态

```
概览  ┌─ 信息中枢（原「运行总览」升级；菜单项数不变）
      │   标签 1  总览   ← 现有 metric cards + 策略边界卡 + 新增健康灯
      │   标签 2  产物   ← 新增：跨运行产物列表 + 证据包复验
      │   标签 3  诊断   ← 新增：error_kind 聚类 + 定位链 + 复现命令
      │   标签 4  文档   ← 摘要三数（文档/分块/向量覆盖率）+ 「去知识库」深链
      │   标签 5  进化   ← 新增：7 环状态 + 断点「缺什么」
```

- 菜单 **12 项 / 5 组完全不变**，只把第一项 `overview「运行总览」` 换成 `hub「信息中枢」`。
- 命名建议：**「信息中枢」**（备选「统一信息台」）。不建议叫"知识库管理"——它管的不止文档。

**一条硬原则：不重复实现。** 中枢的「文档」标签**只放三个数字 + 一个深链按钮**，深度操作（导入、文档表、批次、回收站）仍由知识库页承载。否则中枢就只是"第 13 个入口"，而不是"统一入口"——这正是方案 A 的问题换个位置复发。

### 12.7 什么时候才该升级为独立顶层项

给出可判断的阈值，避免以后凭感觉争：

1. **某标签成为日常主线**——例如"诊断"被每天打开 → 提到「协同运行」组，与 Run 画布并列；
2. **需要独立 URL 供外部引用**——告警、报告、其他系统要深链它；
3. **标签数 > 6**，或**单个标签内容 > 150 行**（参照：`plugins` 218 行已偏大，`knowledge` 78 行尚可）；
4. **出现第二个使用方**——例如某个自动化任务需要直接打开它。

任一条成立再拆分，**不要提前拆**。

### 12.8 明确不做

- ❌ **不动分组结构**——12 项分 5 组是合理的，重组会制造大 diff 且无收益；
- ❌ **不把中枢做成"第二个知识库页"**——重复实现会让"统一入口"变成"第 13 个入口"；
- ❌ **不删 `overview` 键**——深链兼容优先；
- ❌ **不继续往 `App.tsx` 里加视图实现**——1,877 行已偏大，新视图一律进 `components/`。

### 13.4 导航机制（antd 落地方案）

| 项 | 做法 | 原因 |
| --- | --- | --- |
| **两级折叠** | `navItems` 的 `{ type: "group", ... }` 改为带 `children` 的普通项 → antd 渲染为**可折叠 SubMenu** | 37 页若全展开，侧栏会溢出；折叠后首屏只显示 8 组 |
| **侧栏宽度** | `Layout.Sider width={196}` → **224px** | 中文标签 + 计数徽标需要空间；折叠态可缩到 56px |
| **计数徽标** | 菜单项带 `Badge`（如"诊断 63"、"审批 2"） | 复用现有 `knowledge` 页的计数习惯，让"有东西待处理"可见 |
| **命令面板** | **`Ctrl+K` 统一搜索**（组 1 的 `search` 页） | **页多了必须配搜索**，否则页多反而更难到达——这是拆页的前置条件，不是可选项 |
| **深链** | `?view=<page>`，页内再带 `&tab=<tab>`；扩展 `App.tsx:115` 的参数解析 | 现有已读 `?view=`，扩展成本低；告警/复现命令可直接贴链接 |
| **展开记忆** | 折叠状态存 `localStorage` | 与既有画布编辑同一纪律：只存本地 |
| **独立窗口** | 高密度可视化仍走独立窗口（知识星云 / 审计大脑 / 日志） | 已有 3 个窗口，不改成页内，避免主界面被大图拖慢 |

### 13.5 拆页的三条纪律（否则 37 页会变成灾难）

1. **一页一问**：说不出"这页回答什么问题"的页面**不建**。上表的"回答什么问题"列即准入条件。
2. **拆页 = 提级，不是重写**：优先把**已有页内标签**提升为页（`plugins` 的 8 个标签、`knowledge` 的 3 个、`graph` 的 4 个）——它们的内容与端点都已存在，**零新逻辑**。
3. **空数据也要显形**：新建页在无数据时必须显示"从未产出 / 0 行 / 待治理"，不得用空表掩盖（承 §六 的断点纪律）。

### 13.6 反向阈值：什么时候该合并回去

拆页有代价（导航成本、状态管理、`App.tsx` 膨胀），因此给出**合并**的判据：

- 某页**连续数月无独立访问**，且其内容能被另一页完全吸收；
- 某页**本身不足 30 行**且无独立数据源（属于纯标签）；
- 两页**回答同一个问题**（重复实现，违反纪律 1）。

**建议每季度做一次"页访问审计"**，用实际访问频次决定增删，而不是凭感觉。

### 13.7 明确不做

- ❌ **不平铺 37 项**——必须两级折叠 + 命令面板；
- ❌ **不为拆页重新实现已有标签的内容**（提级 ≠ 重写）；
- ❌ **不把独立窗口改回页内**（星云/审计大脑/日志保持窗口）；
- ❌ **不继续往 `App.tsx` 里加视图实现**（1,877 行已偏大）——新页面一律进 `desktop/src/components/pages/`，每页一个文件；
- ❌ **不一次性开工 37 页**——按 **P0(12) → P1(15) → P2(2)** 分批，每批可独立验收。

### 15.2 诚实化到底改了什么

**改前**：`stats()` 与 `list_documents()` 统计向量时**不限模型**（`LEFT JOIN semantic.chunk_embeddings ON chunk_id`），而 `_vector` 检索**按 `model_key` 过滤**。两者的口径差就是"桌面显示『向量可用』、实际当前模型只有 8 条"的根因；`embedding_model` 还取自"最近一条"，于是把一个残留的测试模型报成语料的嵌入模型。

**改后**：

- `embedding_chunks` / `embedding_model` **都按当前 embedder 模型**统计；
- 新增 `embedding_coverage`（当前模型 / 总分块）；
- 新增 `embedding_models`（各模型分布）——**残留向量保持可诊断，而不是被藏起来**；
- `vector_ready = 当前模型有向量 > 0`（索引侧就绪；服务可用性另由检索响应的 `degraded` 表达）；
- 桌面徽标三态：**向量可用**（覆盖率 ≥95%）/ **部分已向量化 x%** / **全文降级**。

**实测效果**（主库 `local-dev`）：`embedding_chunks` 28 → **8**，`embedding_model` `test-1024` → **`qwen3-embedding:0.6b`**，覆盖率 1.4% → 徽标显示「部分已向量化 1.4%」而不再是「向量可用」。

### 15.4 期间踩到并记下的坑

1. **`alembic_version.version_num` 是 `VARCHAR(32)`** —— 我的首个 revision id 有 34 字符，迁移在**写版本号那一步**才失败（DDL 已回滚，库是干净的）。规则：**revision id ≤ 32 字符**（现网最长 32）。
2. **`catalog.plugin_versions.plugin_id` 是 UUID 外键** —— 想按点号插件名取版本，必须 `JOIN catalog.plugins ON plugins.id = plugin_versions.plugin_id` 并用 `plugins.key`。直接拿 UUID 当 plugin_id 会静默得到 0 行。
3. **`discover_plugins(globs=..., domain=...)` 同时传会让 `domain` 失效** —— 静默不生效的筛选比没有筛选更糟，故 `domain` 改为在视图内过滤，并加了"筛选不得改变 summary、且必须真的减少条数"的断言。

5. **沙箱/环境类假失败**（均非代码问题，记录以便复现）：`.pytest_cache` / `.mypy_cache` / `tsconfig.*.tsbuildinfo` 不可写 → 需 `-p no:cacheprovider`、`--cache-dir=.data/mypy_cache`、`--tsBuildInfoFile`。
