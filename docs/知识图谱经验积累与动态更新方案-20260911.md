# 知识图谱经验积累与关系动态更新方案（2026-09-11 设计稿）

> 状态：**设计稿，待评审，未实现**。遵循 AGENTS.md：一次只承接一个 Phase 任务；先更新契约与测试，再实现服务逻辑；迁移显式执行；所有写入带租户 / Trace ID / 幂等键并经 Policy Gateway；证据不可硬删除。
>
> 一句话目标：让「知识星云」在一次次真实业务运行中，把**实际发生过的插件协作**沉淀为可追溯的经验，使节点关系的**强弱、可信度、缺口**随使用动态更新；系统只自动积累「事实与统计」，关系的**新增固化必须人工确认**，不自动执行、不自动授权。

---

## 1. 背景与问题

当前知识星云（`packages/ai_planner/nebula_graph.py` + `GET /api/v1/topology/plugin-nebula`）是一张**设计态（design-time）静态图**：

- 节点 / 连线完全由磁盘上的插件契约目录 `plugin.protocol.json` 推导：`cluster`（阶段簇→插件）、`dataflow`（输出契约==输入契约）、`cross`（invokes 支撑层）、`trunk`（阶段环流）。
- 它回答的是「**理论上谁能连谁**」，但回答不了「**实际业务里谁和谁配合过、配合得好不好、哪些连线从来没跑通过、哪些实际协作没有在契约里声明**」。
- 手动连线只存在浏览器 localStorage，是个人视图，不沉淀、不共享、无证据。

业务每次真实运行其实已经留下了完整事实（见第 2 节），但这些事实没有回流到图谱上。本方案在**不新增任何执行面、不触碰 Phase 9 边界**的前提下，把运行事实投影成「经验态图层」，与设计态图叠加，实现「越用越懂、关系动态更新」。

## 2. 现状盘点（可复用的既有资产，不重复造轮子）

### 2.1 运行事实源（已存在，本方案只读）

| 既有表 / 对象 | 位置 | 记录了什么 | 对经验的用途 |
| --- | --- | --- | --- |
| `topology.execution_runs` | 迁移 0042 | 一次业务链运行：chain、status(running/success/failed)、node_total/succeeded/failed、checksum、planner_version、trace_id、幂等键 | 经验沉淀的触发单元 / 一次完整业务样本 |
| `control.node_attempts` | 迁移 0052 | 每节点每次尝试：capability、plugin_id、attempt_seq、status、`input_bindings`、`output_refs`、error_kind、lease/fencing、trace_id | **识别「实际数据交接」的核心依据** |
| `event.outbox` | 0004 起 | `node.finished` 等领域事件 | 触发经验投影，复用既有事件通道 |
| `policy.tool_calls / decisions` | policy 域 | 每次工具调用与裁决（不可变） | 经验写入本身也要留裁决证据 |
| `topology.evidence_chain_anchors` | 0046 | 证据链锚点 | 经验边可回链到证据 |

关键结构（来自 `ports_executor.py` / `dag_persistence.py`，已核对）：

- `output_refs = {port_id: {uri, sha256, size_bytes}}`：节点某输出端口产出的产物指纹。
- `input_bindings = {port_id: {port_id, source_instance, source_port, uri, sha256, ...}}`：节点某输入端口**实际**从哪个上游实例的哪个端口取到了哪个产物。
- 运行期输出索引 `outputs[(node_instance_id, output_port_id)] = ArtifactRef`。

因此在**同一个 run 内**：若消费者 B 的 `input_bindings[p].source_instance = A`，则观测到一次真实交接 `A.plugin_id → B.plugin_id @ 契约p`，并带产物 SHA、成败、耗时。这就是经验的最小事实单元，无需插件额外上报。

### 2.2 知识图谱骨架（已存在，本方案对齐其治理模式）

- `graph.spaces / graph.nodes / graph.edges`（0004）：**双时态**（valid_from/valid_to）、**版本化**（row_version）、**软删除**（deleted_at），边自带 `weight numeric` 与 `properties jsonb`，`UNIQUE(space_id, source, target, relation_type)`。
- `knowledge.change_sets`（draft，operations）→ `knowledge.releases`（版本发布）：既有「**提出变更 → 发布生效**」治理闭环。
- `knowledge.recycle_bin`：回收不硬删。
- Policy：`require_policy(capability, tenant, trace, risk_class, side_effects, arguments)`；策略集 `policy.policy_sets` 按租户 seed（参考 0054 为星云只读 CAP 授权）。

> 结论：**不需要新建一套图数据库或学习框架**。在既有「不可变事实 + 可重建聚合 + 变更发布 + 策略门 + RLS」的模式上，增加一个 `experience` 经验域即可。

## 3. 核心设计：双图层 + 三级更新

### 3.1 两张图层叠加，职责分离

```text
设计态图层（Design，已有）   从插件契约目录推导 → 「理论上谁能连谁」，静态、确定性、纯函数
        × 叠加
经验态图层（Experience，新增）从真实运行账本投影 → 「实际谁和谁配合过、效果如何」，随业务增长动态更新
```

- 设计态图保持纯函数、不被运行数据污染（`build_nebula_graph` 不改语义）。
- 经验态是**覆盖层（overlay）**：按 `(source,target,contract)` 对齐到设计态节点 / 边上，提供权重、成败、候选关系；前端把两层一起渲染。
- 任一图层可独立解释、独立关闭；经验层可整体重建（见 5.4）。

### 3.2 三级动态更新（关键安全分级）

| 级别 | 内容 | 谁来做 | 是否进图 / 是否需审批 | 影响 |
| --- | --- | --- | --- | --- |
| **L0 自动统计** | 使用次数、成功率、耗时、最近使用、产物指纹等**派生事实** | 系统在 run 终态后自动投影 | 直接写经验表，**内部能力、外部不可直接调**；仍走 Policy Gateway + 幂等 + 租户/Trace | 只改变边的粗细 / 颜色 / 排序，**不改关系集合、不授权、不执行** |
| **L1 候选关系** | 运行中出现「实际交接了数据，但设计态契约里没有这条边」的**设计外协作** | 系统自动发现并生成「建议连线」 | **不直接进图**，状态 `proposed`，前端画金色虚线 | 提示「实践中产生了新关系」，等待人判断 |
| **L2 人工固化** | 采纳 / 驳回候选；或把稳定经验沉淀为正式契约 | 人（审计员 / 管理员） | 必须经策略门（low，可配审批）+ 幂等；采纳走 `change_sets→releases` 或转成插件 manifest 修订任务 | 关系集合**只在人工确认后**改变；驳回也留痕，不硬删 |

> 原则：**系统自动积累「证据和统计」，人来决定「结构」**。这使「越用越聪明」成立，同时不违反「不开放泛化 AUTO 权限、GUI 不能绕过策略、生产修复需人工确认」。

### 3.3 经验从哪来：一次 run 的投影过程

```text
业务链运行结束（execution_runs 落定 success/failed，node.finished 事件齐）
  → ExperienceProjector.project_run(tenant, run_id, trace)
      1. 读该 run 的全部 node_attempts，建 instance_id → (plugin_id, capability, output_refs) 映射
      2. 遍历每个 target attempt 的 input_bindings：
           source_instance → 找到 source 的 plugin_id / output 端口 / 产物 sha
           得到一条「实际交接」：source_plugin → target_plugin @ contract
      3. declared? = 该三元组是否命中设计态 dataflow 边集合（当时快照）
      4. 写 edge_observation / node_observation（append-only，幂等 ON CONFLICT DO NOTHING）
      5. 增量 upsert edge_stats / node_stats（可重算的聚合）
      6. declared=false 的，upsert relation_suggestion（proposed，累加证据 run，不重复建条）
  → 同 run 重放结果不变（幂等键 = run 维度）
```

## 4. 数据模型（新增 `experience` 域，迁移 0055）

> 分层原则：**原始观测不可变、不可硬删；聚合统计可随时从观测重建；候选是带状态机的工作记录**。所有表 `ENABLE + FORCE ROW LEVEL SECURITY`，应用账号 `audit_app` 仅 `SELECT/INSERT/UPDATE`、无 `BYPASSRLS`、无 `DELETE`（与 0052 一致，downgrade 拒绝删除证据）。

### 4.1 `experience.edge_observations` —— 实际数据交接观测（append-only 不可变）

```text
observation_id        uuid PK
tenant_id             uuid NOT NULL              -- RLS 隔离
run_id                uuid NOT NULL              -- -> topology.execution_runs
trace_id              text NOT NULL
source_plugin_id      text NOT NULL              -- 生产者插件（由 source instance 解析）
target_plugin_id      text NOT NULL              -- 消费者插件
contract_id           text NOT NULL              -- 交接的数据契约 / 端口
source_attempt_id     uuid NOT NULL              -- -> control.node_attempts
target_attempt_id     uuid NOT NULL
source_instance       text NOT NULL
target_instance       text NOT NULL
artifact_sha256       text                       -- 被交接产物指纹（可回链 artifact）
declared              boolean NOT NULL           -- 设计态是否已声明（判定时快照）
status                text NOT NULL              -- succeeded / failed（消费者侧结果）
latency_ms            integer
observed_at           timestamptz NOT NULL DEFAULT now()
UNIQUE (tenant_id, run_id, source_instance, target_instance, contract_id)  -- 幂等
```

### 4.2 `experience.node_observations` —— 节点使用观测（append-only）

```text
observation_id uuid PK, tenant_id, run_id, trace_id
plugin_id text, capability text, attempt_id uuid, attempt_seq int
status text, error_kind text, latency_ms int, observed_at
UNIQUE (tenant_id, attempt_id)                   -- 同一 attempt 只观测一次
```

### 4.3 `experience.edge_stats` / `experience.node_stats` —— 聚合（可重建，upsert）

```text
-- edge_stats：按主体对 + 契约聚合
PRIMARY KEY (tenant_id, source_plugin_id, target_plugin_id, contract_id)
success_count int, fail_count int, total_latency_ms bigint
first_used_at, last_used_at timestamptz
declared boolean                                 -- 是否设计态声明边
confidence numeric                               -- 成功率置信下界（见 5.3）
weight numeric                                   -- 综合展示权重（可重算，不用于授权）
evidence_run_ids jsonb NOT NULL DEFAULT '[]'     -- 最近 N 条证据 run（环形限量；全量在观测表）

-- node_stats：按插件（可再按 capability 细分）
PRIMARY KEY (tenant_id, plugin_id[, capability])
use_count, success_count, fail_count, total_latency_ms
error_kind_counts jsonb, first/last_used_at, confidence, weight
```

### 4.4 `experience.relation_suggestions` —— 设计外关系候选（状态机，不硬删）

```text
suggestion_id uuid PK, tenant_id
source_plugin_id, target_plugin_id, contract_id
status text CHECK (status IN ('proposed','accepted','dismissed'))
evidence_count int, confidence numeric, evidence_run_ids jsonb
proposed_by text DEFAULT 'system'
decided_by uuid, decided_at timestamptz, decision_trace_id text
idempotency_key text NOT NULL                    -- = tenant|source|target|contract，重复发现只累加证据
created_at, updated_at
UNIQUE (tenant_id, source_plugin_id, target_plugin_id, contract_id)
```

- `accepted`：进入正式结构（写 `knowledge.change_sets` 并走 release，或生成 manifest 修订任务，见 5.5）。
- `dismissed`：保留记录与证据，后续不再重复提示（同幂等键不再回到 proposed）。
- 不提供 DELETE 路径。

## 5. 关键机制

### 5.1 触发与事务边界（不进执行热路径）

- 复用既有 outbox / run 终态：`execution_runs` 落定 `success/failed` 后触发一次投影；本地单机可在链运行完成的服务方法末尾、以**独立短事务**调用 `ExperienceProjector.project_run`（与 CW3「事务外启动、短事务提交」一致）。
- 投影失败**不影响业务 run 结果**：失败留 outbox / 日志，可重试、可由 rebuild 兜底。
- 投影只读 `topology/control`，只写 `experience`；不执行插件、不触网络。

### 5.2 幂等

- 观测表以 run / attempt 维度 `ON CONFLICT DO NOTHING`；重复投影同一 run，观测不增、聚合不翻倍。
- 聚合 upsert 采用「可由观测表完整重算」的语义；任何时候可对账：`edge_stats` 计数必须等于观测表对应分组行数（加自检查询 / 测试）。
- 人工决策、rebuild 接口都必须带 `idempotency_key`。

### 5.3 置信度与动态权重（避免「一次成功就满分」）

- 成功率置信度用 **Wilson 95% 下界**（小样本保守）：n 次、s 次成功，
  `p̂=s/n`，`lo = (p̂ + z²/2n − z·√(p̂(1−p̂)/n + z²/4n²)) / (1 + z²/n)`，z=1.96。
- 统计窗口**默认全量**（所有历史观测都计入计数与成功率），在此基础上叠加时间衰减，只作用于展示权重、**不删证据**：`decay = exp(−λ·Δ天)`，Δ 为距最近一次使用的天数；**λ=ln2/90（90 天半衰期，已定）**。
- 展示权重 `weight = log1p(n) · lo · decay`；前端把 weight 映射到边宽 / 饱和度。weight 仅用于可视化与推荐排序，**绝不参与授权或自动执行决策**。

### 5.4 可重建 / 可审计

- `rebuild(tenant)`：清空**聚合表与候选的派生字段**（观测表保留），从 `*_observations` 全量重算 stats，并重新扫描 declared 标记与候选；结果与增量投影一致（测试断言两条路径等价）。
- 每条经验都能下钻：边/节点详情 → evidence_run_ids → execution_runs → node_attempts → output_refs 的产物 SHA / 证据链锚点。

### 5.5 L2 固化出口（已定：先轻固化，契约修订作为后续）

**出口 1（轻固化）已落地（2026-09-11，迁移 0057）**，出口 2 仍仅预留、不在本期实现：

1. **图内轻固化（已实现）**：accepted 写入 `knowledge.change_sets`（`change_type='experience'`，operation 的 `target_kind='experience.relation'`，payload 记录「新增关系 + 证据 run + 决策人」），随 knowledge release 经 validate→approve→release→activate 发布为正式关系；过程留策略裁决与决策人、带幂等键。发布后回写 `relation_suggestions.changeset_id/release_id/released_at`，该关系在图上从「候选」转为「已确认关系」（青绿实线），但**不改插件 manifest、不改执行器**、不向 `graph.nodes` 物化（关系两端是插件而非知识节点）；固化幂等（已发布则复用同一 release），证据不可硬删、关系不自动回滚。实现：`packages/knowledge/lifecycle.py`（扩展 experience.relation）、`packages/experience/solidify.py`，decision 端点 accepted 同步固化。
2. **契约回写（后续阶段，本期不做）**：把稳定的已确认关系转为插件 `plugin.protocol.json` 的 inputs/outputs/invokes 修订任务，走代码评审与迁移；发布后该关系从「已确认」进一步变为「设计态原生边」。

> 决策记录（2026-09-11）：L2 先做轻固化、再谈契约；统计窗口默认**全量 + 90 天半衰期衰减**（λ=ln2/90，见 5.3），不做近 N 次滑窗。

## 6. API 设计（对齐现有 nebula 端点写法）

全部要求 `X-Tenant-Id` + `X-Trace-Id`，经 `require_policy`，写操作带幂等键；错误 fail-closed。

| 方法 & 路径 | 能力 CAP | risk / side_effects | 说明 |
| --- | --- | --- | --- |
| `GET /api/v1/topology/plugin-nebula/experience?lifecycle=&window=` | `topology.nebula_experience.read` | read_only / read_only | 返回设计态图 + 经验覆盖（node_stats、edge_stats、suggestions 摘要） |
| `GET /api/v1/topology/nebula-experience/suggestions?status=` | 同上 read | read_only | 候选关系列表 + 证据 run |
| `POST /api/v1/topology/nebula-experience/suggestions/{id}/decision` | `topology.nebula_experience.suggestion.write` | low（可配 approval_required） | body `{decision: accept\|dismiss, idempotency_key}`；唯一人工结构写面 |
| `POST /api/v1/topology/nebula-experience/rebuild` | `topology.nebula_experience.rebuild` | low | body `{idempotency_key}`；从观测重建聚合，管理员 |

- 新增 Pydantic 模型沿用 `extra=forbid`，与 `NebulaNode/NebulaEdge` 同风格（新增字段必须同步模型，避免端点校验失败）。
- 策略 seed 用一个独立迁移（0056）按 `local-dev` 租户幂等下发，参照 0054；**只授 read_only 给读，写 CAP 默认不给、显式授予**。

## 8. 安全与 Phase 9 边界合规（逐条对齐 AGENTS.md）

1. **不新增执行面**：经验投影是 run 结束后的**事后只读分析 + 经验库写入**，不启动命令、不触外网、不改真实基础设施、不创建真实交易。
2. **不开放 AUTO**：L0 仅写派生统计，CAP 标记 internal、外部无法直接调用；关系结构变更（L1→L2）必须人工，经 Policy Gateway；GUI 与 API 同走一个门，不能绕过。
3. **租户 / Trace / 幂等**：每张表带 tenant_id 并 RLS 强制隔离；每次投影与决策带 trace_id；观测、决策、rebuild 全部幂等。
4. **证据不可硬删**：观测表无 UPDATE 事实字段、无 DELETE；候选只迁移状态；聚合可删但可重建；迁移 downgrade 拒绝删除证据（同 0052 写法）。
5. **最小库权**：`audit_app` 无 BYPASSRLS；经验表仅授予必要 DML，不授 DROP/DELETE/TRUNCATE（rebuild 的「清空聚合」用受限的服务函数或按主键批量 UPDATE/DELETE 聚合表且策略门保护，观测表不动）。
6. **迁移显式执行**：0055（表 + RLS + 索引 + 授权）、0056（策略 seed）显式 alembic 升级，应用启动不自动升级；同步推进 `EXPECTED_MIGRATION_HEAD` 与迁移链测试。
7. **先契约 / 测试后实现**：先定类型契约与测试（红灯），再写投影器与 API。

## 10. 明确不做（本次范围外，避免提前实现后续 Phase）

- 不做跨租户经验共享 / 全局联邦学习；不把经验自动回灌成执行计划或自动组网执行。
- 不做 LLM 自动判定关系语义、不做嵌入聚类自动命名（候选仅基于「实际产物交接」这一确定性证据，可解释、可复算）。
- 不引入新中间件 / 图数据库 / 外部服务；不依赖外网。
- 不改动既有执行器语义与设计态星云纯函数；手动编辑 localStorage 层保持原样。

> 后续若要「经验驱动自动推荐组网」「经验自动转契约」，属于新的授权模型与新阶段，需单独立项、重新过策略与评审，不在本方案内默认开启。
