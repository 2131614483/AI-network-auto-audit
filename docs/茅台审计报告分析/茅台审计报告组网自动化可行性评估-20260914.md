## 1. 实测解剖：118 页由什么构成

### 1.1 一个反直觉的发现 —— 连报告本身都是"两条产线"出来的

| PDF 页 | 内容 | 文本层 | 图片 |
|---|---|---|---|
| 1–6 | 目录 + 审计报告正文 | 有（442–759 字/页） | 无 |
| **7–14** | **8 张财务报表（合并/母公司 × 4）** | **0 字符** | **每页 1 张 3307×4677 扫描图** |
| 15–112 | 财务报表附注 | 有（~900–1100 字/页） | 无 |
| 113–118 | 事务所资质附件 | 极短 | 扫描件 |

**这条证据很关键**：连茅台自己的报告，**报表与附注也是分离生产**的 —— 报表由核算系统出数后打印、盖章、扫描；附注由报告系统排版成电子文本。也就是说「报表 + 附注」在源头就是**同一套账务数据的两条呈现分支**，这正是组网可以合并掉的重复劳动。

复现：

```bash
python -c "import pymupdf; d=pymupdf.open(r'<pdf>'); \
  print([(i+1, len(d[i].get_text()), len(d[i].get_images())) for i in range(20)])"
```

## 4. 实测：用模拟账套真跑一遍

为了不空谈，我按真实上市酒企口径造了一套**自洽的模拟账套**并跑通了整条链路。

### 4.1 造了什么

| 产物 | 内容 | 文件 |
|---|---|---|
| 试算平衡表 × 3 | 母公司 / 黔岭销售(100%) / 黔岭包装(80%)，59 个科目 | `sim/out/source/trial_balance_{P,S1,S2}.csv` |
| 记账凭证 | **80 张凭证 / 160 条分录**，每行带 `产品/渠道/地区/客户/供应商/关联方/税种/资产类别/账龄/现金流项目` 十个维度标签 | `sim/out/source/journal_entries.csv` |
| 子公司档案 | 持股比例、合并方式 | `sim/out/source/subsidiaries.csv` |

**设计要点**（也是"数据可行性"的核心论据）：

1. **凭证驱动** —— 所有数字由复式记账生成，**借贷天然平衡**，所以「资产 = 负债 + 所有者权益」不是配出来的，是推理出来的；
2. **维度标签即附注** —— 附注明细表由**同一批分录按维度聚合**得出，**附注不是第二套数据源**；
3. **合并工作底稿** —— 三个主体各自试算平衡，再经 6 笔抵消分录生成合并数。

### 4.5 这次实测告诉我们什么

| 问题 | 实测答案 |
|---|---|
| 附注能不能自动出？ | **能**。前提是**分录上带维度标签**。10 张附注全部由同一批分录聚合得出，附注与主表 100% 勾稽。 |

### 5.4 两个必须先修的工程阻断（已实测复现）

#### 阻断 A：API 侧的能力召回看不到磁盘上的 123 个插件

| 召回来源 | 打到的能力数 | 谁在用 |
|---|---|---|
| `capability_catalog_from_db()`（DB `topology.plugin_blueprints`） | **实测本机 `local-dev` 租户：377 行，**全部 `status='planned'`，其中 **374 行是契约测试残留**（键名形如 `it-xxxx-consumer/producer/bridge-dst`），真正的语义蓝图只有 3 个：`ledger-quality-slot` / `finding-draft-slot` / `research-note-slot` | **`apps/api/main.py` 的 `/api/v1/topology/planning/ai` 与 `/canvas/chat`** |
| `domain_catalog('audit')` + `build_port_contracts(_specs_for('audit'))` | **实测 107 capability / 161 端口 / 0 冲突** | 只有 `workbench.revise_with_ai`（桌面画布改稿） |

**后果**：桌面画布上对 AI 说"帮我生成一份审计报告编制流程"，模型**只能看到 1 个真实能力**（`audit.ledger.validate`），必然返回空草稿或"能力不可满足"。

#### 阻断 B：API 侧未传目录派生契约，退回 7 条遗留注册表

`apps/api/main.py` 调用 `AiPlanner.plan()` 时**没有传 `port_contracts`**，于是 `draft.py` 落到兜底的 `PORT_CONTRACTS`——只有 7 个端口（`ledger`、`candidates`、`audit-quality-candidates`、`finding-draft`、`experiment`、`evaluation`、`research-note-draft`）。

**实测证据**（用真实插件 `audit.report.report-frame-build` 的真端口 `project-snapshot` 造最小草稿）：

```

  输入端口=project-snapshot schema_ref=dataset-validation.schema.json
  该输入端口在 API 兜底注册表(7条)里? False
  该输入端口在 目录派生注册表(161条)里? True
```

**即：只要模型规划的流程用到任何一个真实审计端口，就一定会被闸门以 `contract_mismatch` 拒绝，连编译器都到不了。**

**修复建议**（两处，改动都很小）：

1. `apps/api/main.py` 两处 `/topology/planning/ai`、`/canvas/chat`：把 `capability_catalog_from_db(...)` 换成 `workbench.domain_catalog(domain)`，并把 `build_port_contracts(_specs_for(domain))` 传给 `plan()`；

## 7. 风险、边界与诚实声明

### 7.1 本评估**没有**验证的东西

1. **没有跑通真实的组网执行**。§4 的端到端复算是一套**与插件端口契约同构的独立复算引擎**（`sim/engine.py` + `sim/report.py`），**未经过 Policy Gateway、未落 `topology.execution_runs`、未走隔离运行时**。它证明的是「**数据与算法可行**」，**不是**「组网已能跑这条链路」。
2. **§5.3 的 11 个插件只是端口契约草案**，没有 runtime 实现、没有 schema 文件、没有门禁测试。
3. **8 张主表的金额单元格数（约 736）是表格结构估算**，因为原 PDF 该部分是扫描图，无文本层可计数。
4. **§6 口径三的"人时"是主观估计**，非实测。

### 7.2 模拟账套的简化处理（已在代码中标注）

| 简化 | 影响 | 真实项目需补 |
|---|---|---|
| 内部存货未实现利润假设为 0（当年内部采购全部耗用并对外销售） | 合并毛利略高 | 存货中含内部加价的期末余额 |
| 所得税按 25% 法定税率简化，未做纳税调整 | 有效税率=法定税率 | 纳税调整明细表、递延所得税 |
| 附注成本按"标准成本率"分摊（费率显式声明在代码里） | 产品/渠道/区域毛利率是分摊结果 | 成本核算模块的产品成本 |
| 合并所有者权益变动表按归母权益滚存呈现，未展开子公司权益抵消明细 | 权益变动表偏简 | 子公司权益逐项抵消 |
| 未编 8 张主表的**母公司现金流量表**与**权益变动表** | 覆盖 6/8 张 | 同合并逻辑 |
| 未含 分部报告、每股收益稀释、金融工具敏感性 | 附注九/十四未覆盖 | 分部核算、估值模型 |

### 7.3 能力边界（写入约束，不可绕过）

沿用项目既有硬约束，**这些不会因为自动化而放宽**：

- 经验/自动化**只改变概率分布，不改变权限集合** —— 不新增能力、不新增端口、不放宽数据边界、不绕过闸门与策略网关；
- **报告签发永远由人完成**；`audit.report-draft` 的设计前提就是"草稿永不覆盖历史报告"；
- 每个读取携带**租户 + Trace ID**；每次写入具备**幂等键 + Policy Gateway 裁决 + 可回溯执行历史**；
- 证据与历史记录**不可硬删除**。

### 7.4 真实的实施风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| **科目映射的"脏"** | 每家客户的科目表都不同，重分类规则要人工确认一次 | 首次映射留人工确认闸门，之后版本化复用 |
| **关联方识别的召回率** | 依赖交易对手主数据质量，漏标 = 披露不完整 | 用股权穿透 + 名称模糊匹配双路召回，加 `disclosure-checklist` 兜底 |
| **"看起来对"的合计数** | 表平了但抵消错了，是审计最怕的错 | 强制 §4.3 这 8 项勾稽作为编译期门禁 |
| **AI 生成 KAM 的越界** | 模型可能"猜"出事实 | KAM 只做候选推荐 + 引用已有工作底稿，不允许生成无来源事实 |
| **报告是法律文件** | 排版/套红/签章出错代价高 | `layout-render` 输出后强制人工比对，`e-signature` 前加审批 |

## 8. 建议的下一步（分三步）

### 第 1 步：修装配位（1–2 天，无新功能）

1. `apps/api/main.py` 的 `/topology/planning/ai` 与 `/canvas/chat` 改用目录派生召回 + `port_contracts`（§5.4）；
2. 清理 `topology.plugin_blueprints` 中 374 行测试残留，并加回归测试；
3. 验收标准：在桌面画布对 AI 说"生成一份年度审计报告编制流程"，能得到一个**通过闸门**的草稿。

### 第 2 步：建报告编制插件组（按 §5.3 顺序）

先做 **#2 合并工作底稿** 和 **#5 附注明细表生成器** —— 这两个吃掉 60 页 = 51% 的篇幅，且是其余插件的公共前置。
每个插件交付物 = 协议 JSON + schema 文件 + runtime + 契约测试 + 一个合成夹具。**沿用项目既有约定：端口 `schema_sha256` 一律从 schema 文件派生，不得手写。**

### 第 3 步：把这次模拟账套升级成组网验收用例

把 `sim/` 的 80 张凭证 → 3 张试算平衡表 → 8 项勾稽，改造成 `tests/evaluation/` 下的**固定基准用例**，用真实插件跑一遍，指标为：

- 8 项勾稽通过率（目标 100%）
- 8 张主表行项目覆盖率
- 43 个科目附注自动生成率
- 与人工编制版逐单元格差异数（目标 0）

这样"能自动化多少"就从一个判断题，变成一个**每次都跑得出来的数**。
