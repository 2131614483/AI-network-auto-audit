## 3. 已吸收进当前设计

| 参考思想 | 当前项目的吸收方式 |
| --- | --- |
| 模块能力图、流程图、本体图、证据图四图协同 | 明确拆为 T/W/O/E 四个图族，各自有权威所有者，通过版本化 Ref 协同 |
| 业务域与技术家族同时存在 | 插件集群改为多轴成员关系：业务、能力、运行池、治理区；取消单一 `cluster_id` |
| `PRODUCES/CONSUMES` 推导组合能力 | 蓝图输入输出升级为带 SemVer、格式、交付方式、数据分级的接口契约 |
| 模块依赖、兼容、替代、场景适用 | 进入 T 图的显式有类型边；替代路径必须契约兼容且不能静默升级风险 |
| 能力缺口查询 | 路由计划新增 `unresolved_capabilities`，缺能力时停止并报告 |
| YAML 流程与 module-lock 可复现 | 增加 `PluginTopologyRelease`；计划锁定目录 SHA、planner 版本、健康快照 Ref 和 trace |
| default/custom/runtime 三级配置 | 默认配置不可变、自定义配置版本化、运行时覆盖带 TTL；覆盖不能扩大权限 |
| 消息总线与 KG 各司其职 | 本地继续使用 PostgreSQL Outbox/Inbox；KG 不承担事件传递、锁、队列或心跳 |
| 5 层数据下钻与 AI 总结 | 放入 E 图设计：模块→发现→Artifact→记录定位→派生总结；总结必须保留模型/Prompt/来源，不覆盖原证据 |
| Canvas 初始化与二级容错经验 | GUI 规范增加零尺寸防护、ResizeObserver、局部视图标记和可操作错误状态 |

## 4. 明确不直接照搬

| 参考方案 | 不直接照搬的原因 | 当前决策 |
| --- | --- | --- |
| Neo4j 作为所有模块注册与心跳主存储 | 高频心跳会污染语义图、放大写入，且引入新的生产前置依赖 | PostgreSQL Registry/运行表保存在线真相；图只存语义拓扑和快照 Ref |
| Redis/etcd/Kafka/Flink/Neo4j 同时作为 MVP 前置 | 与本机原生 PG16、无 Docker 的开发约束冲突，显著扩大运维面 | 定义 Adapter；当前使用 PostgreSQL、Outbox/Inbox、pgvector，规模证据出现后再替换 |
| `/execute` 作为所有模块统一入口 | 过于宽泛，无法从路径表达副作用、幂等和审批语义 | 继续使用 capability + 类型化请求 + Policy Gateway；蓝图阶段只 `plan_only` |
| 在图边上保存可执行条件字符串 | 可能成为绕过策略的表达式执行入口 | 边只存 `condition_ref`，条件本体必须单独发布、校验和审计 |
| 直接把 45 条数据边变成执行流程 | 数据兼容、风险、信息墙和循环尚未验证 | 只导入为候选依赖；规划时重新做契约/Policy/预算校验 |
| 把参考模块成熟度或模型指标视为可信 | 文档含模板、TODO 和未经本项目复测的效果声明 | 一律作为来源事实；当前成熟度从 `idea/contracted` 起步 |
| 大对象经消息或控制图传递 | 造成重复、泄露与不可追溯 | 只传 ArtifactRef/GraphReleaseRef，权威正文留在领域模块 |
| 单个巨大统一本体和共享可变节点 | 会导致边爆炸、权限耦合和回滚困难 | 多图空间、有限桥接、分层预算、版本发布和回收站 |
