# 入口形状与资料缺口（2026-09-27）

上一轮收了尾说「下一步补 44 份入口形状声明（每份约 10 行），那是 71 节点全量的解锁点」。
这一轮把 64 个外部入口**逐条**走完（读运行时 + 找源文件），结论要改。

先厘清一件事：**入口种子一直是合成的**。归档那次全流程运行
（`审计项目案例报告效果展示/全流程运行日志-20260912/02-全流程时序日志/00-运行原始输出.log`）
写着 `nodes=100 edges=71 seeds=44` —— 44 个种子没一个来自案例资料，全是
`.data/_ai_compose_demo.py` 造的。所以真问题不是"能不能跑起来"（跑起来了），
而是"这些入口里有多少能改吃**真实案例资料**"。

> 答：把那次的组网调用**今天**重算（`select=<71 个已验证插件>` + `chain=<49 条主链>`，
> 今天得到 100 节点 / **42 个入口端口需要种子**，比当天少 2 个是 composer 之后有演进），
> 其中**能换成案例资料的只有 4 个**：`policy-input` `sampling-input` `raw-biz-set`
> `inventory-input`。**剩下 38 个换不了。**
> 形状声明不是 44 份内容工作；**把入口从合成种子换成案例资料的障碍是源资料，不是形状声明。**

## 方法（可复核）

1. **外部入口 = 被消费 − 被产出**，从 135 个插件的 `plugin.protocol.json` 算出：64 个，其中 audit 域 54 个
   （与 `a8a2c48` 提交信息里的 54 一致）。
2. 逐条读消费方 `runtime.py` 的 `handle()`，抽出**运行时期望的顶层键与逐项字段**（不是猜 schema，
   是读它实际 `payload.get(...)` 什么）。
3. 逐条在三个案例变体里找**对口源文件**，并核对真实表头。
4. 能声明的写进 `contracts/input-shapes.json` 的 `shapes`，且对着真实资料真跑一遍插件；
   不能声明的写进同一个文件的 `unmet`，标清楚**卡在哪一类**（`blocker`）与**缺什么**（`need`）。

`unmet` 不是"待填的空白声明"：glob 匹配不到文件会直接报错，把缺源的入口写成声明等于埋雷。
它是**已探明的形状 + 明确的缺什么** —— 下一步该照它去补资料，而不是照它去补声明。

## 三个值得单独说一句的发现

1. **`mask-request` 是静默失效，不是跑不起来。** 该插件按**列名里的英文关键词**
   （`name`/`id`/`phone`/`account`/`card`）决定哪些列打码，而案例 CSV 的列名全是中文
   （凭证号/科目编码/客户…）。喂进去会返回「成功、已脱敏、N 行」，但**一个字段都没动**。
   要么给英文列名的明细，要么把脱敏词表改成中文口径 —— 这条比缺源更危险。
2. **`asset-input` 在本案例上永远无话可说。** 它只在「账面位置 ≠ 实盘位置」时出违规，而案例的
   固定资产盘点表只有数量（账面数量/实盘数量）或状态（在用/在），**没有位置列**。
   补这份资料比补声明有价值。
3. **盘点表的口径不得不声明出来。** 存货盘点表的数量列按类别混用单位（成品「件」、原辅料「吨」），
   未盘类别整列记 `—`。不做声明就只能靠人肉清洗，而人肉清洗出来的数无法复核：
   `1,286,400 件` 剥成 `1286400`、`—` 整行跳过并计数（**不填 0**，填 0 会刷出满屏假差异）。

## 机制改了什么（`packages/catalog/input_shapes.py`）

原来只有「每文件一项」（`items_from.item`，吃 markdown），而案例资料里 CSV 占一半。新增：

- **`items_from.columns`：每行一项**（CSV 源）。与 `item` 二选一 —— 一份声明同时给两种粒度，
  没人说得清产出的是几项。
- **`numbers`：声明的数值清洗**。只剥声明里列出的分隔符与单位后缀；`1.286.400 箱` 这种
  没列出来的写法**直接报错**，而不是当成"大概也是千分位"抹掉。
- **`skip_rows`：声明的无数据记号**。数值列写 `—` 的行整行跳过并在返回值里计数（`skipped`）。

三条都是**声明出来的口径**、不是代码里的猜，与 `input_mapping` 的 `blank_value` / `row_filter`
同一路子。两条硬约束没变：声明里的列取不到就报错、glob 匹配不到就报错。

验证：单测 18 例（含"每个外部入口要么已声明、要么进 unmet"的登记测试），集成测试把 5 条声明
对着真实案例资料喂进真插件跑通。`inventory-input` 在实验组上抓出 3 项账实差异，含按吨计的原辅料行。

## 一个要定的结构性问题

同一入口在**不同变体上需要不同声明**：存货盘点表只在实验组有，底稿 markdown 只在对照组有。
而现在 `input-shapes.json` 是一张扁平表，没有数据集维度。这轮靠 glob + 硬失败顶住了，
但这是设计上要拍板的：要么承认「一份数据集一份声明」并把声明按数据集分文件，
要么继续用 glob 吸收差异（代价是变体一多，glob 会变成猜）。

## 下一步（按性价比排）

1. **补资料，不是补声明**：照 `unmet` 的 `need` 去收/造那 18 份计划内缺源的入口资料。
2. **先摘低垂的 3 个**：`metadata-query`（每列一项）、`nlp-input`（标量根）、
   `audit-source-request`（项是字符串 + 读 Markdown 表格）—— 资料已经在手上，
   补的是声明框架的粒度，做完就能直接多喂 3 个入口。
3. **改口径**：`mask-request` 的脱敏词表改成中文列名（这是产品缺陷，不是数据缺口）。
4. **改目标**：承认"案例资料撑不住全量"，把入口分成「案例可驱动」（今天 4 个）与「需夹具」
   （其余 38 个），后者继续用合成种子、但把合成口径写下来。这比硬凑"全量都吃案例资料"诚实。
